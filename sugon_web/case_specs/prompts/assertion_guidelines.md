# 自动化测试断言编写规范

> **目标**：指导 AI 在编码自动化脚本时合理编写断言，让 UI 用例既不因断言过多而脆弱，也不因断言过少而漏 Bug。
> **适用范围**：SugonCloud 云计算平台 Web UI 自动化测试（Python + Playwright + Pytest + POM）。
> **关联文件**：编码前必读 `../fixtures_index.md`，了解 fixture 复用规范；断言方法定义于 `sugon_web/assertions/`（详见该目录下 `README.md`）。
> **重要声明**：本文档中引用的文件名和方法名均为**当前已有示例**，不代表完整清单。`sugon_web/assertions/` 目录随模块持续扩展，新增断言请按规范自行搜索和创建。

---

# 第一部分：判断测试步骤是否需要写断言

## 一、核心原则

**断言的位置比数量更重要。**

不是"每步都断"，也不是"只断最后"。云计算平台的长流程用例（10-20 步）如果每步都断言，会因异步延迟、状态收敛慢而导致极高的误失败率；如果断言过少，又无法发现中间状态的 Bug。

**平衡公式（参考业界实践）**：

```
UI 自动化断言数 = 流程关键节点数 + 最终业务出口数
```

- **流程关键节点**：失败会导致后续步骤无法执行、或定位困难的操作（如资源创建失败）。
- **最终业务出口**：用例要验证的核心业务结果（如 curl 验证负载均衡转发正确）。

---

## 二、断言分层模型（P0 / P1 / P2 / P3）

将断言按优先级分为四层。每层对应不同的断言时机和策略。

### 第一层：P0 流程阻塞点断言（强制，绝对不能省）

**定义**：验证操作被系统接受（如成功弹窗/Toast 出现）且关键资源/规则已生效（如资源出现在列表中、状态已收敛到目标态），失败会阻塞后续流程或产生脏数据。这一层是测试继续执行的"底线"。

> **P0 与 P1 的边界**：P0 只断言"操作提交成功 + 资源存在性/状态收敛"，**不断言字段值的具体内容**。字段值（如端口、协议、CIDR、规格、名称）在 P1 集中验证。同一操作不重复断言。
>
> 示例：创建安全组规则 → P0 断言"创建成功弹窗出现 + 规则存在于列表中"；P1 断言"端口、协议、方向、CIDR 字段值与输入一致"。再如重置密码 → P0 断言"重置成功弹窗出现"；若后续步骤依赖新密码，则新密码的生效验证属于 P2（SSH 登录验证），不属 P0。

**包含场景**：

| 场景分类 | 具体场景举例 |
|:---|:---|
| **资源生命周期操作** | 计算/存储/网络/数据库/中间件/缓存资源的创建、删除、开机、关机、重启、重置密码、扩容 |
| **资源关联与解绑** | 云硬盘挂载/卸载到ECS、EIP绑定/解绑到实例、安全组绑定/解绑到网卡、负载均衡监听器关联/解绑资源池、RDS只读实例关联/解绑主实例、备份策略绑定/解绑资源 |
| **核心配置变更** | 安全组规则（入站/出站规则）增删改、路由表规则增删改、负载均衡转发规则增删改、DNS解析记录增删改、RDS参数组修改、对象存储桶策略修改、防火墙/访问控制规则配置 |
| **异步状态收敛** | 资源创建后从"创建中"到"运行中"、ECS开机后从"开机中"到"运行中"、备份任务从"备份中"到"已完成"、扩容操作从"扩容中"到"完成"、故障迁移后状态恢复 |
| **异步任务/作业完成确认** | 批量创建/删除任务执行完成、数据迁移任务完成、镜像制作任务完成、批量导入任务完成、定时任务执行结果确认 |
| **资源清理确认** | 删除操作后资源在列表中消失、解绑后关联关系解除、批量删除后所有目标资源已清理、释放后资源不可恢复 |
| **后台服务启动命令** | 通过 `nohup` 等方式后台启动 Web/数据库/消息队列等关键服务，必须断言服务进程已正常启动。服务启动失败会直接阻塞后续所有验证步骤 |

**⚠️ 等待是断言的前置条件，不能省略。** 云平台异步操作多，未等待状态收敛就断言是误失败的最主要原因。资源创建后可能处于"创建中"状态，直接断言"运行中"大概率失败，应先调用状态等待方法等待中间态消失后再断言。

---

### 第二层：P1 末态字段断言（强制，集中断言）

**定义**：验证操作完成后，UI 上展示的字段值与预期完全一致。这一层将分散的字段校验集中在流程末态一次性完成，避免每个字段都触发一次页面操作。

> **注意**：P1 负责验证字段值，与 P0 配合时，P0 已验证"操作成功 + 存在性"，P1 不再重复断言存在性，只聚焦字段内容。

**包含场景**：

| 场景分类 | 具体场景举例 |
|:---|:---|
| **创建后字段回读** | 创建资源后回读规格、容量、网络配置、版本等关键字段值 |
| **修改后字段回读** | 修改资源规格/名称/规则/端口/参数/标签后，回读对应字段值 |
| **查看/查询后字段验证** | 打开资源详情页后验证当前字段值与预期一致、列表页查询后验证展示数据与查询条件匹配、筛选后验证列表数据与筛选条件一致 |
| **末态一致性验证** | 批量创建后各资源字段均正确、关联操作后关联双方字段均正确、配置下发后配置项在UI正确展示、跨页面数据一致性（列表页与详情页字段一致） |

---

### 第三层：P2 业务逻辑断言（建议，价值所在）

**定义**：验证业务逻辑正确性，但失败不会阻塞后续流程。这一层的断言是测试的"价值"所在，能发现功能 Bug，但漏写不会导致测试框架崩溃。

**包含场景**：

| 场景分类 | 具体场景举例 |
|:---|:---|
| **后台服务就绪验证** | ECS内应用服务、容器Pod、中间件、数据库等已启动可访问 |
| **网络连通性验证** | 同VPC/跨VPC互通、负载均衡VIP转发、NAT/VPN规则生效、安全组规则生效 |
| **数据内容一致性验证** | 文件/数据库/对象存储写入后内容正确；备份恢复、快照回滚、消息队列收发后数据完整 |
| **后端实际状态与 UI 配置一致性** | CLI/API查询资源状态/规则/参数/后端等与UI展示一致 |
| **权限与访问控制验证** | 有权限/无权限/越权用户的访问控制验证；角色切换、资源共享后权限范围变化 |
| **定时策略与自动化验证** | 定时备份/伸缩/任务按计划触发执行；告警通知；生命周期规则到期自动执行 |
| **高可用/容灾验证** | 主备切换/多可用区故障/后端节点摘除后的业务连续性；数据库主从切换一致性；存储多副本数据不丢失 |
| **性能与规格验证** | SSH验证ECS实际CPU核数/内存大小与购买规格一致；实测带宽速率达到购买规格；存储配额/数据库连接数限制实际生效 |

---

### 第四层：P3 隐式验证层（无需显式 assert）

**定义**：导航类、操作类步骤，操作本身成功即代表验证通过。用 Page Object 方法内部的等待机制代替断言。

**适用动作**：
- 页面导航与菜单跳转
- Tab 切换与子页面切换
- 按钮点击（非提交类：打开表单、返回、取消、刷新、翻页）
- 表单填写（文本输入、下拉选择、单选/多选、日期选择、文件上传选择）
- 搜索/筛选/排序操作（输入搜索关键词、点击筛选标签、点击表头排序）
- 分页/滚动加载操作（点击分页按钮、滚动加载更多数据）
- 展开/收起/折叠操作（展开详情面板、收起配置项、折叠树形节点）
- 弹窗打开/关闭（确认弹窗的打开、关闭弹窗、关闭提示）
- Loading/Spinning 等待
- SSH 连接建立与断开
- 无返回值的命令（目录创建、文件写入、配置复制、环境变量设置）
    - **注意：若命令目的是后台启动服务，则上升至 P0，不在此列**

**原则**：用 Page Object 封装的方法执行操作，内部等待机制确保页面加载完成；SSH 连接失败会自然抛异常；无返回值命令的成功由后续步骤隐式验证。测试层严禁直接访问 Playwright 底层 `page` 对象做断言。

---

## 三、断言决策树

编写每一个操作步骤时，按以下决策树判断是否需要写断言：

```
当前操作步骤
│
├─ 是纯交互/导航/准备步骤，不涉及业务状态变更或结果验证？
│   （页面导航 / 菜单跳转 / Tab切换 / 点击打开表单或弹窗 / 文本输入 / 下拉选择
│    搜索筛选排序 / 分页滚动 / 展开收起 / SSH连接建立 / 无返回值命令）
│   │
│   └─ YES → 【P3 隐式验证】无需显式 assert
│              Page Object 方法内部已包含等待
│              后续操作能执行即证明成功
│              ↓ 结束
│
├─ 如果这一步失败了，后续步骤必然失败或产生脏数据？
│   （资源创建 / 绑定关联 / 核心配置变更提交 / 状态收敛 / 异步任务完成 / 清理完成
│    后台服务启动命令）
│   │
│   └─ YES → 【P0 流程阻塞点断言】必须写 assert
│              顺序：操作成功断言 → 存在性断言 / 状态断言
│              ↓ 结束
│
├─ 当前处于流程末态，需要验证字段值是否正确？
│   （创建后详情页回读 / 修改后回读 / 查看查询后字段 / 列表字段完整性）
│   │
│   └─ YES → 【P1 末态字段断言】必须写 assert
│              行数据集中断言所有关键字段
│              ↓ 结束
│
└─ 这一步验证的是端到端业务正确性，而非操作提交或字段展示？
    （后台服务就绪 / 数据一致性 / 网络连通 / 后端配置一致 / 权限控制
     定时策略 / 高可用容灾 / 性能规格）
    │
    ├─ YES → 【P2 业务逻辑断言】推荐写 assert
    │           SSH 验证：断言命令返回码 + 断言输出内容匹配
    │           服务就绪：轮询等待 + 超时断言
    │           ↓ 结束
    │
    └─ NO  → 重新审视当前步骤定义。每个步骤必然属于上述四类之一，
               若走到此处说明前面判断有误。
               常见误判：把"等待状态收敛"步骤忽略了 P0；
               把"进入详情页验证字段"步骤忽略了 P1。
               建议从 Q1 重新判断。
               ↓ 结束
```

# 第二部分：如何写断言

> **编写顺序**：优先复用项目已有断言方法 → 没有可复用的再自行编写。

## 四、断言编写决策流程

```
1. 搜索项目中已有断言方法 → 有匹配方法？直接复用
2. 无匹配方法 → 判断断言类型：
   ├─ UI 层面断言（弹窗/元素存在性/状态/字段值）→ 在 assertions/ 层封装 Mixin（遵循 7.1）
   └─ SSH 后端验证（服务就绪/数据一致/网络连通）→ 测试层直接写 assert（遵循 7.2）
```

## 五、查找已有断言方法（编码前必做）

项目中已有断言分散在 `sugon_web/assertions/` 目录下，**编码前务必先搜索，避免重复造轮子**。断言方法随业务模块持续新增，本文档不维护静态枚举列表。

### 断言存放位置

| 目录 | 类型 | 说明 |
|:---|:---|:---|
| `assertions/base/` | Mixin | 通用断言：弹窗、列表、状态（任何模块都能复用） |
| `assertions/<模块>/` | Mixin | 专属断言：依赖具体业务页面结构（如 `network/slb.py` 的 `SlbAssertionMixin`） |
| `assertions/helpers/` | 纯函数 | 无 `self`，供多模块复用的场景级验证（如轮询算法验证） |

### 搜索命令（编码前必执行）

```bash
# 搜索项目中已有的断言方法（按被测对象或验证点关键词）
grep -r "def assert_<你的对象>" sugon_web/assertions/

# 示例：验证资源池相关的断言方法
grep -r "def assert_pool" sugon_web/assertions/
```

### 判断能否复用的标准

- 方法名匹配 `assert_<你的对象>_<你的验证点>` → **直接复用**
- 方法名接近但对象不同 → **参考其实现**，在对应模块的 assertions/ 下新建专属版本
- 完全找不到匹配 → **按 7.1 规范自行编写**，详见 `sugon_web/assertions/README.md`

### 使用方式

Page Object 通过**多重继承**引入断言 Mixin：

```python
from sugon_web.assertions import PopupAssertionMixin, ListAssertionMixin, SlbAssertionMixin

class SlbPage(SlbAssertionMixin, PopupAssertionMixin, ListAssertionMixin, BasePage):
    pass
```

纯函数直接从 helpers 引入：

```python
from sugon_web.assertions.helpers import assert_lb_algorithm
```

## 六、断言层新增方法决策

用于指引 AI 在新增断言方法时，正确决定存放位置与形态，确保与 `sugon_web/assertions/` 现有代码风格一致。

### 6.1 UI 断言具体写在哪个文件里

**先判定形态，再判定路径。**

#### Step 1 — 判定形态

问：这个断言是否需要操作页面元素（`self` / `page` / `locator` / 点击 / 搜索 / 刷新）？

- 需要页面上下文 → **Mixin 形态**（有 `self`，通过多重继承注入页面对象）
- 不需要页面上下文 → **纯函数形态**（无 `self`，调用方传入数据）

#### Step 2 — 判定文件路径

| 形态 | 通用性 | 写入路径 | 现有示例 |
|:---|:---|:---|:---|
| Mixin | 任何模块都能复用 | `sugon_web/assertions/base/<类别>.py` | `base/popup.py` 的 `PopupAssertionMixin` |
| Mixin | 仅当前业务模块使用 | `sugon_web/assertions/<模块>/<服务>.py` | `network/slb.py` 的 `SlbAssertionMixin` |
| 纯函数 | 被 >=2 个模块复用 | `sugon_web/assertions/helpers/<功能>.py` | `helpers/__init__.py` 的 `assert_lb_algorithm` |
| 纯函数 | 仅当前模块使用 | `sugon_web/assertions/<模块>/<服务>.py` | `compute/ecs.py` 的 `assert_ecs_details_info` |
| 纯函数 | 仅当前用例使用 | 不写 assertions 层，放测试文件内 | 直接使用 `assert xxx` |

### 6.2 通用断言 vs 专属断言的区分标准

**判定标准只有一条：删除所有业务专属选择器后，方法逻辑是否仍然完整可用？**

#### 通用断言

- 答案为"是"。不依赖具体资源的页面结构，只依赖通用组件（表格、弹窗、对话框）。
- 写入 `base/`（Mixin）或 `helpers/`（纯函数）。
- 示例：`assert_popup_success`（任何页面都适用）、`assert_deleted`（任何资源删除都适用）。

#### 专属断言

- 答案为"否"。方法体内使用了业务专属选择器或业务语义（如"监听器"、"资源池"、"ECS"）。
- 写入 `<module>/`。
- 示例：`assert_lb_basic_info`（依赖 SLB 详情页嵌套 Tab 结构）、`assert_ecs_details_info`（依赖 ECS 详情字段定义）。

#### 边界情况

- 一个验证流程同时涉及 UI 定位和数据比较 → **统一用 Mixin**，由 Mixin 内部先定位再比较，不强制拆分为纯函数。
- 数据比较逻辑被 >=2 个 Mixin 复用 → 将比较逻辑提取为 `helpers/` 纯函数，Mixin 方法内部调用之。

---

### 6.3 断言方法归类的判断标准

#### 命名规则

| 项目 | 规则 | 正确示例 | 错误示例 |
|:---|:---|:---|:---|
| Mixin 类名 | `<业务>AssertionMixin` | `SlbAssertionMixin` | `SlbAssert` |
| 方法名 | `assert_<资源>_<验证点>` | `assert_listener_exists` | `assert_data` |
| 纯函数名 | `assert_<资源>_<验证点>` | `assert_ecs_details_info` | `check_ecs` |

#### Mixin 形态检查清单

- [ ] 不定义 `__init__`
- [ ] `timeout` 参数必须有默认值
- [ ] Docstring 必填
- [ ] 优先用 `expect()` 做 UI 状态断言，`assert` 做后端/逻辑断言

#### 纯函数形态检查清单

- [ ] 无 `self`
- [ ] 参数 `actual` 与 `expected` 成对出现
- [ ] Docstring 首行注明"纯函数，只比较数据，不操作页面"
- [ ] 错误消息格式：`[<分类标签>] <被测对象> | <描述> | 期望: x | 实际: y`

#### 错误消息分类标签

`assert` 语句必须使用以下分类标签之一：

| 标签 | 适用场景 |
|:---|:---|
| `[PopupAssertion]` | 弹窗/Toast/对话框 |
| `[ListAssertion]` | 列表存在性、删除验证 |
| `[StatusAssertion]` | 资源状态收敛 |
| `[FieldAssertion]` | 详情页/弹窗字段值 |
| `[BackendAssertion]` | SSH/API/后端验证 |
| `[ScenarioAssertion]` | 算法/场景/端到端 |

#### 绝对禁止

1. 在 `helpers/` 中写页面元素断言（helpers 只放纯函数）。
2. 在 `pages/*.py` 中写断言逻辑（页面对象只负责业务操作）。
3. 强制将所有 Mixin 拆分为纯函数（按场景选择形态，UI 断言保留 Mixin）。
4. 命名模糊如 `assert_data`（必须用 `assert_<资源>_<验证点>`）。

---

### ⚠️ 强制约束：公共断言方法禁止修改

**`sugon_web/assertions/` 目录下已封装的断言方法（含 `base/`、`helpers/` 及各模块下），一律禁止直接修改。**

理由：
- `base/` 下的通用断言（如 `assert_popup_success`、`assert_deleted`、`assert_status`）被**所有模块的 Page Object 继承**，修改一处会影响全平台，风险最高
- `helpers/` 下的纯函数被多个模块复用，同样禁止直接修改
- 需要适配新场景 → 新建方法或新增可选参数（默认值保持原行为不变）
- 发现 Bug 需修复 → 确认影响范围后统一修复，不可局部 hack

正确做法：
- 功能扩展 → 新建 `assert_<资源>_<新验证点>` 方法
- 参数扩展 → 新增可选参数，默认值保持原行为
- 行为差异大 → 在对应模块下新建专属版本

## 七、自行编写断言的规范

### 7.1 自定义断言方法编码规范

当项目中没有可复用的断言方法时，按断言类型选择编写位置：

- **UI 层面断言**（弹窗出现、元素存在性、资源状态、字段值等）→ **在 `sugon_web/assertions/` 层封装 Mixin**，编码遵循本节规范及 `sugon_web/assertions/README.md`
- **SSH 后端验证**（服务就绪、数据一致、网络连通等）→ **在测试层直接写 `assert`**，遵循 7.2 SSH 验证规范；若需跨用例复用，可封装到对应模块的 `assertions/<模块>/` 或 `assertions/helpers/`

---

#### 命名规范

- 前缀必须是 `assert_`
- 格式：`assert_<被测对象>_<验证行为>`
- 示例：`assert_user_exists`、`assert_response_status`、`assert_listener_exists`
- **禁止**命名模糊的方法，如 `assert_data`、`assert_result`、`assert_ok`

#### 参数设计规范

- 参数命名必须语义明确，**禁止**使用 `arg1`、`arg2`、`x`、`y` 等无意义命名
- 控制类参数（如 `timeout`、`retry`、`refresh`）**必须**有默认值
- 可选校验项使用 `None` 做默认值，表示"该校验项本次不验证"
- 参数顺序：被测对象 → 校验条件 → 控制参数

#### 方法体规范

- **单一职责**：一个 assert 方法只验证一个独立点，禁止一个方法里验证多个不相关的条件
- **UI 元素可见性/存在性断言**：优先使用 Playwright `expect()`（内置自动轮询等待，避免异步导致的误失败）
- **字段值比较、状态判断**：使用原生 `assert` 语句，统一抛出 `AssertionError`，禁止用 `try/except` 包裹并吞掉异常
- **失败信息必须包含三要素**：被测对象、期望结果、实际结果
- **需要等待时必须轮询检查**，禁止固定等待（如 `time.sleep(5)`）。Playwright `expect()` 已内置轮询，使用 `assert` 时需自行实现轮询逻辑
- **无副作用**：assert 方法不返回值，不修改被测对象状态

#### 文档规范

- 必须有 docstring，包含：
  - **验证目的**：该方法验证什么
  - **参数说明**：类型、默认值、含义
  - **异常说明**：失败时抛出什么异常、异常信息包含什么

```python
def assert_status(self, names, status, timeout=300, refresh=False):
    """断言指定资源的状态收敛到目标状态。

    Args:
        names: 资源名称或名称列表。
        status: 期望的状态值，如"运行中"。
        timeout: 轮询超时时间（秒），默认 300。
        refresh: 是否自动刷新列表，默认 False。

    Raises:
        AssertionError: 超时后状态仍未收敛到期望值。
    """
```

#### 禁止项清单

| # | 禁止行为 | 正确做法 |
|:---:|:---|:---|
| 1 | 命名模糊如 `assert_data`、`assert_ok` | `assert_<对象>_<行为>` |
| 2 | 参数无意义命名如 `arg1`、`arg2` | 语义化命名如 `names`、`status`、`timeout` |
| 3 | 控制参数无默认值 | `timeout=300`、`retry=3` |
| 4 | `try/except` 吞掉断言异常 | 直接 `assert` 抛出，让框架捕获 |
| 5 | 失败信息不含被测对象、期望结果和实际结果 | `f"资源 {name} 期望状态 {expected}，实际 {actual}"` |
| 6 | 固定等待如 `time.sleep(60)` 后直接断言 | 轮询检查（循环内允许 `time.sleep(短间隔)` 作为轮询间隔）+ 超时 |
| 7 | assert 方法返回值 | 方法体以 `assert` 结束，无 `return` |
| 8 | assert 方法修改被测状态 | 只读验证，禁止调用修改接口 |
| 9 | 一个 assert 方法验证多个独立点 | 拆分为多个单一职责方法 |

### 7.2 SSH 验证规范（适用于所有涉及 SSH 的断言层级）

当项目中没有现成方法可用时，通过 SSH 自行编写断言需遵循以下规范：

```python
result = ssh_vm.run("command", return_rc=True)

# 必须断言 return code
assert result["rc"] == 0, f"命令执行失败: {result.get('stderr', '')}"

# 必须断言输出内容（不要只记录日志）
assert "预期内容" in result["stdout"], f"期望输出...，实际: {result['stdout']}"
```

**严禁**：
- 使用 `` `|| true` `` 掩盖命令错误
- 只调用 `logger.info()` 记录结果而不做 assert
- 对 `mkdir`、`echo`、`cp` 等无返回值的命令写显式断言（由后续依赖步骤隐式验证）

**服务就绪轮询规范**：

当需要验证后台服务（如 Web 服务、数据库）是否就绪时，必须使用轮询检查，禁止固定等待。

```python
# 正确：轮询检查，超时后断言
for _ in range(30):
    result = ssh_vm.run("ss -lntp | grep 8080", return_rc=True)
    if result["rc"] == 0 and "8080" in result["stdout"]:
        break
    time.sleep(2)
else:
    raise AssertionError("后台服务未在60秒内就绪")

# 错误：固定等待，浪费时间且不可靠
time.sleep(60)  # ❌ 禁止固定等待
```

### 7.3 断言编写反模式

以下写法是断言过多导致脆弱或断言无效的典型错误，编码时必须避免。

| # | 反模式 | 错误做法 | 正确做法 |
|:---:|:---|:---|:---|
| 1 | 导航后断言 | `assert "负载均衡" in page.title()` | `vpc_page.goto_service("负载均衡")`，内部已 wait |
| 2 | 未等待就断言 | 资源还在"创建中"就断言"运行中" | 先 `wait_for_source_complete()` 再断言 |
| 3 | 日志代替断言 | `logger.info(f"结果: {result}")` | `assert result["rc"] == 0` |
| 4 | `\|\| true` 掩盖错误 | `ssh_vm.run("cmd || true")` | `ssh_vm.run("cmd", return_rc=True)` 后断言 rc |
| 5 | 分散断言字段 | 每个字段操作一次页面 | 末态时 `get_row_data()` 一次性获取集中断言 |
| 6 | 条件过宽 | `assert "运行" in status` | `assert status == "运行中"` 精确匹配 |

### 7.4 断言数量参考

一个完整用例的断言分布自检标准：

| 优先级 | 类型 | 典型数量 | 自检方法 |
|:---:|:---|:---:|:---|
| P0 | 流程阻塞点 assert | **2～4 个** | 资源创建、状态收敛、核心配置、清理确认 |
| P1 | 末态字段 assert | **1～3 个** | 创建后详情页回读、修改后字段集中断言 |
| P2 | 业务逻辑 assert | **0～3 个** | 服务就绪、数据一致、后端验证 |
| P3 | 隐式验证 | 每步都有 | 检查是否使用了 `wait_for_page_ready()` / `wait_for_source_complete()` |

**警戒线**：
- 如果一个用例有超过 **10 个分散的 assert**，通常说明把 P3（导航动作）也写了断言，需要审查并删减。
- 如果一个用例只有 **1～2 个 assert**，通常说明遗漏了 P0 关键检查点（如资源创建成功未断言、核心配置变更未断言），需要补充。

### 7.5 编码自检清单

编码完成后，用以下清单快速检查断言是否合理。

**断言覆盖检查**：

- [ ] 导航/操作类步骤没有显式断言（P3）
- [ ] 创建/修改/绑定操作后，有成功弹窗则断言 `assert_popup_success()`；
  静默保存（无 Toast）的修改操作无需此项，直接进 P1 字段回读（P0）
- [ ] 删除操作后断言资源已从列表消失（`assert_deleted` / `assert_list_not_contain`），
  而非断言弹窗（P0）
- [ ] 每个资源创建后都有存在性断言（`assert_list_contain` / `assert_资源_exists`）（P0）
- [ ] 每个绑定/关联操作后都有关联关系生效断言（绑定侧和被绑定侧列表/字段均已更新）（P0）
- [ ] 状态变更类操作先 `wait_for` 收敛再断言（P0）
- [ ] 流程末态有一次性集中字段断言（P1）
- [ ] 核心配置生效类功能有 SSH 后端验证（P2）
- [ ] SSH 命令执行后断言了 `rc` 和 `stdout`（P2）
- [ ] 没有用 `logger.info` 代替断言
- [ ] 没有用 `|| true` 掩盖命令错误
- [ ] 断言总数在 3～8 个之间（长流程用例不超过 10 个）

**自定义断言方法规范检查**（如编写了新的 assertions Mixin）：

- [ ] 方法命名符合 `assert_<对象>_<行为>` 格式，无模糊命名
- [ ] 方法有完整的 docstring（验证目的、参数说明、异常说明）
- [ ] 失败信息包含被测对象、期望结果、实际结果三要素
- [ ] 不使用 `try/except` 吞掉异常、不返回值、不修改被测状态
