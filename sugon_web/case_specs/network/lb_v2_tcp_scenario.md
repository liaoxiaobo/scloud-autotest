## 前置条件

> 以下资源在多个场景中复用

1. 已预置VPC（如vpc1），并在VPC下创建四台虚机：ecs0、ecs1、ecs2、ecs3

## 测试步骤

### 场景1：v2-新建监听器-TCP+轮询基本功能验证（用例编号：436717）

#### 步骤1：进入负载均衡模块

- 操作：进入负载均衡模块，依次点击：产品与服务 -> 网络 -> 负载均衡SLB
- 预期：可以正常进入负载均衡模块，lb列表可以正常显示

#### 步骤2：进入监听器详情页

- 操作：在slb列表页，点击预置的实例名称slb-v2，进入详情，选择监听器tab
- 预期：详情页可以正常显示

#### 步骤3：创建TCP监听器

- 操作：点击新建按钮，按如下参数创建TCP监听器
  - 监听器名称：由 random_data() 生成
  - 描述：1234567890edwqWDWQ中文~
  - 协议：TCP
  - 协议端口：8080
  - 资源池名称：由 random_data() 生成
  - 负载调度算法：轮询
  - 不开启会话保持
  - 不开启健康检查
- 预期：
  - 创建监听器成功并提示信息
  - 监听器详情页显示信息与新建数据一致

#### 步骤4：添加资源池成员

- 操作：在slb-v2详情页 -> 监听器tab下 -> 点击监听器名称 -> 选择资源池tab，进入资源池详情后，点击创建按钮，选择ecs1、ecs2、ecs3为该资源池的成员，对应端口为8080
- 预期：
  - 新建成员成功
  - 资源池列表显示信息与新建资源数据一致

#### 步骤5：后端虚机启动web服务

- 操作：使用 `ssh_vm` fixture 分别连接ecs1、ecs2、ecs3的MFIP，执行如下操作
- 子步骤：
  1. 创建测试目录：`cd /root && mkdir -p test`
  2. 创建测试文件：`cd /root/test/ && echo "this is ecsN" > index.html`（N对应ecs编号）
  3. 后台启动web server：`cd /root/test/ && nohup python3 -m http.server 8080 > /dev/null 2>&1 &`
  4. 轮询等待60秒内检查端口：`ss -lntp | grep 8080`
- 预期：
  - 目录创建成功
  - 文件创建成功
  - web服务启动成功

#### 步骤6：内网VIP访问测试

- 操作：使用 `ssh_vm` 连接ecs0，执行 `curl http://$lb_vip:8080/index.html`，多次执行
- 预期：
  - 执行成功，显示"this is ecsX"
  - 多次执行后，整体符合1:1:1的轮询规律

#### 步骤7：绑定公网IP

- 操作：在负载均衡列表页，点击绑定公网ip按钮，绑定公网ip
- 预期：fip绑定成功，可以在列表显示绑定的公网ip地址

#### 步骤8：公网IP访问测试

- 操作：使用 `ssh_host` 连接测试环境，执行 `curl http://$lb_fip:8080/index.html`，多次执行
- 预期：
  - 执行成功，显示"this is ecsX"
  - 多次执行后，整体符合1:1:1的轮询规律

### 场景2：v2-健康检查器-TCP基本功能验证（用例编号：436718）

> 依赖：场景1（用例436717）已执行完成

#### 步骤1：创建TCP监听器（开启健康检查）

- 操作：按前置条件创建TCP监听器，开启健康检查，类型选择TCP，其它参数保持默认值
  - 协议：TCP
  - 端口：8080
  - 健康检查：开启，类型TCP
  - 资源池成员：ecs1、ecs2、ecs3
- 预期：可以正常创建TCP监听器，并且web服务可以正常开启

#### 步骤2：确认Real-Server初始状态

- 操作：进入资源池详情页，确认各Real-Server状态
- 预期：因各节点已开启web服务，所以rs显示运行中状态

#### 步骤3：停止ecs1和ecs2的web服务

- 操作：使用 `ssh_vm` 分别连接ecs1、ecs2，执行 `pkill -f 'python3 -m http.server 8080'` 停止web服务
- 预期：可以正常退出

#### 步骤4：确认健康状态变化

- 操作：在资源池详情页，确认各Real-Server状态
- 预期：只有ecs3是健康的，状态为运行中

#### 步骤5：内网VIP访问测试（健康检查后）

- 操作：使用 `ssh_vm` 连接ecs0，执行 `curl http://$lb_vip:8080/index.html`，多次执行
- 预期：执行成功，会显示"this is ecs3"，多执行几次后，都是显示此提示信息

#### 步骤6：恢复ecs1和ecs2的web服务

- 操作：使用 `ssh_vm` 分别连接ecs1、ecs2，后台启动web服务
- 预期：web服务可以正常启动

#### 步骤7：确认全部恢复运行中

- 操作：在资源池详情页，确认各Real-Server状态
- 预期：三个节点均显示为运行中状态

#### 步骤8：关闭健康检查

- 操作：在资源池详情页，点击健康检查-配置，关闭健康检查
- 预期：健康检查关闭成功

#### 步骤9：再次停止ecs1和ecs2的web服务

- 操作：使用 `ssh_vm` 分别连接ecs1、ecs2，停止web服务
- 预期：各Real-Server显示为运行中状态，停掉web服务不影响其健康状态

#### 步骤10：内网VIP访问测试（关闭健康检查后）

- 操作：使用 `ssh_vm` 连接ecs0，执行 `curl http://$lb_vip:8080/index.html`，多次执行
- 预期：请求到ecs3时访问通，请求到ecs1或ecs2时访问不通

#### 步骤11：确认健康检查状态为关闭

- 操作：在资源池详情页，确认健康检查状态
- 预期：应该显示为关闭状态

#### 步骤12：重新开启健康检查

#### 步骤13：再次恢复ecs1和ecs2的web服务

- 操作：使用 `ssh_vm` 连接ecs0，执行 `curl http://$lb_vip:8080/index.html`，多次执行

## ⚠️ 实现注意事项

### 1. SSH操作强制约束

- 若测试步骤或前置条件中需要SSH到服务器后台或虚拟机后台执行命令，**必须**调用 `sugon_web/common/ssh.py` 中封装好的公共方法
- 推荐使用fixture：
  - `ssh_vm` fixture：通过跳板机连接虚机的SSH会话
  - `ssh_host` fixture：直接SSH连接目标主机（不经过跳板机）

### 2. Fixture强制约束

- 实现测试步骤或前置条件的自动化脚本前，**必须**阅读 `sugon_web/case_specs/fixtures_index.md`
- **禁止**针对已有的fixture进行重复封装

### 3. 可复用Fixture参考

- `vpc` fixture：创建VPC
- `vm` fixture：创建虚机（支持count=4参数批量创建4台虚机，自动绑定MFIP）
- `slb` fixture：创建负载均衡实例（支持version="V2"参数）
- `ssh_vm` fixture：SSH连接虚机
- `ssh_host` fixture：SSH连接测试环境物理机

### 4. 后台命令执行规范

- 所有需要后台长期运行的命令（如启动web server），**必须**使用 `nohup` 并在末尾添加 `&`
- 示例：`nohup python3 -m http.server 8080 > /dev/null 2>&1 &`

## 清理数据

### ⚠️ 清理顺序强制要求

1. 从监听器资源池中将成员（虚拟机）移除
2. 删除监听器
3. 删除负载均衡实例
4. 删除虚拟机
5. 删除vpc

### 清理注意事项

- 清理顺序不可颠倒
- 虚机和VPC的清理由fixture的teardown机制自动完成
- 需确保在此之前已完成lb、slb相关资源的清理
