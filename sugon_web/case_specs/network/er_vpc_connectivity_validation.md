# 测试用例：企业路由器-HA-连接VPC-生效性验证

## 基本信息

- 用例编号：412950
- 所属产品：曙光云Stack
- 一级模块：网络
- 二级模块：企业路由器

## 适配范围

### 存储适配

- 该用例不支持的存储：无

### 架构/节点限制

- 架构限制：无
- 节点要求：无

## 前置条件

1. 已预置虚拟私有云 `er1_vpc1`，网段 `173.3.3.0/24`，并在该VPC下预置一台虚机 `vm1`
2. 已预置虚拟私有云 `er1_vpc2`，网段 `174.4.4.0/24`，并在该VPC下预置一台虚机 `vm2`
3. 已预置HA类型企业路由器 `er-ha-autotest`

## 测试步骤

### 场景1：ER打通同租户两个VPC功能验证（用例412950）

#### 步骤1：进入企业路由器列表页

- 操作：登录云平台后，依次点击：资源中心 -> 网络 -> 企业路由器
- 预期：可以正常打开企业路由器列表页

#### 步骤2：进入HA企业路由器详情页

- 操作：在ER列表页，点击前置条件中预置的HA实例 `er-ha-autotest` 名称，进入详情页
- 预期：详情页可以正常打开

#### 步骤3：切换到连接tab

- 操作：在详情页中，点击"连接"tab
- 预期：可以正常打开连接tab，连接列表可以正常显示

#### 步骤4：添加VPC1连接

- 操作：点击"添加连接"按钮，按如下内容输入：
  - 名称：`vpc1`（按常规输入）
  - 连接类型：默认值为"虚拟私有云"，保持不变
  - 虚拟私有云：选择前置条件中预置的 `er1_vpc1`
  - 子网：选择该VPC下的子网
  - 其它字段保持默认值，点击确定
- 预期：
  - 可以正常打开连接新建弹窗
  - 可以正常输入名称
  - 可以正常选择VPC和子网
  - 可以正常提交，添加连接成功

#### 步骤5：添加VPC2连接

- 操作：点击"添加连接"按钮，按如下内容输入：
  - 名称：`vpc2`（按常规输入）
  - 连接类型：默认值为"虚拟私有云"，保持不变
  - 虚拟私有云：选择前置条件中预置的 `er1_vpc2`
  - 子网：选择该VPC下的子网
  - 其它字段保持默认值，点击确定
- 预期：
  - 可以正常打开连接新建弹窗
  - 可以正常输入名称
  - 可以正常选择VPC和子网
  - 可以正常提交，添加连接成功

#### 步骤6：在VPC1路由表中添加自定义路由

- 操作：进入VPC模块，在VPC列表页点击 `er1_vpc1` 进入详情页，切换到"路由表"tab，点击添加自定义路由按钮，按如下内容输入：
  - 版本：ipv4
  - 目的地址：`174.4.4.0/24`（er1_vpc2的网段）
  - 下一跳类型：企业路由器
  - 下一跳：选择前置条件中预置的 `er-ha-autotest`
  - 其它字段保持默认值，点击确定
- 预期：
  - 可以正常打开添加自定义路由弹窗
  - 可以正常输入目的地址
  - 可以正常选择下一跳类型和下一跳
  - 可以正常提交，自定义路由添加成功
  - 在自定义路由列表中，可以根据目的地址 `174.4.4.0/24` 断言新添加的路由规则是否存在

#### 步骤7：在VPC2路由表中添加自定义路由

- 操作：返回VPC列表页，点击 `er1_vpc2` 进入详情页，切换到"路由表"tab，点击添加自定义路由按钮，按如下内容输入：
  - 版本：ipv4
  - 目的地址：`173.3.3.0/24`（er1_vpc1的网段）
  - 下一跳类型：企业路由器
  - 下一跳：选择前置条件中预置的 `er-ha-autotest`
  - 其它字段保持默认值，点击确定
- 预期：
  - 可以正常打开添加自定义路由弹窗
  - 可以正常输入目的地址
  - 可以正常选择下一跳类型和下一跳
  - 可以正常提交，自定义路由添加成功
  - 在自定义路由列表中，可以根据目的地址 `173.3.3.0/24` 断言新添加的路由规则是否存在

#### 步骤8：验证vm1到vm2的连通性

- 操作：通过 `ssh_vm` fixture 连接虚机 `vm1`（使用 `ssh_vm.connect(vm1_mfip)` 建立SSH连接），执行如下命令：
  ```bash
  ping -c 4 <vm2_ip>
  ```
  其中 `<vm2_ip>` 为虚机 `vm2` 的IP地址
- 预期：
  - 可以正常SSH连接到vm1
  - ping命令执行成功，ping的明细需要打印出来并输出到日志中
  - ping 4次全通，断言ping结果中 packet loss 为 0%

#### 步骤9：验证vm2到vm1的连通性

- 操作：通过 `ssh_vm` fixture 连接虚机 `vm2`（使用 `ssh_vm.connect(vm2_mfip)` 建立SSH连接），执行如下命令：
  ```bash
  ping -c 4 <vm1_ip>
  ```
  其中 `<vm1_ip>` 为虚机 `vm1` 的IP地址
- 预期：
  - 可以正常SSH连接到vm2
  - ping命令执行成功，ping的明细需要打印出来并输出到日志中
  - ping 4次全通，断言ping结果中 packet loss 为 0%

## 清理数据

### 清理顺序强制要求

测试数据清理流程**必须**按照如下顺序执行：

1. 删除两个VPC下的自定义路由规则
2. 删除ER实例下的所有连接
3. 删除企业路由器实例
4. 删除弹性云服务器vm1和vm2
5. 删除虚拟私有云er1_vpc1和er1_vpc2

### 清理注意事项

- 清理顺序不可颠倒，必须严格按照上述顺序依次执行
- 如果在清理过程中某一步骤失败，需先解决该步骤的问题后再继续后续清理
- 每个清理步骤完成后应验证清理成功，再执行下一个清理步骤
- 测试数据标记为"不可复用"，测试完成后需要彻底清理所有资源

## 实现注意事项

### 1. SSH操作强制约束

- 若测试步骤或前置条件中需要SSH到服务器后台或虚拟机后台执行命令，**必须**调用 `sugon_web/common/ssh.py` 中封装好的公共方法
- 禁止在测试代码中直接使用 `paramiko`、`subprocess` 等方式建立SSH连接
- 推荐使用fixture：
  - `ssh_vm` fixture：通过跳板机连接虚机的SSH会话
  - `ssh_host` fixture：直接SSH连接目标主机（不经过跳板机）

### 2. Fixture强制约束

- 实现测试步骤或前置条件的自动化脚本前，**必须**阅读 `sugon_web/case_specs/fixtures_index.md`
- 查阅fixture强制约束和速查表，确认框架中是否已有可复用的fixture
- **禁止**针对已有的fixture进行重复封装

### 3. 可复用Fixture参考

根据 `fixtures_index.md`，本用例可能涉及的fixture：

- `vpc` fixture：创建虚拟私有云（支持 `count` 参数批量创建）
- `vm` fixture：创建虚机（支持 `count` 参数批量创建，若引用vpc fixture则自动复用其网络和子网）
- `er_page` fixture：企业路由器页面对象（已定义于 `sugon_web/testcase/network/conftest.py`）
- `vpc_page` fixture：虚拟私有云页面对象
- `ecs_page` fixture：弹性云服务器页面对象（用于获取虚机IP等信息）
- `ssh_vm` fixture：通过跳板机连接虚机的SSH会话（用于执行ping命令）
- 企业路由器创建：可通过 `er_page.er_create()` 方法在测试前置步骤中创建

### 4. 后台命令执行规范

- ping命令执行后会立即返回结果，不需要使用 `nohup` 后台执行
- ping命令示例：`ping -c 4 <目标IP>`

### 5. VPC路由表操作说明

- 添加自定义路由需要在VPC详情页的"路由表"tab中操作
- 需要断言路由规则是否添加成功，可通过目的地址在路由列表中定位并验证
- 清理时需要先删除自定义路由规则，再删除VPC

### 6. 连通性验证说明

- vm1和vm2分别位于不同的VPC中，默认情况下无法互通
- 通过ER连接两个VPC并配置路由后，两个VPC下的虚机应当可以互通
- ping验证需要双向测试（vm1→vm2 和 vm2→vm1）
- ping 4次全通才算验证通过，需要断言 packet loss 为 0%
