# 基于前端工程 + AI 提示词的自动化脚本开发模式落地方案

## 1. 背景与目标

当前自动化工程已经具备以下基础条件：

- 自动化框架已统一为 Playwright + Pytest + POM
- 工程内已沉淀公共页面能力、fixture、测试数据加载、Allure 步骤日志和通用断言
- 已引入前端参考工程，可用于辅助理解页面结构、表单字段、列表列名和业务交互
- 已开始沉淀 AI 生成脚本与失败分析所需的结构化提示词和模板资产

当前团队推广自动化面临的核心问题不是“框架能力不足”，而是：

- 业务测试人员熟悉业务流程，但不熟悉测试代码组织方式
- 自动化脚本开发依赖少数熟悉框架的同学，产能受限
- 新人容易跳过已有 fixture、页面对象和断言能力，重复造轮子
- 同模块脚本风格不统一，后续维护成本高

本方案的目标是建立一套可复制、可培训、可平台化的“前端参考工程 + 结构化用例描述 + AI 生成脚本 + 自动校验”开发模式，使不懂测试代码的业务测试人员也能够顺利参与自动化脚本生产。

---

## 2. 总体思路

### 2.1 核心原则

将自动化脚本开发拆成三层：

1. 业务输入层
   由业务测试人员负责，输出结构化测试用例说明，不直接编写 Python 脚本。
2. AI 编排层
   由固定提示词约束 AI 的分析与生成路径，保证其先读已有用例、页面对象、fixture，再输出最小变更。
3. 框架承载层
   由自动化骨干维护 Playwright + Pytest + POM 工程公共能力，承接 AI 生成结果。

### 2.2 模式本质

这套模式不是“让业务测试学会写自动化代码”，而是“让业务测试学会描述清楚测试意图”，剩下的代码映射、能力复用和风格对齐交给 AI 与现有框架共同完成。

---

## 3. 适用对象与角色分工

### 3.1 业务测试人员

职责：

- 理解业务需求、页面流程和测试点
- 按模板填写结构化用例描述
- 补充前端参考路径、页面截图、预期结果和适配范围
- 验证生成结果是否符合业务预期

不要求：

- 不要求掌握 Pytest
- 不要求理解 POM 设计模式
- 不要求手写页面对象和 fixture

### 3.2 自动化骨干

职责：

- 维护自动化框架公共能力
- 维护提示词、模板和 case specs 目录规范
- 审核 AI 生成代码是否符合项目风格
- 补强 AI 无法自动抽象的公共能力

### 3.3 模块 Owner / 资深测试

职责：

- 确认业务规则是否描述完整
- 确认前端参考工程路径与实际页面对应关系
- 评估高风险场景的前置条件和环境要求

## 5. 标准开发流程

建议统一成如下流程：

### 步骤 1：业务测试编写结构化用例

业务测试人员基于模板填写一个 Markdown 用例说明，至少包含：

- 用例名称
- 模块归属
- 用例类型
- 页面入口
- 适配范围
- 测试步骤
- 每步预期结果
- 前置资源要求
- 清理策略

### 步骤 2：补充前端参考信息

在 case spec 中补充以下材料之一：

- 前端工程中的页面路径
- 页面组件文件路径
- 交互截图
- 产品原型或需求链接

这样 AI 在生成脚本时可以从前端代码中读取真实字段名、弹窗标题、列表列名和交互流程，而不是靠猜。

### 步骤 3：AI 按提示词生成脚本

AI 必须严格按照提示词执行以下顺序：

1. 阅读同模块已有用例
2. 阅读相关页面对象、fixture、测试数据
3. 先复用已有公共能力
4. 仅在缺失时补最小页面对象方法
5. 生成或修改测试脚本
6. 做语法检查
7. 做最小范围 pytest 收集或执行验证

### 步骤 4：自动化骨干 Review

Review 重点不是业务逻辑是否正确，而是以下规范是否满足：

- 是否复用了现有 `search / btn_reset / assert_list_contain / assert_deleted`
- 是否新增了不必要页面对象方法
- 是否存在重复前置和清理逻辑未抽取
- 是否遵循同模块现有命名风格
- 是否完成最小范围校验

### 步骤 5：业务回归确认

业务测试人员确认：

- 生成用例是否覆盖目标测试点
- 断言是否与业务预期一致
- 前置与清理是否符合业务场景

### 步骤 6：沉淀可复用能力

当某模块出现以下情况时，应反向沉淀到框架：

- 同类页面对象方法重复出现 3 次以上
- 同类 fixture 前置 / 清理逻辑重复出现 3 次以上
- 同类等待、搜索、列表校验模式频繁复现

## 6. 推荐目录与资产组织方式

### 6.1 输入资产目录

建议统一放在 `sugon_web/case_specs/` 下，按模块拆分：

```text
case_specs/
  prompts/
  templates/
  network/
  compute/
  storage/
  database/
  backup/
```

### 6.2 每条用例建议结构

每条业务用例建议形成以下文件组合：

- `xxx_case.md`
  业务测试填写的结构化用例描述
- `xxx_refs.md`
  可选，补充前端页面路径、截图、原型、说明
- `generated_xxx.py`
  AI 生成并由自动化骨干审核后的正式脚本

### 6.3 输入输出边界

业务测试只维护：

- case spec
- 参考信息
- 业务验收结论

自动化骨干维护：

- 页面对象
- fixture
- 测试脚本
- 提示词
- 模板

## 7. 让不懂代码的业务测试顺利上手的关键设计

### 7.1 把“写代码”改成“填模板”

业务测试不直接提“帮我写个 Pytest 用例”，而是统一填写以下问题：

- 这个功能在哪个页面
- 要执行什么操作
- 操作成功后页面应该看到什么
- 需要什么前置资源
- 哪些字段必须校验
- 如何清理

这相当于把“代码输入”改造成“结构化业务输入”。

### 7.2 给出模块级黄金样例

每个模块至少沉淀 3 到 5 个完整样例：

- 页面功能基础类
- 搜索重置类
- 修改类
- 批量删除类
- 典型场景类

业务测试只需要照着样例改字段和步骤，不需要从空白开始思考。

### 7.3 统一术语表

需要为业务测试提供统一术语映射，例如：

- 页面动作词：创建 / 删除 / 修改 / 搜索 / 重置 / 绑定 / 解绑
- 断言词：列表包含 / 状态正确 / 字段回读 / 资源已删除
- 数据词：前置资源 / 清理资源 / 依赖资源 / 共享资源

统一术语后，AI 的理解稳定性会显著提高。

### 7.4 降低失败成本

为业务测试准备固定的失败分析入口：

- 输入失败日志
- 输入截图
- 输入相关代码
- 使用失败分析提示词自动输出根因归类与修复建议

这样业务测试不需要直接读复杂堆栈，也能理解“是环境问题、用例问题还是产品缺陷”。

## 8. 平台化实现建议

## 8.1 最小落地形态

第一阶段不一定要开发复杂平台，可以先提供一个统一入口脚本，例如：

- 输入：`case_specs/network/peer_connect_basic.md`
- 输入：前端参考路径
- 输出：目标 `testcase` 文件和必要的页面对象补丁建议

### 8.2 推荐能力清单

后续可逐步平台化以下能力：

1. 用例模板生成器
   自动创建标准 Markdown 用例模板
2. 前端参考信息挂载
   支持关联前端页面路径、截图、原型链接
3. AI 代码生成入口
   固定读取模板、prompt、参考工程、已有脚本
4. 自动校验
   自动执行 `py_compile`、`pytest --collect-only`
5. 自动生成 Review 清单
   输出本次是否新增页面对象、是否复用公共能力、是否存在重复逻辑
6. 失败分析入口
   基于失败日志和截图自动输出根因报告

### 8.3 不建议一开始做的事情

- 不建议直接开放自由自然语言输入
- 不建议跳过已有代码阅读步骤
- 不建议一开始就让 AI 直接批量改整个模块
- 不建议让业务测试直接修改页面对象和 fixture

## 9. 团队推广实施路径

### 阶段一：试点阶段

目标：

- 在 1 个模块内验证模式可用性
- 建立一套完整样例链路

建议选择：

- 网络模块

产出：

- 3 到 5 条高质量 case spec
- 3 到 5 条 AI 生成并审核通过的正式脚本
- 1 份“业务测试填写示例”
- 1 份“常见失败案例与修正方式”

### 阶段二：标准化阶段

目标：

- 固化模板、提示词、目录规范和审核清单

产出：

- 各模块统一 case spec 模板
- 统一 AI 生成入口
- 统一 review checklist
- 模块级黄金样例库

### 阶段三：团队推广阶段

目标：

- 让业务测试在日常需求迭代中直接参与自动化输入

方式：

- 新需求评审后，业务测试先补 case spec
- 自动化骨干再进行 AI 生成和审核
- 脚本通过后进入冒烟或回归集合

### 阶段四：平台化阶段

目标：

- 从“人工协作流程”演进到“可自助使用的平台流程”

方向：

- Web 表单化录入 case spec
- 自动关联模块模板
- 自动读取前端参考路径
- 自动触发代码生成与轻量校验

---

## 10. 审核机制建议

建议把审核拆成两类：

### 10.1 业务审核

关注：

- 业务流程是否覆盖
- 断言是否符合预期
- 前置与清理是否合理

### 10.2 自动化审核

关注：

- 是否复用公共能力
- 是否新增冗余页面对象
- 是否遵循同模块风格
- 是否满足提示词规范
- 是否通过最小范围校验

这样可以避免业务测试被代码细节阻塞，也避免自动化骨干承担所有业务验收责任。

---

## 11. 成功衡量指标

建议用以下指标衡量推广效果：

- 业务测试独立提交 case spec 的人数占比
- AI 生成脚本一次审核通过率
- 单条基础功能脚本平均开发时长
- 新增脚本中复用已有页面对象 / fixture 的比例
- 新增页面对象方法数量占比
- 失败脚本中“用例问题”占比是否下降
- 模块内脚本风格一致性是否提高

## 12. 主要风险与应对

### 风险 1：业务输入不结构化

表现：

- 用例描述缺少前置条件
- 预期结果太抽象
- 页面路径不明确

应对：

- 强制模板化填写
- 设置必填项
- 提供样例与填写说明

### 风险 2：AI 生成结果偏离项目风格

表现：

- 重复造 helper
- 不复用 fixture
- 新写一套断言方式

应对：

- 强制使用固定 prompt
- 强制先读同模块代码
- 保留自动化骨干 review 机制

### 风险 3：前端参考工程与现网页面不一致

表现：

- 字段名、弹窗标题、交互细节有差异

应对：

- 明确前端参考工程只作为“结构参考”
- 真正落地时仍需结合运行页面做最小验证
- 对高风险页面增加截图辅助材料

### 风险 4：团队误以为 AI 可以完全替代自动化设计

表现：

- 忽视框架治理
- 忽视公共能力沉淀
- 页面对象持续碎片化

应对：

- 明确 AI 负责加速，不负责替代框架治理
- 页面对象、fixture、公共能力仍由自动化骨干统一治理

---

## 13. 推荐的团队工作机制

建议建立以下日常机制：

1. 每个新需求先产出 case spec，而不是直接提“写自动化”
2. 每周沉淀模块黄金样例
3. 每两周回顾一次 AI 生成质量
4. 每月整理一次重复页面对象与 fixture 抽象机会
5. 对失败样本建立“根因 -> 修复方式 -> 提示词优化建议”闭环

## 15. 总结

最适合推广给测试团队的落地模式，不是让业务测试去学习自动化代码，而是：

- 用前端参考工程帮助理解真实页面
- 用结构化模板承接业务测试输入
- 用固定提示词约束 AI 生成路径
- 用现有 Playwright + Pytest + POM 框架承接落地
- 用自动化骨干做框架治理与质量兜底

这套模式一旦跑顺，业务测试提供的是“高质量业务输入”，AI 负责“代码翻译与复用”，自动化骨干负责“规范守门与能力沉淀”。这样才能真正把自动化能力从少数写代码的人手里，扩展到整个测试团队。
