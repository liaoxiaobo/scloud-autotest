# 【阶段一 · 子智能体】启动强制动作与回报格式

> 本阶段"执行什么、遵守什么规范"全部以下方正文为准，一字不漏。

**启动后强制动作（顺序执行，不得跳过）：**
1. 先 `Read` 编排层传入的运行报告文件（若为本次运行首个阶段、glob 无结果，则由本阶段按下方「完成时立即输出」创建并写文件头）。
2. **在本全新上下文中通读下方内联的本阶段全文规范**，并按其要求读取关联文件（`CLAUDE.md`、`pytest.ini`、`sugon_web/refrence/module_index.yaml` 等）。
3. 严格按下方正文规范执行本阶段任务。
4. 按正文「阶段一完成时立即输出」的确切格式：对话框输出 + 双写运行报告，并运行
   `python .claude/skills/test-self-heal/scripts/report_check.py <运行报告 md 路径> --phase 1`，退出码非 0 则按提示补写后重跑。
5. 向编排层只返回**一句话状态**（明细已写运行报告），不返回长篇明细。

**全程通用硬约束（与全工作流一致，必须遵守）：**
- **全程禁 git + 防误删**：执行期间严禁运行任何 `git` 命令（checkout/reset/restore/clean/pull/commit/push/stash 等；只读 `git diff/log` 查看 `refrence/` 版本差异属唯一豁免），严禁从 git 还原、严禁提交、严禁误删/覆盖已有脚本或任何文件；万一误删/误覆盖立即停止并醒目提示人工从版本库/备份恢复、不自行补救。
- **读文件用 `Read`、搜内容用 `Grep`**；**严禁用 `python -c "...print(...)"`/`type`/`cat` 打印文件内容**（Windows GBK 会 `UnicodeEncodeError` 崩溃空转）。命令一律在仓库根目录用 bash 直接跑、**禁加 `cd`/`cd /d` 前缀**；同一坏命令连续 2 次报错即停下诊断、不原样重发。
- **完成时间精确到秒**：写入运行报告的 `## 阶段一…完成时间：` 必须先 `date "+%Y-%m-%d %H:%M:%S"` 取真实系统时间原样填入（年月日+时:分:秒俱全），`report_check.py` 会机械校验。
- **防重复读空转（强制·实测踩过坑：曾在几个小文件上反复重读、空转一小时）**：同一文件**读过一次且内容未变，就不要再重复 `Read`**——读完立即据其产出结论/落盘，不反复回读；**连续 2 次工具调用没有任何新的落盘产出（没写运行报告、没定位到新证据）就停下来自检是否跑偏**，切勿在几个小文件间空转。

# 阶段一：范围圈定 + 执行 + 失败采集

> 自愈的输入是"已有脚本因产品发版而失效"。本阶段**不写新脚本、不改脚本、不修复、不下根因结论**——只做三件事：① 圈定自愈范围并确认前端版本基线与证据采集基建就绪；② 批量执行范围内用例；③ 为每个失败用例采集完整证据、生成结构化失败清单，交阶段二分诊。

## 第一部分：范围圈定与基线对齐

**1. 确定自愈范围（入口）**。编排层会传入下列之一，按其执行；未明确时**默认按模块圈定**（避免一次性全量导致循环过长、墙钟过大）：
- 全量回归：`sugon_web/testcase/`
- 指定模块 / 文件 / `-k` 表达式 / 单个用例
- "只跑上一次失败清单"里的用例

**2. 前端版本基线对齐**。自愈以"被测产品**最新前端工程代码**"为真相，必须确认 `sugon_web/refrence/` 已是当前版本：用 `ls -td sugon_web/refrence/*/` 取最新版本目录；读 `sugon_web/refrence/module_index.yaml`，确认**本次范围内每个模块都能按 4 级匹配策略映射到前端工程目录**。
- **异常处理**：某模块无法定位前端工程目录（4 级匹配失败/目录不存在）→ 在对话框与运行报告**醒目提示**"无法找到该模块对应前端工程目录，请人工直接告知目录"，**暂停该模块、其余可定位模块继续**，不擅自猜目录。

**3. 失败证据采集基建确认**。失败现场的截图与 DOM 摘要由**项目框架自带的失败钩子**（`sugon_web/utils/hooks.py`，路线 A，无需手动开关）自动落盘到 `screenshots/<模块>/<测试名>/`、`dom_snapshots/<模块>/<测试名>/`。本阶段启动时确认该基建在位即可，**不自行另起 DOM dump 开关**。

## 第二部分：批量执行用例

- **每次 pytest 必带 `--log-file`**：通过 `Bash` 定义 `LOG_FILE`（落在 `logs/<模块>/<测试名>/` 下、与截图/DOM 同构），传 `--log-file=$LOG_FILE --log-file-level=DEBUG`；**严禁执行不带 `--log-file` 的 pytest**。
- **测试环境一律以 `sugon_web/config/base.yaml` 为准、不传 `--host`**（让框架按 base.yaml 加载当前环境）；**严禁照搬 Jenkinsfile 里写死的 HOST 默认值（如 172.22.1.190）**。
- 遵守 `pytest.ini`（默认 `-m 'not slow'`，需要 slow 用例显式加 `-m "slow"`）。
- 本阶段执行**不经 run_guard**（run_guard 是阶段三修复循环的执行守卫）；本阶段只是一次性跑出失败清单。
- 首轮全量执行范围内用例，收集所有 FAILED / ERROR。

## 第三部分：失败证据采集与失败清单

为**每个**失败用例生成一条**结构化证据条目**（写入运行报告「失败清单」表）：
- 用例 nodeid（如 `test_xxx.py::TestX::test_y`）
- 错误类型（TimeoutError / AssertionError / 定位错误 / SSH 错误 / 其他）——**这是"技术报错表象"分类（按异常类型/报错形态归类），【不是】阶段二的 4 分类根因（环境/用例/产品缺陷/前端变更）。本阶段【严禁】在此下根因结论：例如填"定位错误"只表示"报了元素定位失败"这个现象，至于它到底是不是前端变更导致、还是脚本等待时机问题、还是环境问题，一律留给阶段二判定，本阶段不猜、不写根因。**
- **最早异常源**（堆栈里**最深的一帧"用户代码" `file:line`**——"用户代码"指 `sugon_web/pages/`、`sugon_web/testcase/`、`sugon_web/assertions/`、`sugon_web/common/`、`conftest.py` 这些**项目自有代码**帧，**不是** Playwright/pytest 等第三方库的内部帧；在这些用户代码帧里取**最深（最靠近实际出错点）**的那个，而不是只看日志最后一行的报错文本。本阶段填到"能定位到哪个文件哪行"即可，属**初步定位**，阶段二/三会据完整堆栈再深挖，不必纠结绝对精确）
- 失败步骤（在第几步、做什么操作时失败）
- 日志路径 `logs/<模块>/<测试名>/...`、截图路径 `screenshots/<模块>/<测试名>/...`、**DOM 快照路径** `dom_snapshots/<模块>/<测试名>/...`（**若该次失败未生成 DOM 快照——如失败发生在页面打开前、`page` 尚不可用时——此列据实填 `无（失败发生在页面渲染前）`，严禁填一个不存在的路径去误导阶段三**）
- 失败时 URL / 服务

**批量主因聚类（失败用例 ≥3 时强制）**：把失败按"同 fixture / 同 Page Object / 同前置资源 / 同 SSH 命令"聚类，给出疑似共因，供阶段二优先按共因分诊（一次定位多个、减少重复）。

**异常处理**：
- 某用例失败不稳定（首次失败、补跑通过）→ 标注"疑似环境波动"，交阶段二复跑确认，**本阶段不下结论**。
- 本阶段**只采集、不修复、不做 4 分类根因结论**（根因分诊是阶段二的事）。
