# 阶段二：4 分类根因分诊 + 前端对齐定位

> 对阶段一失败清单里**每个**失败用例判定根因为四类之一，圈出"可自愈集合"，并把产品缺陷准确识别、取证、隔离、醒目上报。

## 一、铁律与证据优先级

- **★ 无根因不修（Iron Law）**：未完成根因分诊不得提出修复、不得进阶段三。判"用例问题/前端变更"前**必须先排除"环境/产品缺陷"并给排除依据**。
- **诊断起手必读失败案例库**：先比对 `failure_case_library.md`，**命中已收录模式即直接套用其根因方向**，减少从零试错。
- **证据优先级**：失败现场截图 / `dom_snapshots` 真实渲染态 > 日志堆栈 > 前端源码 > 推断。**回溯最早异常源**（最深用户代码帧），而非只看最后报错处；批量失败借鉴二分思路定位上游污染 fixture。
- **★ 先读阶段一「批量主因聚类」区块再逐个分诊（务必读准，别漏读、别重复劳动）**：阶段一失败清单 ≥3 时会附一份「批量主因聚类」（按同 fixture / 同 Page Object / 同前置资源 / 同 SSH 命令给出的疑似共因分组）。分诊前先读这份聚类：**同一聚类组内的用例大概率共享同一根因**，应优先对组内 1~2 个代表性用例做完整证据分析定论，再把该结论套用到组内其余用例（逐一核对关键证据是否吻合，吻合则直接沿用分类，不必每个都从零重新分析）——这正是聚类存在的意义（一次定位多个、减少重复分析），若对每个用例都独立从零分诊，等于浪费了阶段一的聚类产出。
- 信息不足且前端代码也无法佐证 → 标"待人工确认"，**不强行归类、不进自愈**。
- 失败不稳定的用例**复跑确认**（重跑 3 次，≥2 次通过判环境波动；复跑不计任何修复轮次）。

## 二、根因 4 分类判据

> 仅"用例问题"+"前端变更"进入阶段三自愈；"环境问题/产品缺陷"记录后**不改脚本**。

1. **前端变更（UI drift，发版后最高频，进自愈）**：报错为定位失败 / 文案不匹配 / 控件类型变化 / 字段名变化 / 交互流程步骤增减；且 `Grep` 被测模块**最新前端工程代码**证实"Page Object 里固化的旧文案/旧定位/旧流程"与"最新前端"**不一致** → 判前端变更，交阶段三按"前端对齐三手段"修复。
2. **用例问题**：等待时机不当 / 数据冲突 / 清理顺序错 / 断言逻辑错等**脚本自身缺陷**，与前端真相无关 → 交阶段三修复。
3. **产品缺陷（不可自愈·硬隔离·必须人工确认）**：见第四节。
4. **环境问题**：资源耗尽 / 网络中断 / 服务未就绪等。**判环境前必须在原始日志 `grep` 到确定性证据**（如错误码 `-12400078`、`ERR_CONNECTION_CLOSED`、`aria-disabled` 等），无确定证据不归环境 → 记录跳过、建议优化环境后重跑，不改脚本。

## 三、前端对齐定位（为前端变更类用例准备，给阶段三用）

对判为"前端变更"的用例，做**初步**前端对齐定位（最终定论由阶段三运行时侦察裁决），按序尝试、命中即记：
- **静态对齐**：`Grep` 旧文案/旧定位在前端工程目录的现状，找新文案/新结构候选；
- **前端 diff 对齐**：`refrence/` 若是 git 仓库，用**只读** `git diff`/`git log`（属禁 git 的唯一豁免）锁定版本变更点、收敛范围；
- 把"旧值 → 新值候选 + 证据来源（`文件:行号` 或 recon 截图）"写进该用例分诊条目的「前端对齐线索」列，供阶段三对齐修复。**为让阶段三少走弯路（阶段三启动时会把该列作为「阶段二分诊结论/前端对齐线索」直接采用、避免重复侦察），凡本阶段已确认到的信息都要一并写进该列、写具体**：目标元素的**真实定位/文案**、**所在容器**（弹窗 dialog / 内联表单 / 抽屉 / 表格行 / 卡片）、**向导步数或下拉选项**、**已知交互坑**（如"选值后表单项 DOM 会重建、不能用占位符做容器定位"）。**只写"已确认到的"、写清楚来源**；本阶段未能确认的部分留白即可（写"待阶段三运行时侦察确认"），由阶段三 `recon_page.py`/domsnap 补全，不必强行填满、不许凭空猜填。

## 四、产品缺陷：识别、取证、隔离、醒目上报（必须准确实现）

> 发版后失败既可能是前端变更（可自愈），也可能是**真实产品缺陷（不可自愈）**。两者必须分开、互不掩盖。

- **判定**：当"前端对齐也解释不了"，且**后端 `scli`/SSH 取证或界面实况表明产品行为本身异常**（接口报错 / 数据不持久 / 状态不收敛 / 功能实际未生效）→ 判**产品缺陷**。判定**必须附复现要点 + 后端取证证据**。
- **防误判**：判产品缺陷前先**导航回详情/编辑页核对需求显式配置项是否真配上 + 后端取证**，排除"脚本/页面对象漏配""时序未就绪"等被误当产品缺陷的情况（继承失败案例库经验）。
- **隔离**：判为产品缺陷的用例**立即移出可自愈集合**——不进阶段三、不消耗任何 run_guard 修复轮次、不参与后续自愈/稳定性。
- **醒目上报**：写入运行报告**「疑似产品缺陷清单（需人工确认）」区块**（每条含：用例 nodeid、失败现象、为何判产品缺陷、复现要点、后端取证证据、建议人工核实并提缺陷单）。
- **最高红线·严禁掩盖**：严禁为让用例"变绿"而把产品缺陷当脚本问题反复改、或放宽/删除/跳过断言来掩盖——把真缺陷藏成"假绿"比不修更危险。

## 五、循环规则

逐个失败用例走"证据收集 → 假设 → 分类 → 排除其余类"；信息不足必须先 `Grep refrence/` 取证再下结论。**严禁停下来询问用户**，自主完成分诊。全部用例分诊完、可自愈集合圈定、产品缺陷已取证隔离 → 进阶段三（若可自愈集合为空则据情况跳过阶段三、直接收尾或进阶段五守卫判定）。
