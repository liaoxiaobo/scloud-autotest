# 阶段四：回归验证与自愈循环

---

## 一、日志分析与核查要求

> **★ 回归验证的"执行来源"（务必读准，避免冗余重跑 / 也避免无日志空核查）**：本阶段的"回归"**默认不需要你再启动一次 pytest**——正常流程里**阶段三结尾已做过一次"Jenkins 对齐全量执行"**并产出了最新全量日志，本阶段**直接分析那次最新全量日志**即可（对昂贵用例再重复跑一遍纯属浪费）。**仅当**下列情况才需要你**先自己跑一次完整用例（整文件、带 `--log-file`）再分析**：① 从 `regress` 入口直接进入、运行报告里找不到阶段三之后的最新全量执行日志；② 现有最新全量日志已失效/被截断、无法据以核查。无论哪种来源，回归判定都必须基于**一次完整用例执行（整文件，非单步 / 非单 `-k` 方法）**的日志。

**分析范围（2026-06-29 优化·只分析"最新关键日志"，不再全量扫历史，省时省 token）：** 被维护用例对应的需求 MD（项目既有文档、创建该脚本时已产出，**非本次阶段一产出**；若项目中无对应需求 MD，则以被维护脚本自身既有步骤 + `refrence/` 最新前端代码为预期基准）定义了本次自动化测试的预期行为。`logs/<模块>/<测试名>/` 目录（项目根原生日志目录，与截图/DOM 摘要同构；`<模块>`=测试文件在 `sugon_web/testcase/` 下的子目录、`<测试名>`=测试 py 文件去 `.py`）下常累积大量**早期调试轮次**日志——它们的问题多已在阶段三修复、并被后续成功运行覆盖，**全量重复分析纯属耗时耗 token、零增量价值**（实测曾一次扫 62 个日志、耗十万级 token，毫无新发现）。故本阶段**只分析下列关键日志，其余早期调试日志一律跳过**：

1. **最新一次"全量整文件"执行日志**（= mtime 最新、且一次性跑了**全部** `def test_` 方法的那次；优先取阶段三终验 / Jenkins 对齐那次 PASSED 全量日志）——作为**需求覆盖度核查的基准**。
2. **本轮新出现的失败日志**（若该最新全量日志中有 FAILED/ERROR，或本轮仍有未通过用例）——用于定位问题、判是否回退。
3. 上述 ①② 被分析日志的 **teardown / cleanup 段**——按下方"强制扫描"逐一扫 WARNING/ERROR。

> **选取规则**：最新一次是 PASSED 全量 → 只需分析它 + 其 teardown；最新一次是失败/截断 → 同时纳入"它"与"最近一次成功的全量日志"。**严禁为了"全覆盖"而把几十个早期调试日志逐个分析**——它们不是最终态、问题已修复，分析它们既无结论价值又拖垮耗时与 token。

**核查内容：** 检查每个步骤的实际执行情况是否与该需求文档中定义的流程和预期结果一致。

**teardown 段强制扫描（不得遗漏）：** 对上述「分析范围」选定的每个日志（最新全量日志 + 本轮新失败日志），必须主动 `Grep` 其 teardown / cleanup / fixture finalizer 段落，列出该段所有 WARNING 与 ERROR——**严禁只核查测试步骤覆盖度而放过 teardown 告警**（注意：是扫"被分析的那几个关键日志"的 teardown，不是把目录下所有历史日志再翻一遍）。

**输出形式：** 请以表格形式输出检查结果，字段包括但不限于：步骤序号、需求文档要求、实际执行的关键日志、测试结论（是否满足测试需求）；并单列一项汇总各文件 teardown 段的 WARNING/ERROR。

**MD 保护：** 分析过程中严禁修改被维护用例对应的需求 MD 文档（项目既有、非本阶段产出），除非确认该 MD 本身有误。

## 二、问题分级与处理规则

**使用说明：** 将检查结果与需求 MD 文档逐项对比，判断脚本是否满足预期测试需求。

- **重要问题（须返回阶段三修复）**：核心测试步骤遗漏、关键断言缺失、测试流程与需求严重不符、**teardown 段存在 ERROR（如清理失败、SSH 断连、资源未回收）**。
- **非重要问题（可直接进入阶段五）**：日志格式不统一、Allure 步骤描述措辞差异、非关键字段值的小幅偏差、**teardown 段仅有 WARNING（须记录，随修复一并处理）**。

**判断优先级（重要问题优先）：** 若日志中同时存在重要问题和非重要问题，**一律按重要问题处理**——返回阶段三修复脚本，非重要问题随修复过程一并处理；仅在**无重要问题**时，方可直接进入阶段五。

**回退去向（回阶段三 or 回阶段二·连贯性）：** 需回退时**默认回阶段三继续修**（根因分类没问题、只是修复未到位）；但**若证据显示"根因分类本身可能判错了"**——例如同一处反复修仍失败、或后端 `scli`/SSH 取证开始显示疑似产品行为异常/疑似环境问题——则应**带新证据回阶段二重新分诊**（而不是让阶段三对着错误的根因继续死磕）。无论回阶段二还是阶段三，都由编排层按运行报告经 `loop_gate` 闸门放行；本阶段只需在下方「回归结果概览」的"判定去向"里写清是回阶段二还是回阶段三，并把"未过原因/新证据"落盘供下游读取。

**完成标志：** 日志分析完成，每个步骤与需求一致、teardown 段已扫描并分级，或已确认非重要问题并记录。
