# 阶段一：测试需求转换与校验

## 第一部分：测试需求转换（CSV → MD）

> 必须根据以下要求把测试需求的 CSV 文件转换为自动化测试需求的 MD 文件。执行转换前必须先使用 Read 工具依次读取以下关联文件，全部读完后再继续，不可跳过。

requirements_csv/目录下存放着本次编码任务的测试需求的csv文件，请你阅读这个测试需求的csv文件，把它转换成一个标准的、结构化的md文件，这个md文件用于AI生成UI自动化测试用例脚本的需求文档，通过该文档快速且准确地理解当前编写自动化测试脚本的需求，MD 输出样式模板请你务必根据 `sugon_web/case_specs/templates/base_case.md` 关联文件中的【实现注意事项】与【推荐填写示例】来写。同时你必须严格遵守以下注意事项与规范：

**注意事项**
1. `sugon_web/case_specs/templates/base_case.md` 关联文件只是一个初稿，可能信息不全，你可以根据实际情况适当增加内容，但只增加有必要的重要内容，无关紧要的内容不要增加，不要让该文档的篇幅太大或过于臃肿。
2. 你生成的 MD 文件命名须为简短英文，采用 `模块_功能描述.md` 或有意义的命名风格，使其能直观反映测试内容。
3. 你生成的 MD 文件，需要放到 `sugon_web/case_specs/` 目录下对应的业务模块目录中，如网络模块的则放在：`sugon_web/case_specs/network`
4. 你在转换的 md 文件中，需要新增注意事项：实现测试步骤或者前置条件的自动化脚本，必读参考 `sugon_web/case_specs/fixtures_index.md`，查阅 fixture 强制约束和速查表，确认框架中是否已有可复用的 fixture，不要针对已有的 fixture 进行重复封装。重复封装会增加维护成本并可能导致用法不一致。

**多场景处理规范**

若 CSV 中包含多条测试用例（多行），必须将所有用例合并输出到**单个** MD 文件中，确保一个 CSV 对应一个 MD。拆分会导致需求分散，难以统一管理和追溯。每行 CSV 数据（除标题行外）对应一个独立的自动化测试需求，阶段二必须为每行生成一个 `def test_` 方法，禁止合并或遗漏。

**★ 前置条件必须转成"自动化可执行的前置"（强制·最易翻车，直接决定编辑/删除/详情类用例能否跑通）**：CSV 里"前置条件：已预置 / 已创建好 XX（如 policy1）"是**人工测试语境**——**自动化环境不会有人工预置数据**。转写时**绝不能照抄成"环境已预置 XX"**（那会让阶段二假设它已存在、只去 `search` 而不创建，导致编辑/删除类用例无对象可操作、必然失败）。必须改写成**可执行前置**，二选一并在"前置条件"+"实现注意事项"里写明：
- **① 脚本自保证（self-provision）**：在 fixture/setup 里"先查、不存在则创建"（`exists()? else create`）该前置资源；
- **② 复用前序场景**：若 CSV 标注该数据"可复用=是"且依赖前一新建场景，则改写为"**复用前序场景 class-scoped 共享创建的资源**"，**严禁让前一场景用完即删**。
**反例（本次真实事故）**：把"已预置 policy1"原样写成环境前置、又让新建场景各自创建+删除 → 编辑场景既没有 policy1、也没有可复用数据 → 卡死。

1. **提取公共前置条件（强制）**：将各用例中重复的前置条件提取到统一的"前置条件"章节，只保留一份
   - 必须识别可复用资源：如 4 台虚机、SLB V2 实例等跨场景共享资源，在"前置条件"中声明
   - 必须标注共享标识：在资源描述中注明"本资源在多个场景中复用"
   - 不要在每个场景中重复声明相同的前置条件。重复声明会增加冗余且容易遗漏。
2. **场景化测试步骤**：在"测试步骤"章节中用二级标题按场景分组，格式参考 `sugon_web/case_specs/templates/base_case.md` 的【推荐填写示例】章节。
3. **场景依赖标注**：若某场景依赖其他场景执行，必须在前置条件或场景开头注明，例如：`> 依赖：场景1（用例436746）已执行完成`
4. **测试数据复用判定**：若 CSV 中包含"测试数据是否可复用"字段，标记为"是"则在 MD 中注明这些场景共享同一套测试数据，所有用例执行完成后统一清理；标记为"否"则各自独立创建和清理。**标记为"是"的可复用数据严禁在前一场景就删除**——应由 class-scoped 共享、待复用它的所有场景都执行完再统一清理（否则后续依赖它的场景无数据可用，正是上面"前置条件必须可执行"反例的成因）。

**执行测试命令的编写规范**
1. CSV 文件中若测试步骤写明了具体执行的命令，则需要把这些命令转换后写进 MD 文件中。因为要避免在自动化用例执行过程中出现长时间占用会话连接，所以在转换命令时必须修改成使用 nohup 后台执行命令。
2. CSV 文件中的同一组操作若需要执行多个执行命令才能完成的，则使用 `&&` 合并成同一行命令，如：`cd /root/test/ && echo "this is ecs1" >> index.html`
3. CSV 文件中有些命令在执行后，系统不会立刻返回执行结果，这种命令则必须增加轮询等待，直至命令输出符合预期的正确结果，设置最长等待时长为 60 秒，如：`nohup python3 -m http.server 8080 > /dev/null 2>&1 &` 这类命令则需要轮询等待。
4. CSV 文件中若有【打开虚拟机 vnc】、【打开虚拟机 vnc 控制台】、【打开虚拟机 vnc 窗口】等类似的操作虚拟机 VNC 的描述，则在 md 文件中必须改写为：通过 `ssh_vm` fixture 连接虚拟机后台，使用 `ssh_vm.connect(vm_mfip)` 建立 SSH 连接，再调用 `ssh_vm.run()` 执行命令。
5. CSV 文件中若有【ssh 连接虚拟机系统后台】、【ssh 连接虚拟机】、【连接虚拟机后台】等类似的描述，则在 md 文件中必须改写为：使用 `ssh_vm` fixture（`sugon_web/conftest.py`）提供的 SSH 实例，调用其 `connect()`、`run()`、`ping()` 等方法（定义于 `sugon_web/common/remote/ssh.py`）。
6. CSV 文件中若有【本地客户端 ssh 连接环境和访问】、【ssh 连接环境物理机后台时】、【连接节点后台】等类似的描述（如：本地客户端通过 fip 访问负载均衡，执行命令：`curl http://$lb_fip:8080/index.html`），则在 md 文件中必须改写为：使用 `ssh_host` fixture 用于直接连接测试环境的系统后台。

## 第二部分：需求文档校验

> 转换完测试需求的 MD 文件后，还不能直接使用，必须检查 MD 文件是否正确、表达是否清晰、是否存在错误或歧义。若有问题直接修改，直至无误。

**执行要点**

> **★ 校验优先级（先查、最严格查这几项——它们最决定下游阶段二能否写对、阶段三返工多少）**：① **前置条件可执行性**（CSV"已预置 XX"必须转成"脚本自建/复用"，不能照抄"环境已预置"）；② **完整性**（步骤/预期/边界无遗漏、可验证）；③ **多场景与数据复用**（公共前置提取、依赖标注、可复用=是的数据不在前一场景删）；④ **命令规范与 fixture 改写**（转写正确）。这几项查到位，阶段二写得对、阶段三返工最少；其余（内容精简/模板结构/文件名）为格式项，过一遍即可。

- **内容精简检查**：检查 MD 文件是否在 `sugon_web/case_specs/templates/base_case.md` 基础上只增加了有必要的重要内容，无关内容未增加，文档篇幅不过度臃肿
- **模板结构检查**：检查 MD 文件是否符合 `sugon_web/case_specs/templates/base_case.md` 的标准章节结构
  - 是否包含基本信息、适配范围、前置条件、测试步骤、实现注意事项、清理数据等必要章节
  - 适配范围中是否明确了存储适配和架构/节点限制
- **文件名与路径检查**：检查 MD 文件的命名和存放位置是否符合规范
  - 文件名是否为简短英文，是否采用 `模块_功能描述.md` 或有意义的命名风格
  - 是否存放在对应业务模块的子目录下（如网络模块放 `case_specs/network/`）
- **完整性检查**：逐段检查 MD 文件是否完整、准确地表达了 CSV 中的测试意图
  - 测试步骤是否完整无遗漏，预期结果是否明确可验证
  - 边界条件是否在 MD 中体现
- **多场景处理检查**：检查多场景合并规范是否落实（即使 CSV 只有单行，也应按场景1格式分组）
  - 确认一个 CSV 文件只产出**单个** MD 文件，未拆分为多个 MD 文件
  - 是否提取了公共前置条件，没有在多个场景中重复声明相同资源
  - 是否按场景分组（二级标题），每个场景是否标注了用例编号
  - 场景间若存在依赖，是否已标注 `> 依赖：场景X（用例xxx）已执行完成`
  - 测试数据复用场景是否标注"共享同一套测试数据，所有用例执行完成后统一清理"
- **★ 前置条件可执行性校验（最高价值·治"编辑/删除/详情类用例无对象可操作"）**：检查 CSV 的"前置条件：已预置/已创建好 XX（如 policy1）"**没有被照抄成"环境已预置 XX"**，而是已转写成**自动化可执行的前置**
  - 凡某场景步骤是"对已存在的 XX 执行编辑/删除/查看详情"，确认 MD 已写清该 XX 的来源——"脚本自己保证存在（先查、不存在则创建）"或"复用前序场景 class-scoped 共享创建的资源"，而非默认环境里已有、让阶段二只 `search` 就用
  - CSV 标"数据可复用=是"的场景：确认 MD 写明复用前序场景数据、**不在前一场景就删除**（否则后续依赖它的场景无数据可用——这是连撞 15 次冻结的真实事故成因）
- **命令规范检查**：检查命令转换是否符合第一部分的编写规范
  - 后台执行命令是否使用 nohup
  - 同一组多命令是否用 && 合并成一行
  - 执行后不会立刻返回结果的命令，是否增加了轮询等待（最长 60 秒）
- **fixture 改写检查**：检查 VNC / SSH / 本地客户端操作描述是否已按规范改写
  - 【打开虚拟机 vnc】等操作 → 通过 ssh_vm fixture 连接虚拟机后台执行
  - 【ssh 连接虚拟机系统后台】等操作 → 使用 ssh_vm fixture
  - 【本地客户端 ssh 连接环境】等操作 → 使用 ssh_host fixture
- **fixture 约束检查**：检查 MD 文件中是否已包含 fixture 强制约束的注意事项
  - 实现注意事项章节是否包含"实现测试步骤或前置条件前必须阅读 `fixtures_index.md`"的强制约束提示
  - 可复用 Fixture 参考是否已列出本用例可能涉及的 fixture 及其用途说明
- **清理顺序检查**：检查测试数据清理流程顺序是否正确（是否按照测试需求的 CSV 文件中定义的顺序）
- **脚本可执行性预判**：检查以下内容是否已在需求文档中明确，若缺失或不明确直接补充
  - **关键路径覆盖**：明确每个测试步骤对应的脚本操作和验证结果
  - **断言策略**：明确每个关键步骤使用页面元素断言 / SSH 后端验证 / 两者结合
  - **测试数据策略**：资源名称使用 `random_data()`，批量创建使用 fixture 的 `count` 参数
  - **清理策略**：资源清理顺序按照 CSV 文件中定义的清理顺序来写
- 若发现缺失、歧义或不明确，直接在 MD 文档中补充完善，无需询问

**循环规则**

按上述检查项逐项检查 → 发现不符合 → 修改 MD 文档 → 重新检查 → 直至全部符合。
- **遵循通用循环约定，严禁停下来询问用户**，所有检查发现的问题自主修改
- 直至全部检查项均通过，方可进入下一阶段
