# 阶段五：稳定性验证

## 一、执行总纲

本阶段对每个测试文件执行稳定性验证，轮次按用例成本**自适应**（见 1.1），全部轮次执行完毕后统一判定结果。执行过程中严禁中途修复、结束或跳转其他阶段。

### 1.1 自适应轮次（按用例单次墙钟成本分级）

> **依据**：稳定性验证的价值是"用重复执行暴露偶发抖动"。对单次墙钟很长的昂贵用例（如裸金属 BMS 单次 70~100min），固定 5 轮会带来 7.5 小时级的纯验证耗时，而 5 轮相对 3 轮对"偶发抖动"的边际发现收益很低、远不及墙钟代价。故按成本分级，**不是降低标准，而是把验证强度用在性价比合理处**。

| 用例单次墙钟成本 | 稳定性轮次 | 判定"通过轮次"阈值 |
|---|---|---|
| 低成本（< 15min） | **5 轮**（维持原标准，多跑无妨，保留高置信度） | ≥ 3 轮通过 |
| 高成本（> 15min） | **3 轮** | ≥ 2 轮通过 |

- 成本依据需求 MD 中各步骤等待时长之和粗判（与阶段三 6.1 同口径）。
- **含 `pytest.skip`（产品超时）或已标记产品缺陷的用例**：不重复消耗稳定性轮次。
- 阈值随轮次同步（5 轮→≥3、3 轮→≥2），**判定决策树本身不变**（见 3.2）。

**执行注意事项**

1. **全量执行约束（含早停/超时例外）**：原则上必须完整执行所选定的轮次数、不得随意提前终止；**唯二的例外见下方 1.2「早停与超时熔断」——连续同一失败早停、单轮超时**，命中即按 1.2 提前终止并判定，避免对"注定失败 / 已卡死"的用例硬跑满轮次。
2. **禁止中途修复**：所选轮次执行完毕前，发现用例问题也不得返回阶段三修复，须等全部轮次执行完毕后统一处理。
3. **MD 文档保护**：验证过程中严禁修改阶段一产出的 MD 需求文档，除非确认 MD 本身存在转换错误。
4. **日志规范**：每次运行 pytest 前，通过 `Bash` 定义 `LOG_FILE` 变量（路径在项目根目录的原生日志目录 `logs/` 下，命名按测试 py 文件名），并传入 `--log-file=$LOG_FILE --log-file-level=DEBUG`。严禁执行不带 `--log-file` 的 pytest 命令。
5. **失败处理**：每轮执行后若存在失败用例，按阶段三四步法分析根因并记录，但**仅记录、不修复、不阻断后续轮次**（但若命中 1.2 的早停/超时条件，则按 1.2 提前终止，优先级高于本条"不阻断"）。

### 1.2 早停与超时熔断（防无意义长跑 / 卡死，2026-06-19 新增；2026-06-24 删除"阶段五总墙钟 90min"限制、连续同一失败早停由 2 轮放宽到 3 轮）

> 阶段五不经 run_guard、本身没有机械熔断，历史上出现过"对没修好的用例硬跑满轮次、或某轮 hang 住导致卡死几小时"。本节给阶段五补两道刹车，**优先级高于 1.1 的"必须跑满轮次"要求**：

1. **连续同一失败早停**：若**连续 3 轮**出现"同一个失败"（失败用例相同、错误类型 / 堆栈位置本质相同——与阶段三状态冻结同口径）→ **立即停止剩余轮次**，判定"稳定性不通过（用例问题）"，按 3.2 决策树处理（返回阶段三；若阶段三额度已耗尽 / 已是遗留则标记遗留并结束本阶段）。连续 3 轮报同一个错说明这是**稳定的用例缺陷、不是偶发抖动**，再多跑也是同样结果、纯浪费。
2. **单轮超时（机械杀进程，不靠掐表自觉）**：每轮 pytest **必须设单轮超时上限**（≈ 该用例单次墙钟成本的 2 倍、且**不低于 20 分钟**；**算不准就直接用 `1200` 秒=20 分钟**）。优先用 `timeout <秒> python … pytest …` 包装（git-bash 的 `timeout` 命令，超时会自动杀子进程、返回码 124）；若采用"后台运行 + 轮询"方式，则**一旦累计轮询等待超过该上限，必须 `kill <pytest PID>` 杀掉该轮进程**、判该轮失败，**严禁无限 `sleep` 轮询等待一个迟迟不结束的 pytest**。

**一句话：阶段五宁可早停 / 超时收尾，也绝不对注定失败的用例硬跑满轮次、绝不无限轮询等待一个 hang 住的 pytest。**

## 二、"环境问题"的明确定义

1. **定义**：某用例因环境波动失败且被判定为**环境问题**时，本轮 pytest 仍须完整执行所有用例（不得中途终止）。待本轮全部执行完毕后，在结果分析阶段将该用例标记为"环境问题"。
2. **核心原则**："环境问题"只能在结果分析阶段标记，严禁以任何方式修改测试脚本来绕过失败，包括但不限于：`pytest.skip()`、`@pytest.mark.skip`、`try/except` 捕获异常后既不处理也不重新抛出。
3. **流程**：pytest 完整执行本轮所有用例 → 某用例因环境波动失败 → AI 分析根因确认为环境问题 → 记录失败原因与环境波动特征 → 标记为"环境问题" → 继续执行下一轮。

## 三、执行与判定规则

### 3.1 执行规则

- 按 1.1 自适应轮次执行（低成本 5 轮 / 高成本 3 轮），每轮执行该文件的全部用例，不得遗漏。
- 每轮执行前按日志规范定义 `LOG_FILE`。
- 某轮中存在失败用例时，分析根因并记录，然后继续执行下一轮。
- **早停 / 超时优先（见 1.2）**：执行全程持续监控 1.2 的两道刹车——连续 3 轮同一失败 / 单轮超时，**命中任一立即按 1.2 提前终止并判定，不再跑后续轮次**（此优先级高于"必须跑满轮次"）。

### 3.2 判定决策树

原则上在所选轮次（低成本 5 轮 / 高成本 3 轮）全部执行完毕后，再按以下决策树判定；**但若已触发 1.2 的早停/超时（连续 3 轮同一失败、单轮超时），则按【已完成的那几轮】结果直接套用本决策树判定，不要求跑满轮次**（早停下"通过轮次"几乎必然未达标，会落到对应的不通过分支，这是预期行为）。

**判定前说明**：
- "失败轮次中有 用例问题"指：只要任意一轮的任意一个失败用例，其根因判定为**用例问题**，即触发该分支。
- "失败轮次中有 产品缺陷"指：只要任意一轮的任意一个失败用例，其根因判定为**产品缺陷**，即触发该分支。
- "遗留问题"指阶段三因轮次耗尽或状态冻结而强制标记的问题，正常情况下不参与阶段五验证；如带入则按用例问题路径处理（返回阶段三）。
- "通过轮次"指：该轮 pytest 执行结果为 PASSED，即该轮所有用例均执行成功，无任何 FAILED 用例。
- "失败轮次"指：该轮存在根因为用例问题/产品缺陷/环境问题/遗留问题的 FAILED 用例，即该轮 pytest 执行结果为 FAILED。
- "通过轮次达标"指：按 1.1 阈值——低成本用例 ≥ 3 轮通过，高成本用例 ≥ 2 轮通过。
- 无论最终判定结果如何，均需在问题总结中如实记录所有失败轮次的根因。

```
失败轮次中有 用例问题？
  ├─ 是 → 【验证不通过】返回阶段三修复用例
  │         （按阶段三四步法修复，重新执行阶段四、阶段五。同一根因的用例问题最多修复 8 次，
  │          超过 8 次仍失败的，记录为遗留问题并结束本阶段任务）
  └─ 否 → 通过轮次达标（低成本 ≥3 / 高成本 ≥2）？
       ├─ 是 → 【验证通过】阶段五结束任务，稳定性验证通过
       └─ 否 → 失败轮次中有 产品缺陷？
                ├─ 是 → 【验证不通过】阶段五结束任务，醒目提示"发现产品缺陷，请提交缺陷"
                │         （若失败轮次中同时含环境问题，提示"环境问题及产品缺陷"）
                └─ 否 → 【验证不通过】阶段五结束任务，提示根因为环境问题
                          （已排除用例问题和产品缺陷，剩余失败轮次即为纯环境问题）
```

### 第二部分：修复经验沉淀总结

> 每行 = 一个被修复/标记的问题。各字段填写说明见表格下方编号列表，务必按「填写总则」写详细。

| 所属阶段 | 问题描述 | 问题具体根因 | 根因分析依据 | 涉及文件与定位 | 关联组件/适用场景标签 | 最终修复方案及原因 | 经验沉淀总结 | 复发概率·优化优先级 | 建议沉淀去向 |
|:---:|---|---|---|---|---|---|---|:---:|---|

**字段填写说明**（逐列对照填写，宁详勿简）：

1. **所属阶段**：该问题首次被发现或高发的阶段（阶段一~五）。
2. **问题描述**：失败现象 + **报错原文关键句**（如 `locator ... resolved to 0 elements`），不得只写"定位失败"这类笼统词。
3. **问题具体根因**：真正的根因，而非表象（如"Vue v-if 选值后销毁并重建了表单项 DOM"，而非"找不到元素"）。
4. **根因分析依据**：判定根因所凭的证据，标注来源——截图 / 日志 / 代码 / 后端取证（scli·SSH）。
5. **涉及文件与定位**：精确到 `文件路径:行号 方法名`，定位/断言类须写 **原值 → 新值**（如 `lb_pool.py:142 lb_forward_rule_create，.el-form-item 占位符过滤 → .form-left 区域定位`）。**这是无上下文可复现的命门，必填。**
6. **关联组件/适用场景标签**：本问题牵涉的前端组件/技术特征 + 该经验可推广到的模块/操作类型，合并为一组检索标签，便于后续按特征查同类问题。例：`Element UI 表单 + Vue v-if 动态渲染；适用：转发规则、策略配置等动态表单`、`cl-button 自定义组件；适用：BMS 等自定义组件页面`。
7. **最终修复方案及原因**：实际怎么修的 + 为什么这么修（含与其他候选相比的取舍理由，一句话带过即可，如"用 `.form-left` 区域定位替换占位符过滤：区域类名最稳定、不依赖 v-if 渲染时序，优于'选值前先存引用'方案"）。
8. **经验沉淀总结**：从本案例提炼的**可复用规律/方法论**（如"含 v-if 动态切换的表单，禁止依赖会消失的占位符做容器定位，应用稳定区域/类名"），要写成"下次遇到同类情况应怎么做"。
9. **复发概率·优化优先级**：用"复发概率（高/中/低）·优先级（1~5★）"合并表示——复发概率指该问题在其他用例再现的可能性，★越多越应尽快据此优化项目/skill。如 `高·★★★★☆`。
10. **建议沉淀去向**：该经验应回填到哪里去固化——① 回填 `phase2-coding.md` 编码/定位规范；② 回填 `phase3-execution.md` 速查表/分析原则；③ 提请新增/增强 fixture 或 Page Object 公共方法；④ 提请补充 `case_specs/prompts/` 下规范文档；⑤ 仅记录（个案，不具普适性）。
