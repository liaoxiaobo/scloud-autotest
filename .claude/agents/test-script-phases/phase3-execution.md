## ★ 强制：阶段三所有 pytest 必须经 run_guard.py 执行（机械硬熔断，针对 AI 自律失效）

> **为什么强制**：阶段三修复循环在本子智能体内部跑，编排层的 loop_gate 插不进来；而轮次上限/状态冻结若靠"自觉计数"会被忽略（实测曾 40+ 轮、计数区停留 0、空耗 10+ 小时）。故把刹车放在**每次 pytest 调用**这个绕不开的点。

- **进入阶段三执行 pytest 前先重置守卫状态**（首次进入用本条命令；**回退重入见下一条、改用 `--reset --reentry`**），并传入本次**场景数**（= `def test_` 方法数）以缩放全局上限：
  `python .claude/skills/test-script-dev/scripts/run_guard.py --reset --task <任务标识> --cases <场景数>`
  - **全局上限随场景数缩放** = `max(60, 场景数×10)`（如 8 个场景→80）；**单用例上限 40 次、连续相同失败冻结 15 次**（口径：1 次 pytest = 1 次）。（阈值沿革：2026-06-17 收回为 20/场景数×8/5；2026-06-19 冻结 5→10、单用例 20→30、全局下限 20→40；2026-06-21 单用例 30→40、冻结 10→15、全局下限 40→60、每场景 8→10）
  - **★ 回退重入用 `--reset --reentry`（重要，杜绝"无限续命"）**：阶段四/五回退到阶段三、重新派发本子智能体时，**执行 `python .claude/skills/test-script-dev/scripts/run_guard.py --reset --reentry --task <任务标识> --cases <场景数>`**——它**不清零累计的全局次数**（全局墙钟与全局额度跨回退连续计），只清空各用例的单用例/冻结计数让本次回退能继续修，并**从当前全局累计位置再发放 10 次额度**（幂等：即便重复 reset 也不会叠加预算）。**严禁再用裸 `--reset`（不带 `--reentry`）做回退**，那会把全局清零、退化回"每次回退拿全新预算"的旧 bug。**注意区分两个计数器（互不冲突、各管各的）**：① run_guard 的单用例 40 次 = "**每一次阶段三派发内部**"的执行次数闸（回退重入时该计数清空、全局不清空）；② 编排层运行报告里的 `heal_same_rootcause`（同一根因最多 8 次）= "**这个根因总共被回退重修了多少次**"的闸，**跨回退累加、不随 reset 清零**。前者控"单次进阶段三能跑多少"，后者控"能回来几次"。
- **★ 上下文压缩 / 中途续跑：绝不重跑 `--reset` 或 `--release`（2026-06-26 新增·治"续命"事故）**：阶段三常长跑数小时、会触发 Claude Code 自动上下文压缩；压缩后你可能"忘记"开机已经 reset 过，**切勿把上面首次的 `--release`/`--reset` 当成开机动作又跑一遍**——重跑裸 `--reset` 会清零次数/全局墙钟上限（"续命"，实测曾因此 9h14m 跑 60+ 次会话却没被任何上限拦住）。**铁律：本次阶段三只在最开始 reset 一次；此后无论是否被压缩、是否换了上下文，一律【不再 `--reset`、不再 `--release`】，直接继续下面"每次跑 pytest"那条命令即可。** 确需对本任务全新重置才用 `--reset --force`，回退重入才用 `--reset --reentry`。（run_guard 已加机械兜底：检测到本任务"运行中"时会忽略多余的裸 `--reset`、不清零计数；但你仍须主动不重跑，别依赖兜底。）

## 完工前·状态翻转类用例的迷你稳定自检（架构新增·2026-06-18·减少"阶段五→三"昂贵回退）

> **背景（实测教训，sg_scenario）**：用例阶段三单次跑过了、却在阶段五连挂 5 轮——根因是"删 ICMP 规则后验证 ping 不通"这类**依赖平台异步行为的状态翻转**断言：单跑会偶发"假通过"（实为平台在绑定后自动重新加回 `default` 安全组、放行了流量），只有重复多轮才稳定暴露。等到阶段五才发现 → 触发昂贵的 阶段五→三→四→五 整轮回退。把这一步**前移到阶段三完工前**，可在同一上下文、用最小代价提前发现并修掉，避免回退往返。

- **触发条件（仅限高风险类，普通用例不加跑、不拖慢简单用例）**：某用例的**核心断言是验证一次"状态翻转/反向预期"**——典型：删除/解绑/禁用/删规则后验证"已不存在 / 已不可达 / 已失效 / ping 不通 / 访问被拒"。这类"反向预期"最容易被平台异步行为或默认兜底（如自动重加 default 安全组）悄悄破坏，单跑易假通过。
- **做法**：对命中上述条件的用例，在判定"最终通过"前，**额外连续重复跑该用例 2 次**（即该用例需连续 3 次一致通过才算过；可用 `-k` 只跑该方法、复用已建资源，单次秒级~分钟级，每次仍经 run_guard）。**3 次中只要有 1 次出现"状态没真翻转"（删了还在/还通、解绑了还连）→ 判未通过，按四步法找真根因修对**——根因多半是"被测对象没真正只受目标配置控制"（如本例 default 安全组未被排除，应用后端 `scli` 取证 + 排除干扰，而不是放宽/跳过断言）。
- **不命中此条件的普通用例**（创建成功、字段回读、正向连通等）：**维持原流程——一次完整执行 + 一次 Jenkins 对齐执行即可，不额外加跑**。
- **与 Jenkins 对齐执行闸合并计数、不重复跑**：上述"3 次一致通过"里，允许其中一次就是 Jenkins 对齐形态那次（即"完整跑1 + 重复1 + Jenkins对齐1"≈3 次），不必在 Jenkins 对齐之外再额外多跑，避免拖慢。
- **目的说明**：本步骤是把"阶段五会发现的状态翻转类偶发问题"**尽量在第一次阶段三就拦下并修对**，从而减少回退重入次数；它**不替代**阶段五（阶段五仍按其轮次做整套件稳定性验证）。

## 二、修复前强制约束(在做任何修改前必读)

### 2.1 修复纪律

- 严禁盲目修改代码 —— 盲目修改会引入回归或掩盖真实根因(基于错误假设的重复尝试由 3.3 状态冻结机制兜底)

- **修复必须遵循阶段二编码规范** —— 阶段二(`.claude/agents/test-script-phases/phase2-coding.md`)中定义的全部编码规范同样适用于阶段三的修复动作;凡是阶段二禁止的写法,阶段三修复时一律禁止;凡是阶段二要求的写法,阶段三修复时一律遵守

- **已有用例只增不减（防误删，与阶段二同规）** —— 修复只能改动"本次任务相关的用例/Page 方法";**严禁用 `Write` 覆盖整个测试文件、严禁删除或改写文件里与本次无关的已有 `def test_` 用例**。改动测试文件后,若发现已有用例数变少＝误删/误覆盖（**严重事故**）→ **立即停止本阶段任务,严禁用 git 或任何其它方式自行补救/恢复,在对话框醒目提示用户"已有用例被误删、需人工从版本库/备份恢复后再继续"并等待处理,不要继续执行**。**本工作流全程禁止执行任何 `git` 命令（`git checkout`/`git reset`/`git clean`/`git restore`/`git pull`/`git commit`/`git push` 等一律不准，且严禁提交代码）——既不准用 git"绕过失败",也不准用 git"恢复误删"（误删按上述：停止并提示用户人工恢复）。**

### 2.2 ❌ 错误修复模式速查表(命中任一项 → 立即停止,回 Diagnose)

**反模式识别口诀**:遇"补充逻辑 / 绕过失败 / 掩盖错误"动作 → 强制对照下表;表里没有的变体也按下表精神识别(如 `if not exist: 补创建` 是第 5 项变体,`|| true` 是第 12 项)。

| # | 错误修复模式 | 正确做法 |
|---|---|---|
| 1 | 把"快速让测试通过"当首要目标,跳过根因分析直接调代码 | 先完成 Diagnose,再按根因类别修复 |
| 2 | 用 `try/except` 兜底吞错让用例继续 | 让真实异常抛出,修复实际问题 |

| 4 | 把断言"等于"改"包含"、删除断言、放宽预期 | 保持原断言强度;若产品行为改变 → 产品缺陷 |

| 6 | 改 `pages/` 已有公共方法的定位逻辑绕过页面对象缺陷 | 记录为页面对象修复项,提请测试开发处理 |
| 7 | 修改 CSV/MD 中的端口、协议、权重、URL 等业务参数让脚本通过 | 业务参数偏差是产品缺陷或环境问题,不是改 MD 的理由 |
| 8 | 移除 `@submenu` 等已有装饰器以"消除报错" | 装饰器报错通常是环境问题(抽屉遮挡/导航异常),修环境不动装饰器 |
| 9 | 测试层引入 `locator()` / `expect()` / XPath / 直接 `from playwright import expect` | 必须通过 Page Object 封装的方法调用 |
| 10 | 在测试主流程里加 `try/finally` 包裹核心步骤 | 用 fixture 的 yield 机制管理清理 |
| 11 | 忽视 teardown 阶段的 ERROR(如清理失败、SSH 断连) | teardown ERROR 视同用例问题,必须修复;teardown WARNING 必须记录 |
| 12 | 用 `\|\| true`、`echo $?` 兜底掩盖 SSH 命令失败 | 必须断言 `rc` 和 `stdout` |
| 13 | 凭空构造新定位(未经前端代码/运行时侦察佐证就改 locator 试错) | 必须以 `Grep` 前端工程代码或 `recon_page.py` 运行时渲染态为依据再改 |
| 14 | 把"前端流程/表单结构性差异"当普通定位反复改 locator | 识别为结构性差异 → 回对齐需求 MD 重新梳理步骤,而非死磕 locator |
| 15 | 为"复现快"把调试期裁剪(跳前置/复用资源)固化进脚本 | 调试期手段≠脚本逻辑;最终判定通过必须是一次完整、未裁剪的执行(见"六") |
| 16 | 只为消除 teardown 报错而弱化清理(删清理步骤、清理加 `\|\| true`) | teardown 是成功标准一部分,按根因修清理逻辑,不绕过 |
| 17 | 把 P0/P1 断言降级(P0 必断的成功弹窗/存在性/状态收敛被删或改弱以求过) | 断言分层是需求覆盖的一部分,按 `assertion_guidelines.md` 保持分层强度 |
| 18 | 擅自修改已有且稳定的方法以适配本用例(改稳定的 Page Object 业务方法、断言方法、fixture 内部实现去迁就本用例) | **扩展而非改写**:新建 `assert_<对象>_<新验证点>`/新业务方法,或给原方法新增带默认值的可选参数(保持原行为不变);`assertions/`、`common/` 内已封装方法严禁直接改 |
| 19 | 把需求 MD 要求的**核心断言用 `if 条件: 跳过` / 提前 `return` / `try` 吞掉**,使其在某些运行下根本不执行——只为让用例"显示通过"(实测教训:删 ICMP 规则后"ping 不通"断言被"if default 存在则跳过"绕过,被阶段四判定核心断言缺失、打回重修) | **核心断言必须无条件执行,不许条件跳过**。若平台行为/异步兜底导致"反向预期"暂时无法在 UI 验证(如平台自动重加 default 安全组),正确做法是**按根因修对**:用后端 `scli`/SSH 取证、或排除干扰因素让被测对象只受目标配置控制(如强制把端口安全组设为目标组),让断言真实执行并通过;实在是产品限制 → 标"产品缺陷/遗留",**绝不"跳过断言求过"** |

### 2.3 修复前 7 项强制自检(每轮 Fix 步骤必须逐条勾选并输出到对话框)

□ 1. 触及 CSV/MD 业务参数?              ___(是 → 禁止修复,回 Diagnose)

## 三、防循环机制（次数上限·状态冻结·进展信号；已无"加轮次奖励"）

### 3.1 单用例次数上限:40 次

单个用例（= 测试需求 CSV 的一行 / 一个 `def test_` 方法，阶段三调试时用 `-k` 单独跑）累计 40 次 pytest 仍未修复 → 标记"遗留问题(用例问题-次数耗尽)",停止该用例。计数由 run_guard.py 机械维护，1 次 pytest = 1 次。（上限定为 40：弱模型修复准确度低、复杂用例 setup 链长，需要更多修复空间；原地打转由"连续相同失败冻结"机制兜底，不会无限续命）

> **计数粒度说明（重要，防误解）**：调试某个失败需求时，**必须用 `-k <该方法名>` 只跑这一个方法**——这样每个需求（方法）各自独立拥有 40 次额度、互不挤占（run_guard 以"测试文件 + -k 方法名"为计数键）。若不带 `-k` 整文件跑（仅用于首次全量跑、最后整文件验证），则整文件共用一份计数。所以"单用例 40 次"成立的前提是：调试单个需求时用 `-k` 单独跑。

### 3.2 进展信号(仅用于记录与冻结清零,不再额外加次数)

**触发轮次**:从该用例的**第 2 轮**起每轮都做检查,任意一轮满足触发条件即可生效。

**触发条件(以下任一即可,需在反馈中明确标注证据)**:

- **根因类型变化**:根因类型从 A 类切换到不同类(如从"用例问题"切到"产品缺陷";或同为用例问题但子类型从"等待时机"切到"定位错误"且基于新证据)
- **失败现象本质变化**:失败步骤、错误类型、堆栈位置发生本质改变(不是同一行同一报错重复出现)

**规则(2026-06-19 调整)**:单用例上限为扁平 40 次,**不再因进展额外增加次数**（"动态进展奖励"机制已评估，因弱模型易滥用"自称有进展"骗额度而不采用，改为提高固定上限 + 由冻结机制放行真有进展者）。本节"进展"判断仅两个用途:① 在反馈中记录本次相对上次是否在推进;② 失败现象一旦变化(有进展),run_guard 的"连续相同失败"冻结计数立即清零(见 3.3),从而保证有进展时不会被误冻结。

### 3.3 状态冻结检测:连续 15 次失败在同一位置（零前进）

连续 15 次失败在**同一位置**(run_guard 按「失败测试 nodeid + 最深的用户代码 file:line」做指纹判定,**与报错文本是否变化无关**) → 判定原地打转、零前进,标记"遗留问题(用例问题-状态冻结)",停止该用例。**只有推进到新的失败位置(真有进展:过了旧阻塞点、在更靠后处失败)或某次通过,冻结计数才清零;靠换 selector/等待让报错文本变一变【不会】清零。** 由 run_guard.py 机械判定。（上限连续 15：配合 §3.3.1「连续卡同一处先看失败现场再改」，避免把额度浪费在盲改/原地打转）

### 3.3.1 ★ 连续同一失败：先看"失败现场真实渲染态"再改、禁止继续盲改（2026-06-19，治"原地打转"根因）

**这是把"被动等冻结(15 次)"提前为"主动纠偏"的硬规则。** 失败位置连续相同（同一测试 / 同一处用户代码 file:line，**即便报错文本变了**），说明你上一次的修改方向是错的、或根因不在你改的地方——继续在代码里猜 selector / 微调等待，只会一次次卡在**同一个位置**、白烧修复次数直到冻结（实测曾连续多次卡同一处、全程没看真实渲染态、反复改 selector 原地打转）。

**触发与动作（机械执行，不得跳过）**：
- **连续第 2 次起仍失败在同一位置**（改一次、重跑后**仍卡在同一测试/同一处代码**——run_guard 按失败位置而非报错文本判定，**报错文本变了也算同一位置**）→ **立即停止"继续猜 / 微调 selector / 加 `.first` / 改正则 / 只换等待"这类没有新证据的改动**。
- **⓪ 先确认"是不是站对了页面"（列表页元素定位失败的头号根因，务必第一个查）**：定位**搜索框 / 表格行 / 行内按钮**等"列表页元素"失败时，先看失败现场 `*_domsnap.md`/截图里的**当前 URL/页面**是不是目标列表页——**极可能是导航只到了服务概览页（如 `#/vpc-overview`）而没真正切到目标列表页（如 `#/transfer-strategy`）**。**若不在目标页：先修导航（强制走 `_ensure_list_page` 类兜底、或确认 `goto_submenu` 真的切了路由），绝不在元素定位上反复改**。**注意：domsnap/截图里的真实 URL 优先于日志里的"成功导航到子菜单/导航成功"——后者会误报**（实测曾因信了"成功导航"日志、在概览页上反复改搜索框，连撞 15 次冻结）。
- **第一手·必看：失败现场 DOM 摘要——在 `dom_snapshots/<模块>/<测试名>/` 目录下取【最新生成】的 `*_domsnap.md`**（失败时由框架**自动生成、无需你跑**；同一用例失败多次会有多个，**务必按时间戳取最新那个＝本次失败现场**；内含失败那一刻**真实渲染态**的可定位元素清单——顶部标注"弹窗/抽屉状态"，下列按钮/输入/radio·checkbox/tab/表头的**真实文案 + role + class**，标【DISABLED】的为当前不可点）。**先读它**，逐项核对：① 容器（是 dialog 弹窗、还是内联表单/抽屉——摘要顶部已判定）；② 目标是表格行 `tr`、还是卡片/下拉/radio；③ 真实文案与层级；④ **你失败用的定位/文案在清单里有没有对应元素**（没有＝多半还没渲染好或选错容器，应补等待/换容器，而非继续换 selector）；⑤ 是否在某 tab/向导步内。**只要 domsnap 已能确定真实定位，直接据此重写——硬产出物：未结合 domsnap（或失败截图）就改 locator = 本轮修复无效。**
- **补充·按需 recon**：仅当 domsnap 不足时才跑 `recon_page.py`——典型：目标元素在 domsnap 里**根本没有**（疑似未渲染/需先滚动展开，需重新导航侦察），或要用 `--probe-click` 秒级验证"点击到底有没有效果"：
  `python .claude/skills/test-script-dev/scripts/recon_page.py --service "<服务>" [--submenu "<子菜单>"] [--probe-click "<目标文案>"]`
- **若发现是"结构性差异"**（典型：你按"表格行 `tr` + `.el-radio`"写、实际是"卡片/下拉选项"）→ 按 2.2 速查表 #14 回到正确结构重写，而非死磕 selector。

**一句话铁律：失败位置连续 2 次不变（报错文本变了也算）= 先读 `*_domsnap.md`/看截图、用真实渲染态证据重写定位；严禁不看现场就再交一版"只换了 selector"的修改。** 15 次冻结上限是给"确实在推进、失败位置在往后走"的修复留的，不是给"同一处猜 15 遍"用的。

### 3.4 第 3 轮 Mini-Checkpoint:零基重新分析(强制)

**触发时机**:**该用例的第 3 轮**修复(不是阶段三全局第 3 轮)。每个用例独立计数。

任意用例进入第 3 轮修复时,**强制做一次零基重新分析**,而不是基于前两轮假设递推:

```
【零基复盘 - 强制执行】
1. 重新完整阅读需求 MD 中本场景的预期行为(忘掉前两轮假设)
2. 重新读取最新日志的完整堆栈,找最早的异常来源(不是最深的)
3. 检查是否有公共因素(fixture / 页面对象 / 上游用例污染)
4. 重新做证据收集 → 重新做根因判定 → 给出与前两轮不同的假设或明确确认前假设
```

零基复盘后若仍维持原假设,必须给出新证据支持;否则视同状态冻结。

### 3.5 全局次数上限:max(60, 场景数 × 10)

整个阶段三累计达到 max(60, 场景数×10) 次后,未修复用例全部标记"遗留问题(全局次数耗尽)",停止修复,进入阶段四、五。遗留问题不参与阶段五验证。（全局活跃墙钟超 10h 时 run_guard 直接硬停、强制收尾标遗留转人工——硬上限、防长跑；已扣除长空闲间隔）**此上限由 `run_guard.py --reset --cases <场景数>` 自动算出（场景数 = `def test_` 方法数），你无需手算，只要 reset 时把 `--cases` 传对即可。回退重入用 `--reset --reentry`：全局额度不清零、仅 +10 小额回退预算。**

### 3.6 批量失败主因优先(仅在首轮触发,且失败用例 ≥3)

**触发条件**:某测试文件**首次** pytest 执行后,失败用例数 ≥3 → 触发本机制(后续轮次不再触发)。

**先做主因聚类再开修**:

- 是否同一 fixture 报错(setup / teardown 失败)→ 先修该 fixture
- 是否同一页面对象报错(同一 locator / 同一方法)→ 先修该页面对象的下游用例
- 是否同一前置资源缺失(SLB / VPC / VM 未就绪)→ 先确认前置 fixture
- 是否同一 SSH 命令报错 → 先确认目标节点和命令语法

**主因修完后再用一轮验证整体改善**,避免对每个连锁失败用例独立耗轮次。**次数归属**:批量主因修复占用 1 次全局计数(计入 3.5 全局 max(60,场景数×10) 次上限),不计入任何单用例的 40 次上限。

### 3.7 三次失败质疑根因/架构(Phase 4.5,强制)

**触发时机**:同一用例修复累计 **≥3 次**仍失败(与 3.4 第 3 轮零基复盘叠加生效:3.4 解决"换个假设",3.7 解决"是不是方向/对象本身错了")。

进入本机制时,**停止"头痛医头"式的第 4 次定位/等待修补**,强制在反馈中显式回答三问并给出结论:

```
【Phase 4.5 - 三次失败质疑(强制显式输出)】
1. 是否实为产品缺陷? → 用四步法 Diagnose"判定纪律"中的"后端取证(scli/SSH)"复核 UI 与后端是否均异常
2. 是否需求理解/脚本结构本身错了? → 回读需求 MD,确认不是"在错误的步骤/对象上反复改 locator"(可能需较大重写而非局部改)
3. 是否每次修复都在"别处"冒新问题? → 是 → 架构性信号,不是单点 bug,标记需人工评估
```

- 三问结论必须显式写入本轮反馈,再决定是否继续(仍受 3.1 单用例 40 次 / 3.3 连续 15 次冻结 / 3.5 全局上限约束)。
- 若复核后判定为产品缺陷/环境问题 → 转对应处理路径,不再消耗用例修复轮次。

## 四、四步修复法(每轮修复必走全流程)

### 第一步:复现(Reproduce)

```
[ ] 1. 诊断起手:先 `Read` 失败案例库 `.claude/skills/test-script-dev/references/failure_case_library.md` 比对已收录失败模式,并读运行报告里阶段二写入的「页面侦察结论卡」(命中即直接用、免重复 recon;无卡不报错、按常规四步法继续)
[ ] 2. 重读需求 MD 对应步骤的预期行为
[ ] 3. 完整读本失败用例自身的 `test_*.py` 及其调用的 Page Object 方法实现,理清调用链(**严禁在没读懂自己脚本调用链的情况下就改代码**)
[ ] 4. 定位日志文件(在 `logs/<模块>/<测试名>/` 下,如 `logs/network/test_lbv2_create_lb_and_http_listener/test_xxx.log`),看完整堆栈,确认错误类型(TimeoutError / AssertionError / 定位错误 / SSH 错误 / 其他)
[ ] 5. 查看 `screenshots/<模块>/<测试名>/` 下的失败截图 `.png`;**定位/元素类失败必看 `dom_snapshots/<模块>/<测试名>/` 下【最新】 `*_domsnap.md`(失败那一刻框架自动采集的真实渲染态元素摘要)**,对比预期 vs 实际页面状态/真实元素的 class·role·文案
[ ] 6. 诊断优先用已有证据,不强制全量重跑(见下"诊断重跑分离");仅"失败不稳定/疑似环境波动"时才补跑确认
[ ] 7. 截图、DOM 摘要与日志冲突时,以截图、DOM 摘要和日志事实为准
```

> **诊断重跑分离(高成本用例提效,见"六")**:Diagnose 应优先基于"已有证据(日志最早异常源 + 失败截图 + `*_domsnap.md` DOM 摘要 + 后端 scli 取证)"推理,**不必每轮都全量重跑**;只有失败不稳定(首次失败、补跑通过)需要确认环境问题时才补跑,且高成本用例可只重跑到失败步骤的最小前置,而非整条。**修复后才做一次完整用例验证**(避免"边猜边全量长跑")。

### 第二步:隔离(Isolate)

按错误类型只执行对应动作,不要全部执行:

| 错误类型 | 隔离动作 |
|---|---|
| **TimeoutError** | 检查是否在 `wait_for_load_state('networkidle')` 之前操作;用 `.count()` 验证 locator 命中数;查异步加载未完成 |
| **AssertionError** | 对比预期值与实际值,辨别"数据被污染"还是"断言逻辑错误"(如写死期望值但实际动态) |
| **定位类错误** | 用 `page.locator(selector).all()` 或 `recon_page.py`(运行时侦察,先 `--help`)列出页面真实匹配元素,对比实际文本/属性;**先比对 `dom_snapshots/<模块>/<测试名>/` 下最新 `*_domsnap.md`(失败现场自动采集的真实元素摘要)**;确认是否在正确的 dialog/tab/表格/行范围内;**先用 `Grep` 查 `sugon_web/refrence/` 前端工程代码确认定位/文案是否真的对不上** |
| **SSH 连接错误** | 检查 `ssh_host.run()` / `ssh_vm.run()` 命令语法、目标节点可达性、资源是否已创建成功;核对 MD 中 SSH 命令转换是否正确 |
| **其他**(仅在以上 4 类均不匹配时才使用,严禁作为 catch-all 默认归类) | 检查环境状态(测试环境是否重启、节点是否可用);若仍不能定位,补查前端工程代码 |

### 第三步:诊断(Diagnose)

**7 条分析原则(必须遵守)**:

1. 先还原事实,再下结论
2. 区分报错表象和真实根因 —— 超时 / 点击失败 / 接口报错 / 断言失败都是表象,不是根因
3. **回溯最早异常源**:读最新日志完整堆栈,定位**最早的异常来源**(不是最深/最后那个报错);长流程用例中,后段失败优先排查前段是否埋因(上游资源未就绪、异步未收敛、上一步污染)
4. 结合失败前后上下文 —— 前序步骤、资源变化、页面状态、异步收敛
5. 截图、DOM 与日志、代码交叉验证;冲突时以截图、DOM 和日志事实为准
6. 仅基于本次提供的材料分析,不假设未提供的信息
7. **检验隐含前提,不默认基础功能正常** —— 搜索/过滤/分页/表单提交等基础 UI 操作,"已生效"是需验证的假设而非默认前提(如搜索后结果集完全未变,根因可能是"搜索未生效",而非"目标不存在");证据不足时保留不确定性,但仍需给出当前最合理的单一主结论 + 置信度

**根因结论只能 3 选 1**:**环境问题** / **用例问题** / **产品缺陷**(遗留问题由本文第三节机制统一标记,不属于单次根因判定)

**判定纪律**:

- 判定为【用例问题】前,必须明确排除【产品缺陷】和【环境问题】并给出排除依据;严禁缺乏证据时默认归类为用例问题
- **后端取证(区分"产品缺陷 vs 用例问题"的通用动作)**:当 UI 现象疑似"操作成功但结果不对/状态不收敛/字段不一致",判定产品缺陷或用例问题前,应尽量用 `ssh_host.run("scli ...")` 或 `ssh_vm` 取后端真实状态作为交叉证据 —— UI 与后端均异常且非脚本/定位问题 → 产品缺陷;UI 异常但后端正常 → 多为用例问题(等待/定位/断言逻辑);证据不足且无法取证 → 保留不确定性,不默认归"用例问题"
- **配置类失败(502 / 无健康后端 / 连接被拒)判"产品缺陷"前,先核对需求显式配置项是否真落地(适用所有模块)**:当 SSH/curl 出现 502 Bad Gateway、无健康后端、连接被拒这类"后端不可达"失败时,判产品缺陷前**必须先回查**——需求里要求的关键配置项(尤其健康检查及其子字段:开关/类型/方法/URL 等)是否**真正配置成功**。核对方式(按可靠性优先)：① **导航回该资源(如资源池)的详情页/编辑页,实地读取该配置项的当前值,与需求逐项比对**——这是最可靠的核对方式;**注意失败时刻的 `dom_snapshots/<模块>/<测试名>/` 多半停在 curl/列表页、看不到很早之前的创建弹窗,故不能只依赖 domsnap**;② 若创建弹窗当时的 domsnap/截图恰好留有该字段渲染值,可作旁证。**只看"创建成功提示"不算数**(页面对象若用了"找不到就静默跳过"的 best-effort 写法,弹窗能成功关闭但字段根本没配上)。再排除"后端服务晚于资源创建启动、健康检查尚未恢复"的**时序因素**(可适当等待或在服务就绪后复测)。确认配置确已正确落地、后端直连可达、且非时序问题后,方可判产品缺陷;否则优先按用例/页面对象问题处理(参见阶段二编码规范"显式字段强制落地"一条)。
- 失败不稳定(首次和补跑现象不一致)→ 重跑 3 次,3 次中 ≥2 次通过则判定环境问题。**注意：经 run_guard 的每一次 pytest 都计入次数（含这类环境确认补跑）——run_guard 按真实日志机械计数、不区分"诊断重跑 vs 修复重跑"（见上「★ 计数口径」）；故仅在确有"首次失败、补跑又通过"的不稳定迹象时才补跑确认,不要无谓重跑白烧额度**
- 信息不足以形成明确假设时,**必须**补查 `sugon_web/refrence/` 前端工程代码:
  - 用 `Grep` 搜索失败现象中的关键文案(如未知中文字符串、状态值、按钮名称、错误信息文案)
  - 用 `Grep` 搜索失败用例涉及的资源类型/接口路径(如健康检查、监听器、成员状态判定逻辑)
  - **【工具使用·防 GBK 崩溃,2026-06-18 新增】查前端代码/看代码片段一律用 `Grep`/`Read` 工具,严禁用 `python -c "...print(...)"`、`type`、`cat` 打印代码内容来"看"**:Windows 下 Python 标准输出默认 GBK 编码,打印含 `\xa0`(不间断空格)/中文/特殊符号的前端代码会直接 `UnicodeEncodeError: 'gbk' codec can't encode` 崩溃、空转烧 token;看到该报错立即改用 `Read`/`Grep`,**不要纠缠 `encode`/`decode` 变体**(根因在输出流是 GBK,不在被打印的字符串)。
  - **未查证 → 不得判定为"用例问题"**(此为硬约束,与上一条排除依据要求联动)
- **证据优先级**:截图 / DOM 快照 > 日志 > 代码实现 > 推断

**Diagnose 输出格式**(简洁,4 节):

```
1. 结论:根因分类(环境/用例/产品) + 1~2 句摘要 + 置信度(高/中/低)
2. 关键证据:2~4 条,每条标注证据级别(截图/DOM 快照 > 日志 > 代码 > 推断)
3. 排除项:为什么不是其他两类(各 1 句,缺一不可)
4. 修复建议:短期 1~2 条可执行动作,必要时补 1 条长期建议
```

### 第四步:修复(Fix)

修复前回读 Diagnose 结论,确认改动与根因匹配;**再做一步"对照同模块已通过用例"**:找同模块/同类已通过的用例或 Page Object 方法作参照,完整读其定位/等待/断言写法,列出"待修复处与参照的差异",按参照风格修复,严禁自创一套与本模块不一致的写法;然后按下方决策树执行:

```
根因 = 用例问题 → 输出 2.3 节 7 项自检 checkbox(逐条勾选)
                  ├─ 任一项不通过 → 回 Diagnose
                  └─ 全部通过 → 按以下顺序定位修复点(只改第一个命中的):
                        ① 定位方式错误 → 修正 locator(优先 get_by_role / get_by_text(exact=True));
                           凭空定不准时先用 recon_page.py 运行时侦察或 Grep refrence/ 取证,严禁试错
                        ② 等待时机错误 → 用 wait_for_page_ready / wait_for_operation_complete / wait_for_source_complete
                        ③ 测试数据错误 → 用 random_data() 避免冲突;批量用 fixture 的 count 参数
                        ④ 业务流程偏差 → 按需求 MD 重新对齐测试步骤
                        ⑤ 其他(SSH 命令错误 / teardown ERROR / 资源依赖缺失等)→ 按 Diagnose 修复建议执行
                  修复后必须执行完整用例(不是只跑失败步骤),确保无回归
                  涉及断言改动时,必须按本步骤下方"断言差分自检"块对照修复前后断言强度

根因 = 产品缺陷 → 不修复代码,对话框醒目提示"**发现产品缺陷,请提交缺陷**"+ 复现步骤 + 关键日志 + 截图,继续执行其他用例

根因 = 环境问题 → 对话框记录"环境问题已跳过"+ 原因,继续执行其他用例;严禁修改脚本绕过(pytest.skip / try/except 吞错 / 注释步骤);**该用例不参与本阶段后续重跑**(含批量主因修复后的整体重跑),直到阶段五由稳定性验证机制重新触发
```

**断言差分自检(根因为用例问题且本轮修复触及断言时,必须输出)**:

```
【断言差分自检】
- 断言条数:修复前 N → 修复后 M(减少须说明理由)
- 是否把 == 改为 in / 改宽松匹配 / 删除断言 / 注释断言?  ___
- 是否把需求要求的**核心断言用 `if 条件` 跳过 / 提前 `return` / `try` 吞掉**,使其在某些运行下不执行?  ___（是 → 违规,见 2.2 速查表 #19；核心断言必须无条件执行）
- 是否降级了 P0/P1 断言(成功弹窗/存在性/状态收敛/末态字段)?  ___
任一为"是" → 必须给出"这是因产品行为真实变更(→ 产品缺陷)"的证据,否则视为违规修复,回 Diagnose
```

**Teardown 状态判定**(成功标准的一部分):

- **每次执行后必须主动扫描日志的 teardown/cleanup/fixture finalizer 段落**(`Grep` 日志中 teardown/清理/finalizer 关键字),如实记录 WARNING/ERROR,**不得只看测试步骤 PASSED 就判用例通过**。
- pytest PASSED 且 teardown 无 ERROR/WARNING → 用例通过
- pytest PASSED 但 teardown 有 ERROR → 视同用例问题,必须修复(按根因修清理逻辑,严禁删清理步骤或加 `|| true` 绕过)
- pytest PASSED 且 teardown 有 WARNING → 在问题清单中记录,不阻断本阶段完成

## 六、高成本用例的执行提效(诊断/修复重跑分离 + 分层执行)

> **背景**:复杂用例(如裸金属 BMS)单次成功执行的"产品侧固有等待"可达 70~100 分钟(PXE/发现/注册/就绪/清理等异步等待,不可压缩)。若每轮诊断和修复都全量重跑,会把固有等待乘以轮次,导致阶段三耗时数小时。本节用于在**不破坏任何修复纪律**的前提下,减少"全量长跑"的次数。

### 6.1 用例成本分级(进入阶段三时先做)

- 依据需求 MD 中各步骤的等待时长之和,粗判每个用例的单次墙钟成本。
- **低成本用例(单次 < 15min)**:维持现状,全量重跑最简单,不引入额外复杂度。
- **高成本用例(单次 > 15min)**:启用下方 6.2 的诊断/修复重跑分离与 6.3 分层手段。

### 6.2 诊断与修复"重跑分离"

- **诊断阶段不强制全量重跑**:Diagnose 优先基于已有证据(日志最早异常源 + 失败截图 + DOM 快照 + 后端 scli 取证)推理(见四步法 Reproduce/Diagnose);只有失败不稳定需确认环境问题时才补跑。
- **修复后才做一次完整用例验证**:避免"边猜边全量长跑";完整验证是判定通过的唯一依据。

### 6.3 缩短"复现到失败点"的分层手段(给方法,不强制)

对高成本用例,可用以下任一手段缩短定位时间,**必须遵守不破坏断言强度、不绕过步骤的红线**:

1. **就地复现优先用证据**:能从 DOM/截图/scli 后端确认根因的,不重跑。
2. **资源复用断点**:对前置资源已成功创建的情况,利用项目 fixture 作用域与 CSV"测试数据是否可复用"约定,在**调试期**复用已存在资源缩短前置;仅调试期,最终验证仍全量。
3. **分场景拆分**:一个 CSV 含多个可独立场景时,阶段二就按"数量对齐"产出多个 `def test_`,阶段三可用 `-k` **只重跑失败的那个测试方法**,而非整文件。

### 6.4 红线(硬约束)

- 分层/断点续跑**只用于"缩短定位时间"**;**最终判定该用例通过,必须是一次完整、未做任何调试期裁剪的执行**。
- **严禁**把"调试期跳过前置/复用资源"固化进脚本(命中 2.2 速查表第 5 项 / 第 15 项)。
