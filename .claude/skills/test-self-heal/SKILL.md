# 自愈式测试脚本维护 · 瘦编排 Skill（Orchestrator）

> **本文件为编排层（在主对话上下文运行，可用 `Agent` 工具派发子智能体）。**
> 它**只负责编排调度**：派发五个阶段子智能体、读运行报告状态、维护循环计数器、驱动跨阶段回退状态机、做全局总收尾。
> **它不亲自执行任何阶段任务、不改写任何阶段规范**——各阶段"执行什么、遵守什么规范"全部在对应子智能体文件内（其 body 已逐字内联本阶段全文规范）。
> 「长时间自主任务声明」「运行报告持久化与恢复协议」「工具调用约束」「完成后输出」「run_guard 机械熔断」等通用机制均承袭自经实战打磨的脚本开发编排层、逐字保留；**自愈差异**（4 分类分诊、前端变更对齐、产品缺陷醒目上报）见各阶段派发模板与子智能体正文。

## 长时间自主任务声明

本 SKILL 执行期间 **AI 全程自主运行**，严禁停下来询问用户，因为本任务设计为长时间自主运行，中途等待用户响应会中断自动化流程。所有修复/检查决策自主完成，仅在无法自主解决的阻塞性问题时允许暂停请求输入。任务从执行采集到稳定性验证可能持续数十分钟至数小时。

> **设计哲学**：给足修复机会，但绝不死磕；检测无意义循环，而非掐表计时。

> **停止口径（2026-06-17 团队决策）**：是否停止主要由"次数 + 进展"决定——单用例 40 次、全局 max(60, 失败用例数×10) 次、连续 15 次失败在同一位置冻结（详见下文「循环计数器持久化」；按失败位置而非报错文本判定，换报错文本骗不过）；并设**全局活跃墙钟硬上限**：自首次激活起累计**活跃**墙钟 > 10h 时，run_guard 直接**硬停**（退出码 3 拒绝下一次 pytest），强制收尾标"遗留·转人工"（活跃墙钟已扣除长空闲间隔，跨夜/中断恢复不会被秒杀）。即贯彻"检测无意义循环 + 绝不死磕"：每轮在推进就继续修，原地打转或墙钟过长就尽快交人，**不无脑长跑**。

## 运行报告持久化与恢复协议

为对抗上下文压缩导致前序阶段输出丢失，各阶段"立即输出"须在对话框输出的同时，双写到运行报告文件 `skill_runs/test-self-heal/test-self-heal_{任务标识}_{YYYYMMDD_HHMM}.md`（具体写入要求见各 phase 文件末尾"同步持久化"段）。全局规则：

- **任务标识与单文件**：任务标识统一取**本次自愈范围标识**（模块名，或目标测试文件名去 `.py`，如 `test_ecs_basic`），五个阶段一律以此为准，**不得中途改用别的名**（否则会导致 glob 匹配不到而分裂出第二个文件）。一次运行只用一个文件（放 `skill_runs/test-self-heal/`，严禁写入 `logs/`），由首个执行的阶段创建，其余阶段先 glob 找到该文件再在末尾追加（含回退轨迹），**严禁新建第二个文件、严禁覆盖前序内容**。
- **"追加写入"具体怎么操作（务必读准，防不知道用什么工具卡住）**：**优先用 `Bash`**（`cat >> <运行报告路径> <<'EOF' ... EOF` 或等效的 heredoc/追加重定向写法）把本阶段"立即输出"整段内容追加到文件末尾——这是最直接可靠的追加方式，**严禁用 `Write` 整体重写运行报告文件**（那等同于用新内容覆盖全文件，一旦生成内容遗漏或出错就会连带丢失前序阶段已写入的全部内容，是"严禁覆盖前序内容"这条硬约束最容易被无意违反的方式）。**没有 `Write`/`Bash` 权限的阶段**（如阶段二只有 `Edit`）：先 `Read` 运行报告取文件末尾若干行原文，用 `Edit` 以"文件末尾原文"为 `old_string`、"文件末尾原文 + 本阶段新增内容"为 `new_string` 做替换，效果等同于追加（`old_string` 必须逐字精确匹配已读到的原文，不得凭记忆手打）。
- **双写不替代**：严禁用写文件替代对话框输出，也严禁用对话框输出替代写文件。
- **压缩后续跑**：每阶段开始前先按 glob `skill_runs/test-self-heal/test-self-heal_{任务标识}_*.md` 取最新文件 `Read`，据此判断已完成到哪、从哪重入；任务标识统一从本次自愈范围标识推导，不靠对话记忆。
- **阶段闸门**：进入下一阶段前，须先 `Read` 运行报告文件 `skill_runs/test-self-heal/test-self-heal_{任务标识}_{YYYYMMDD_HHMM}.md` 确认上一阶段完成块已写入，缺失则先补写再继续。
- **各阶段报告必出区块清单**（压缩也带不走的硬清单；缺任一即视为该阶段未完成，必须补写）：
  - 阶段一：`## 阶段一…完成时间` + 范围基线区块 + 失败清单表（每个失败用例一条完整证据；失败≥3 含批量主因聚类）
  - 阶段二：`## 阶段二…完成时间` + 4 分类分诊表（分类+置信度+关键证据+排除项）+ **「疑似产品缺陷清单（需人工确认）」区块（无条件必出，`report_check.py` 强制校验；即使本次无产品缺陷，也要写出该标题并在表内写一行"本次未发现疑似产品缺陷"——机械保证产品缺陷永不被漏报，不是"有缺陷才出"）**
  - 阶段三：`## 阶段三…完成时间` + 完成清单表 + **问题清单**（文件:行 + 一句话改动 + 采用的前端对齐手段 + 修复前自检证据）+ **`Jenkins 对齐执行结果：{通过/未通过/未触发}` 行**（`report_check.py` 强制校验，保证"本地通过=Jenkins通过"）
  - 阶段四：`## 阶段四…完成时间` + 回归结果表 + 遗留问题清单 + **回归结果概览**（可自愈集合总数 / 已通过数 / 未通过数+nodeid / 待修集是否清空 / 判定去向——供编排层回退判定与阶段五前置守卫用）
  - 阶段五：`## 阶段五…完成时间` + 4.2 完成清单 + 4.3 问题总结 + **4.4 第一部分四张表（① Fixture ② Page Object ③ Helper ④ 断言复用/新增清单）+ 4.4 第二部分经验沉淀表**（最重、最易被压缩漏写，一表/一列都不能省）
  - 全局总结（面向人）：`## 完成后输出` + 1.总体结论 + 2.执行概览 + 3.风险与后续待办（**产品缺陷置顶醒目**）+ 4.产物位置索引 + 5.各阶段耗时统计（全局总览，不与各阶段明细重复）
- **落笔前就近重读 + 写后机器校验（强制，对抗压缩漏写/写简）**：每个阶段在生成"立即输出"前，先重新 `Read` 对应 phase 文件末尾的"立即输出"整节，按其确切表头逐项写全；写完后运行报告锚点校验脚本确认结构齐全：`python .claude/skills/test-self-heal/scripts/report_check.py <本次运行报告 md 路径> --phase <1/2/3/4/5/final>`，退出码非 0（缺锚点）→ 必须按提示补写后重跑，通过方可进入下一阶段或总收尾。
- **全局总结从文件聚合**：全部完成后的全局总结（总体结论/执行概览/风险待办/产物索引）须先 `Read` 报告文件后聚合，不依赖对话记忆。

## 五个阶段的执行编排（架构新增·派发与回退）

> **本节为架构新增**：本 Skill 是总控编排层，**自身不执行任何阶段任务**；各阶段的完整执行指令、规范、检查清单、完成时立即输出格式，全部**逐字内联**在对应子智能体文件 body 内（与原 skill `references/` 各 phase 文件逐字一致，已机器自证零差异）。本 Skill 只按顺序与回退状态机派发子智能体、读盘判进度、维护计数器。

### 阶段 → 子智能体映射

| 阶段 | 派发的子智能体（`Agent` 工具，按 name 显式派发） | 该阶段产出物 / 完成标志 |
|---|---|---|
| 阶段一：范围圈定 + 执行 + 失败采集 | `phase1-triage-capture` | 范围基线 + 失败清单（每个失败用例完整证据：日志/截图/DOM；失败≥3 含批量主因聚类） |
| 阶段二：4 分类分诊 + 前端对齐定位 | `phase2-diagnose-align` | 4 分类分诊表 + 可自愈集合 + 疑似产品缺陷清单（无条件必出，无缺陷写"本次未发现"） |
| 阶段三：前端变更对齐与自愈修复 | `phase3-self-heal-repair` | 源码级修复后的 `pages/**`、`test_*.py` + 修复方案（run_guard 机械熔断） |
| 阶段四：回归验证与自愈循环 | `phase4-regression-loop` | 回归结果 + 遗留清单（修复用例全过 / 达熔断上限） |
| 阶段五：稳定性验证与经验沉淀 | `phase5-stability-heal` | 稳定性结论 + 经验沉淀表（通过轮次达标且无未修复用例问题） |

### 指定入口执行部分阶段（入口路由）

> 除默认「完整自愈（从阶段一跑起）」外，用户可指定从某阶段进入（已有前序产出时省时）。**以指定阶段进入时，编排层先按运行报告 glob 校验其前置区块是否齐备：齐备 → 直接从该阶段执行；不齐备 → 自动回填最近缺失的前置阶段后再继续（全程不询问用户）。** 这与「压缩/中断恢复」共用同一套"读盘判进度"机制。
>
> **★ 回填是链式/递归的，不是只退一步（务必读准，防"回退一步就派发、下一步又卡住"）**：下表"前置缺失处理"列写的是"缺 X 区块 → 回填 Y 阶段"，这只是**单步**描述；若从较靠后的入口（如 `stabilize`）进入一个**完全空白的全新任务**（无任何运行报告），需要**递归**一路回填到链条最早缺失的起点：阶段五缺「回归结果」→ 阶段四缺「修复方案」→ 阶段三缺「分诊」→ 阶段二缺「失败清单」→ 最终从**阶段一**开始按 `full` 顺序正常跑起，一步步补齐后再回到用户指定的入口阶段。**编排层每派发一步前都要重新 glob+Read 运行报告确认该步前置是否已齐备，不齐备就继续往更早的阶段回填，直至找到"前置已齐备"的第一个可执行阶段再开始派发**——严禁只回退一步就直接派发（那一步大概率仍会因缺更早前置而卡住/幻觉产出）。

| 入口 | 场景 | 起始阶段 | 前置缺失处理（自动回填、不问用户） |
|---|---|---|---|
| `full`（默认） | 完整自愈 | 阶段一 | 无 |
| `diagnose` | 已有失败清单，只分诊 | 阶段二 | 缺「失败清单」区块 → 先补阶段一 |
| `repair` | 已有分诊，只修复 | 阶段三 | 缺「分诊」区块 → 先补阶段二 |
| `regress` | 已修复，只回归 | 阶段四 | 缺「修复方案」区块 → 回阶段三 |
| `stabilize` | 只稳定性 + 出报告 | 阶段五 | 缺「回归结果」区块 → 回阶段四 |

### 派发机制（架构新增，官方依据：Invoke subagents explicitly）

- 本 Skill 用 **`Agent` 工具按 `name` 显式派发**对应阶段子智能体（`Task` 自 v2.1.63 起更名 `Agent`，`Task` 仍为别名）。

> **★ 强制派发铁律（最高优先级，对抗"在主会话偷懒直接干"）：**
> 1. **阶段二、阶段三、阶段四、阶段五，必须通过 `Agent` 工具派发对应子智能体（`phase2-diagnose-align` / `phase3-self-heal-repair` / `phase4-regression-loop` / `phase5-stability-heal`）在其独立 fresh-context 中执行**。
>    - **阶段三为无条件强制派发（最易失控，特别加硬）**：无论用例成本高低、无论是否预期首轮即过，只要进入阶段三就必须派发 `phase3-self-heal-repair`，**严禁编排层主会话"先直接跑一次 pytest 试试"再决定是否派发**——首轮即过是小概率，实测绝大多数用例都需多轮修复，主会话试跑会污染编排上下文、丢失"旁观监督"，是阶段三失控的根源。
> 2. **严禁本 Skill（编排层主会话）亲自编写测试脚本/页面对象、亲自跑 pytest、亲自做根因分析与修复、亲自做日志核查与稳定性多轮执行**——这些是子智能体的职责。编排层只派发、读盘、读一句话状态、维护计数、驱动回退。
> 3. 阶段一按成本分级**允许**编排层主上下文直跑（上下文轻）；但**一旦阶段一进入需多轮校验/或你判断其上下文将膨胀，也应派发 `phase1-triage-capture`**。除阶段一这一例外，**其余阶段不得在主会话内直接执行**。
> 4. **回退循环同样适用**：阶段四/五回退到阶段三时，**必须重新 `Agent` 派发 `phase3-self-heal-repair`**（再派发 `phase4-regression-loop`/`phase5-stability-heal`），**严禁在主会话里直接修复**。每一次回退重入都要重新派发，不得图省事在主会话内改。
> 5. 若发现自己（编排层）已经开始直接读被测前端代码、直接写 `test_*.py`、或直接执行 `pytest`——**立即停止，改为派发对应子智能体**。这是判断"是否违规偷懒"的硬信号。

- 派发的任务 prompt 中**只写指针型输入 + 该阶段最关键的 1-2 条硬约束**（规范全文已在子智能体 body，此处不重述全文；但把"最易被忽视、后果最重"的硬约束 **front-load 进派发首条消息**，因为那是子智能体 fresh context 里最先读到、显著性最高的位置）：
  - 本次任务标识（= 自愈范围标识：模块名 / 目标测试文件名去 `.py`）；
  - 运行报告文件路径（按上文 glob 取最新）；
  - 若为回退重入：从运行报告「循环计数区」取出的"待处理问题清单 + 当前循环计数"。
  - **派发文本一律照搬下文「各阶段派发 prompt 模板」**（见本节末），按模板填 `<占位符>`，**禁止自由发挥、禁止删改"首要任务/关联文件必读/硬约束/收尾"任一段**——这是防止"派发时随手写、漏掉关键规范与必读文件"的根本办法。
- **子智能体须前台执行**（不放后台：后台子智能体会自动拒绝需授权的工具调用，导致 `Bash`/写盘被静默拒绝）。
- 子智能体完成后**只回一句话状态**（明细已写运行报告）；本 Skill 只读该状态 + 读运行报告锚点，决定下一步。
- 用户只需触发本 Skill（`/test-self-heal` 或描述匹配自动唤起），**派发由本 Skill 自动完成，用户不必手动逐个 @ 子智能体**。

### 各阶段派发 prompt 模板（强制·照搬填空）

> 回退**语义**完全沿用原 skill（阶段四"重要问题须返回阶段三修复"；阶段五"失败轮次含用例问题→返回阶段三修复，重新执行阶段四、阶段五，同一根因的用例问题最多修复 8 次"）。本节只把语义搬到编排层驱动，语义本身不改。

```
[阶段一] →done→ [阶段二] →done→ [阶段三] →done→ [阶段四]
                                                    │
                          重要问题/teardown ERROR    │ 仅非重要问题
                                ┌───────────────────┴──────────┐
                                ▼                              ▼
                          [回退阶段三]                      [阶段五]
                          (按计数器约束)                       │
                                │                   失败轮次含用例问题
                                └──────┐          ┌────────────┘
                                       ▼          ▼
                                  重新跑 [阶段四]→[阶段五]
                                       (按"同一根因最多修复 8 次"约束)
                                          │
                                   达标/缺陷/环境 → [总收尾]
```

- 阶段四 `phase4-regression-loop` 判需回退（重要问题/teardown ERROR）→ **先跑下方「回退派发硬闸门」`loop_gate.py`（带 `--case`），退出码 0 才**派发回退，去向二选一（由阶段四在其「回归结果概览·判定去向」写明、编排层照此派发）：**① 默认·回阶段三继续修** → 派发 `phase3-self-heal-repair`（回退重入）→ 再派发 `phase4-regression-loop` → ……；**② 疑似根因分类判错时（如同一处反复修仍失败/后端取证显示疑似产品缺陷或环境问题）·回阶段二重新分诊** → 派发 `phase2-diagnose-align` → 阶段三 → 阶段四。（退出码非 0 按闸门规则标记遗留问题并停止；上方 ASCII 图为默认路径①的简化示意，路径②为其分支）
- 阶段五 `phase5-stability-heal` 返回"返回阶段三修复"（失败轮次含用例问题）→ 同上（闸门带 `--case --rootcause`），并受"同一根因最多修复 8 次"约束；超过则按原文标记遗留问题并结束。

### 循环计数器持久化（架构新增）

因子智能体无状态、每次全新记不住轮次，下列计数机制的"当前值"由本 Skill 落盘到运行报告**「循环计数区」**（架构新增的一个区块），每次派发回退前先读、派发后更新。**阈值口径（2026-06-17 按团队决策调整为下表，统一以 `run_guard.py` 常量与本表为准；`run_guard.py` / `loop_gate.py` / phase3 正文三处必须保持一致）**：

| 计数器 | 上限 |
|---|---|
| 单用例次数（= 一个失败的 `def test_` 方法，用 -k 单独跑） | **40 次**（口径：1 次 pytest = 1 次） |
| 全局次数 | **max(60, 失败用例数 × 10)**（如本次要修 8 个失败用例→80） |
| 状态冻结检测（零前进） | **连续 15 次失败在同一位置**（同一测试 nodeid + 同一处最深用户代码 file:line，与报错文本是否变化无关；只有推进到新失败位置/通过才清零） |
| 阶段五回退同一根因修复次数 | 最多 8 次 |
| 全局活跃墙钟硬上限 | 自首次激活起累计**活跃**墙钟 **> 10h** → run_guard 硬停（退出码 3 拒绝、强制收尾标"遗留·转人工"；活跃墙钟已扣除长空闲间隔，跨夜/中断恢复不秒杀） |

> **"单用例"的明确定义（务必让子智能体读懂，避免理解错而产生幻觉）**：这里的"单用例"指**测试脚本里的一个 `def test_` 方法**（用 `-k` 单独跑时）。所以"单用例 40 次" = "每个失败的 `def test_` 方法最多跑 40 次 pytest"。它**不是**指整个 `.py` 脚本文件（一个 `.py` 通常含多个 `def test_` 方法），也**不是**指一次 pytest 命令。
> **★ `--cases` 口径（自愈专属，务必读准、防幻觉）**：自愈里 `run_guard --cases` 传的是**本次要修的失败用例数**（= 阶段二圈定的"可自愈集合"里的 `def test_` 方法数），它只决定**全局次数上限**的缩放 `max(60, 失败用例数×10)`，**与单用例 40 次上限无关**。例：本次可自愈集合有 6 个失败用例 → `--cases 6` → 全局上限 = max(60, 6×10) = 60。**自愈没有 CSV / 需求转换环节，绝不要按"CSV 失败用例数"去理解 `--cases`。**

> **状态冻结(15) 与 阶段五同根因(8) 不要混淆**：① **状态冻结的 15**（见 phase3 §3.3）= 在阶段三修复循环里，同一用例**连续 15 次失败在同一位置**就停（机械判定，由 `run_guard.py` 按「失败测试 nodeid + 最深用户代码 file:line」做指纹比对，**与报错文本是否变化无关**；只有推进到新失败位置/通过才清零——换 selector 让报错文本变一变骗不过它，这正是把单用例额度全卡在同一步的关键）；② **阶段五回退同一根因的 8** = 用例在阶段五稳定性验证不通过、**被退回阶段三重修**时，针对**同一个根因**最多来回修 8 次（2026-06-18 由 5 放宽到 8，给偶发/复合根因更多收敛机会）。两者发生的阶段不同、机制不同、互不相关。

> **口径说明（2026-06-17）**：计数极简为"1 次 pytest = 1 次"，不区分"改了代码 vs 诊断重跑"；**全局活跃墙钟硬上限 10h（超过 run_guard 直接硬停·退出码 3 拒绝，已扣除长空闲间隔；2026-06-21 由原 6h 软兜底改为 10h 硬停——软兜底无约束力、实测被无视跑满 7h+）**。`run_guard --reset` 后的绕过审计**只统计本次 reset 之后产生的日志**，阶段二试跑/上一次任务残留的旧日志不再被算进本次额度。**回退重入必须用 `--reset --reentry`：不清零累计全局、只给本用例新预算 + 小额回退预算（+10），杜绝"每次回退拿全新预算→无限续命"。**

达上限 → 标记"遗留问题"并停止回退；未达 → 派发并在子智能体完成后更新计数。

#### 计数区结构（架构新增，供闸门脚本读取）

「循环计数区」须以下列**结构化块**形式落盘在运行报告中（每轮修复后由本 Skill 同步更新当前值，**抗压缩：只认磁盘文件、不靠对话记忆**）。`global_fix_rounds` 始终存在；用例相关计数按用例名各占一行；阶段五回退时补 `heal_same_rootcause` 行。"上限"列写入**生效阈值**：`global_fix_rounds` 上限 = `max(60, 失败用例数 × 10)`（与 `run_guard --cases` 同口径，下限 60）；单用例 `case_fix_rounds` 写 40；`freeze_same_rounds` 写 15；`heal_same_rootcause` 写 8：

> **`<根因标识>` 生成规则（务必读准，防"同根因被拆散计数、8 次上限形同虚设"）**：标识 = **`{失败用例 nodeid}::{根因分类子类型}`**（如 `test_xxx.py::TestX::test_y::用例问题-定位错误`），**不得用自由描述性文字**。同一用例同一子类型根因的历次回退必须复用**完全相同**的标识字符串（照抄计数区里该行已有的值，不重新编词），否则每次措辞略有不同就会被当成新根因、8 次上限被架空。诊断出的子类型变了才算新根因、开新行，不与旧标识合并。详见 `phase5-stability-heal.md` 正文「根因标识生成规则」。
>
> **`case_fix_rounds`/`freeze_same_rounds` 的"标识"列格式（防同名方法混计数）**：填**完整用例 nodeid**（`test_文件.py::TestX::test_方法名`，如 `test_lbv2.py::TestLb::test_create`），**不要只填裸方法名**——若同一次任务里两个不同测试文件恰好有同名方法（如两个文件都叫 `test_create`），只填裸方法名会把两个不同用例的计数误记到同一行。下表示例为求简写用 `test_xxx`，实际填表须写全 nodeid。

```
<!-- LOOP_COUNTER_BLOCK_START -->
| 计数项 | 标识 | 当前值 | 上限 |
|---|---|---|---|
| global_fix_rounds |  | 0 | 80 |
| case_fix_rounds | test_xxx | 0 | 40 |
| freeze_same_rounds | test_xxx | 0 | 15 |
| heal_same_rootcause | <根因标识> | 0 | 8 |
<!-- LOOP_COUNTER_BLOCK_END -->
```
（上例 `global` 上限 80 = 8 失败用例×10；2 失败用例则为 max(60,20)=60；1 失败用例为下限 60。这里的"计数项"沿用 `global_fix_rounds`/`case_fix_rounds` 等历史字段名，含义即"次数"，1 次 pytest = 1 次。**回退重入时 `global_fix_rounds` 当前值不清零、跨回退累加；run_guard 侧的全局上限按 `--reentry` 设为"当前全局累计位置 +10"（幂等，重复 reset 不叠加）。**）

> **★ 计数以 run_guard 状态 JSON 为唯一权威、全局只允许一个计数块（2026-06-29 新增·治"报告计数失真/自相矛盾"）**：
> - **唯一权威**：`global_fix_rounds` 的当前值/上限**必须取 `skill_runs/test-self-heal/_runguard_<task>.json` 里的 `global_runs` / `cap_global` 为准**，严禁按各阶段块叙述的次数自行累加（实测出现过报告写"27+7=34"而真实 `global_runs=61`，差一倍、并误导停止判断）。
> - **全局唯一块**：整份运行报告**自始至终只维护这一个 `LOOP_COUNTER_BLOCK`**（编排层那个，`loop_gate.py` 只读第一个）；回退重入时**只更新它的当前值，严禁再新增第二个 `LOOP_COUNTER_BLOCK`**（实测出现过第二块写 8/61、与第一块 61/61 自相矛盾）。
> - 阶段三正文里的 `计数区` YAML 仅供人读；**一切机读判断（loop_gate / 总收尾）一律以本块 + run_guard JSON 为准**。

#### 回退派发硬闸门（架构新增·把"停止条件"从软约束升级为硬控制）

> **动机**：上表阈值原本写在子智能体正文里、靠其自觉遵守（软约束），弱模型长跑会无视上限继续试错（实测出现过阶段三多轮失控）。现把"要不要再来一轮"的决定权收回到**编排层**，用确定性脚本退出码强制裁决。**阈值与判定语义零改动**，闸门只是机器化地比对上表既有阈值。

- **每次准备回退派发 `phase3-self-heal-repair`（或阶段五回退重入）之前，编排层必须先跑闸门脚本**：
  `python .claude/skills/test-self-heal/scripts/loop_gate.py <本次运行报告 md 路径> [--case <用例名>] [--rootcause <根因标识>]`

  - `1` → **禁止派发**：编排层立即按原文规则把对应用例/分支标记为"遗留问题（轮次耗尽 / 状态冻结 / 同根因超限 / 全局总时长超限）"，停止该回退分支，**严禁再派发**。

### 全局端到端总时长闸（架构新增·2026-06-29·治"整套跑十几小时仍不收"）

> **动机**：run_guard 的 10h 活跃墙钟**只覆盖阶段三**，且对**阶段五裸跑那几小时不可见**（run_guard 未被调用、会误记为空闲），存在盲区——实测整套曾连续跑约 12h、跨度近 15h 仍未收尾。故在编排层加一道**独立于 run_guard、按真实墙钟计**的全局总时长闸。

- **编排层每次准备派发任一子智能体前，先算端到端已耗时** = 当前系统时间 − 运行报告头「运行开始时间」（用 git-bash `date "+%Y-%m-%d %H:%M:%S"` 取当前时间，编排层本就每次派发前读运行报告，顺带算即可）。
- **一旦端到端已耗时 ≥ 全局总时长上限（默认 12 小时）→ 立即停止派发**：把未完成 / 未通过的用例标记为"遗留问题·转人工"，跳转「完成后输出」做总收尾，**严禁再派发任何子智能体（含回退重入）**。
- **机械兜底（2026-06-29 新增·治"弱模型不自觉算时间"）**：`loop_gate.py` 已内置同一道时长闸——每次回退派发前跑 `loop_gate.py` 时，它会读运行报告头「运行开始时间」按真实墙钟算端到端耗时，**≥ 默认 12h（可用 `--deadline-hours` 调整）即走退出码 1、禁止再回退**；解析不到「运行开始时间」则自动跳过该闸、不误杀。即编排层即便忘了手动算，**回退这个咽喉点也会被 loop_gate 机械拦住**（前向 1→2→3→4→5 不过 loop_gate，仍靠上面的编排层自查兜，但时间累积主要发生在回退循环）。
- 该闸**与 run_guard 的 10h 活跃墙钟、loop_gate 的次数闸彼此独立、谁先到谁先停**；它用真实墙钟兜住"整套流程总时长"（含跨夜/空闲——对无人值守自动跑，超长本就是要兜住的对象）。若确需更长预算，由人工确认后调整该上限。

### 按成本分级的隔离策略（架构新增，防"过度设计反而变慢"；成本口径原文沿用：低成本<15min / 高成本>15min）

| 场景 | 是否开独立子智能体 |
|---|---|
| 阶段一（上下文轻） | 可不隔离，本 Skill 主上下文直跑（仍须完整读 `phase1-triage-capture` body 原文执行） |
| 阶段二 | 隔离（派发 `phase2-diagnose-align`） |
| 阶段三（无论成本高低 / 是否首轮即过） | **一律隔离派发 `phase3-self-heal-repair`，无例外**：高成本用例 / 进入多轮修复时**每用例一个 `phase3-self-heal-repair` 子智能体**（本 Skill 遍历用例，子智能体内部不再派 subagent） |

## 工具调用约束

修改测试脚本时，若 `Edit` 因 `old_string` 不唯一失败，严禁中断流程等待人工确认。按以下优先级自动恢复：

1. **扩大匹配范围**：立即 `Read` 文件，增加 surrounding 函数体或相邻注释使 `old_string` 唯一
2. **使用 replace_all**：确认所有匹配处需相同修改时，改用 `replace_all=true`
3. **替代方案**：上述方法均不可行时，改用 `Write` 重写整个文件

`Edit` 和 `replace_all` 均失败时，必须使用 `Write` 作为最终降级方案；仅当 `Write` 也失败时，记录错误并继续下一步。严禁弹出确认对话框。

### Shell 命令执行约束（强制·防 `cd /d` 报错空转，2026-06-18 新增）

> **背景**：Claude Code 实际通过 **bash（`/usr/bin/bash`，Windows 上是 git-bash）** 执行命令，**不是 CMD**。实测出现过：模型因系统是 Windows 就给命令加 CMD 风格前缀 `cd /d "路径" && python ...`，bash 不认 `/d` → 报 `cd: too many arguments`（退出码 2）→ `&&` 后的 `python run_guard.py` 根本没执行 → 模型又原样重发同一条坏命令、循环空转一个多小时、狂烧 token。

1. **命令一律在仓库根目录、用 bash 执行**：本文所有 `python .claude/skills/.../*.py ...`、`pytest ...` 命令都假定当前工作目录＝仓库根目录、用相对路径，**直接原样运行即可**。
2. **严禁给命令加 `cd` / `cd /d` 前缀**：默认就在仓库根目录，无需切目录；**`cd /d` 是 CMD 语法，在 bash 里必然报 `cd: too many arguments`**。万一确需切目录，只用 bash 语法 `cd "路径"`（**绝不带 `/d`**）。
3. **反循环硬规则（防空转烧 token）**：**同一条命令连续 2 次返回相同报错 → 立即停止"原样重发"**，先诊断命令本身（语法 / 路径 / 工作目录），改对了再发：
   - 看到 `cd: too many arguments` → 你在 bash 里用了 CMD 的 `cd /d`；**去掉整个 `cd ... &&` 前缀**，直接跑后面的 `python`/`pytest` 命令。
   - 看到 `No such file or directory` / 路径找不到 → 确认是否用了正确的仓库相对路径，而不是去 `cd` 到绝对路径。
   - 报错与 run_guard 的"守卫拒绝(退出码 3)"无关时，**不要把 shell/语法错误误判为产品缺陷或环境问题、更不要反复改测试代码**。
4. **只用脚本真实支持的参数**：调 `run_guard.py` 只用 `--reset` / `--reentry` / `--task` / `--cases` / `--release` / `-- pytest ...`（见脚本 `--help`）；**严禁臆造不存在的参数**（如 `--status`），那会被 argparse 当成 pytest 参数误跑、白白消耗一次额度。要查进度就 `Read` 运行报告 + run_guard state 文件，不要靠臆造命令试探。
5. **严禁用 `python -c "...print(...)"`（或 `type`/`cat`）打印文件内容/前端代码片段来"看代码"（防 GBK 编码崩溃空转，2026-06-18 新增）**：要读文件内容一律用 `Read` 工具、要搜内容用 `Grep`/搜索工具——这既是正道，也避开一个实测高发坑：**Windows 下 Python 标准输出默认是 GBK(cp936) 编码，`print` 含 `\xa0`(不间断空格)、中文、特殊符号的前端代码/文案时会直接 `UnicodeEncodeError: 'gbk' codec can't encode character`、命令崩溃**（实测模型为此反复改 `encode('utf-8')`/`decode` 仍失败、空转烧 token——根因在"输出流是 GBK"，不在被打印的字符串）。
   - 看到 `UnicodeEncodeError: 'gbk' codec can't encode ...` → **立即停手，不要再试 encode/decode 变体、不要原样重发**，改用 `Read` 工具读该文件即可。
   - 万一确有必要用 python 处理并打印含中文/特殊字符的内容：用 bash 语法前置环境变量 `PYTHONIOENCODING=utf-8 python -c "..."`，或脚本内先 `import sys; sys.stdout.reconfigure(encoding="utf-8")`。（本 skill 自带的 `precheck.py`/`report_check.py`/`run_guard.py` 已内置该保护，直接调用不受影响。）

6. **全程禁止执行任何 `git` 命令（强制，2026-06-19 新增）**：本工作流执行期间**严禁运行任何 git 命令**（`git checkout` / `git reset` / `git clean` / `git add` / `git commit` / `git push` / `git pull` / `git stash` / `git restore` 等一律不准）——既不准用 git"绕过失败 / 撤销本应做的修改"，也不准用 git"恢复误删"。**若不慎误删 / 误覆盖了已有测试用例（或任何文件）：立即停止当前任务，在对话框醒目提示用户"误删了什么文件、原状如何、需人工从版本库/备份恢复"，然后等待用户处理——绝不自行用 git 或其它方式补救、绝不继续往下执行。**（注：`run_guard.py`/`precheck.py` 等脚本内部对 git 的【只读】查询是脚本自身行为、与本条无关，你不需要也不应主动敲 git。）

### 子智能体被中断 / 状态不明时的编排处理（强制）

阶段三等子智能体若被用户中断、或你无法确认它是否还在跑：**不要慌乱试探、不要臆造命令、不要在主会话直接接管修复**。按序处理：① `Read` 最新运行报告 + `skill_runs/test-self-heal/_runguard_<任务标识>.json` 判断已完成到哪、计数到几；② 确认无残留 pytest 进程后，需要重入阶段三就规规矩矩 `run_guard.py --reset --reentry --task <标识> --cases <失败用例数>`（**不带任何 `cd` 前缀**）再重新 `Agent` 派发 `phase3-self-heal-repair`；③ 仍无法判断则停下、如实向用户说明状态,不空转重试。
