## 一、4 分类总览

| 分类 | 一句话定义 | 是否进自愈 | 后续动作 |
|---|---|---|---|
| 前端变更（UI drift） | Page Object 固化的文案/结构与最新前端代码不一致 | ✅ 是 | 阶段三「前端对齐」修复 |
| 用例问题 | 脚本自身缺陷（等待/数据/顺序/断言逻辑），与前端真相无关 | ✅ 是 | 阶段三按定位顺序修复 |
| 环境问题 | 环境不稳定/资源不足/服务未就绪/网络抖动 | ❌ 否 | 记录跳过，不改脚本 |
| 产品缺陷 | 被测系统功能异常/接口错误/状态机不符预期/UI 与后端不一致 | ❌ 否 | 记录上报缺陷 |

判定为「用例问题」或「前端变更」前，**必须明确排除「环境问题」和「产品缺陷」并给排除依据**。

## 二、前端变更（UI drift）判据

**这是本 skill 的主战场，也是 4 分类中相对"纯脚本失败分析"新增的一类。** 满足以下「现象 + 证据」组合即判定：

**现象特征**（任一）：

- 定位失败：`TimeoutError`/`element not found`/`.count()==0`，目标元素曾经能定位到。
- 文案不匹配：`get_by_text`/`get_by_role(name=...)` 的预期文案在页面找不到，但页面有语义相近的新文案。
- 控件类型变化：原 `button` 变成 `a`/`div[role=button]`，原下拉变成搜索框等。
- 字段名变化：表单 label / 表格列名 / 详情字段名变了。
- 流程步骤增减：弹窗多了一步确认、少了一个步骤、操作入口移动到别处。

**佐证证据（必须）**：用 `Grep` 在 `sugon_web/refrence/{版本}/{module}/` 前端工程代码中搜索：

- 搜旧文案/旧字段名 → 命中很少或为 0，且能搜到语义相近的**新文案/新字段**。
- 搜失败用例涉及的组件/接口路径 → 发现组件结构、按钮渲染、状态判定逻辑已变。
- 对比截图/DOM 的真实渲染态，与 Page Object 里固化的定位不一致。

**判定话术**：「Page Object `xxx.py:第N行` 固化文案/定位 `旧值`，前端工程 `组件路径` 已改为 `新值`（Grep 证据），故为前端变更。」

> **未 `Grep refrence/` 查证，不得判前端变更**（硬约束）。

## 三、用例问题判据

脚本自身缺陷，与前端真相无关。常见子类型：

- **等待时机**：异步未收敛就断言/操作（状态还在「创建中」就断言「可用」），缺收敛点等待。
- **数据冲突**：资源名写死导致重名冲突，未用 `random_data()`；批量未用 fixture 的 count。
- **依赖顺序**：前置资源未就绪就操作、清理顺序错误、上游用例污染。
- **断言逻辑错误**：写死动态期望值、断言对象错。
- **清理不彻底**：teardown 未覆盖所创建资源。

**判定纪律**：必须先排除「前端变更」（`Grep` 前端代码确认定位/文案**没变**）、排除环境与产品缺陷，方可判用例问题。

## 四、环境问题判据

- 现象：失败不稳定（首次失败、补跑通过）；报错指向网络抖动、服务 503/超时、资源不足、节点未就绪、SSH 连接失败。
- **确认手段**：重跑 3 次，≥2 次通过 → 判环境问题（重跑是诊断动作，不计修复轮次）。
- **核心原则**：环境问题只在分诊阶段标记，**严禁改脚本绕过**（不得 `pytest.skip`、不得 `try/except` 吞错、不得注释步骤）。

## 五、产品缺陷判据

- 现象：操作成功但后端状态不符预期；接口返回错误码；UI 显示与后端数据不一致；状态机卡死。
- **确认手段（关键）**：通过 SSH 后端验证 —— `ssh_host.run("scli ...")` 查资源真实状态，或 `ssh_vm` 连虚机查实际效果。若 UI 与后端均异常、且非脚本/前端定位问题 → 产品缺陷。
- **动作**：不改脚本，醒目提示「发现产品缺陷，请提交缺陷」+ 复现步骤 + 关键日志 + 截图，继续处理其他用例。

## 六、按错误类型的隔离动作速查

按错误类型只执行对应动作，不要全部执行：

| 错误类型 | 隔离动作 |
|---|---|
| TimeoutError | 检查是否在 `wait_for_load_state('networkidle')` 前操作；用 `.count()` 验证命中数；查异步未完成；**Grep 前端代码确认定位是否变化**（区分前端变更 vs 等待时机） |
| AssertionError | 对比预期值与实际值，辨别「数据被污染」「断言逻辑错误」「产品行为变化」 |
| 定位类错误 | 用 recon 脚本/DOM 列出页面实际匹配元素对比文本；确认是否在正确 dialog/tab/表格/行范围；**Grep 前端代码**判断是否前端变更 |
| SSH 连接错误 | 检查命令语法、目标节点可达性、资源是否已创建；核对命令转换是否正确（多为环境或用例问题） |
| 其他（仅前 4 类不匹配时） | 检查环境状态；仍不能定位则补查前端工程代码 |

## 七、排除法模板

每个用例的「排除项」必须逐类各 1 句、缺一不可：

```
- 非环境问题：因 {首次与补跑现象一致/无网络服务异常证据}
- 非产品缺陷：因 {SSH 后端状态正常/无接口错误}
- 非用例问题：因 {Grep 前端代码证实定位/文案确实变化}（判前端变更时）
  或
- 非前端变更：因 {Grep 前端代码证实定位/文案未变}（判用例问题时）
```

## 八、本项目特有的高发场景

- **异步中间态**：ECS/EVS 创建删除、快照还原、备份任务、SLB 状态收敛存在中间态，未等收敛就断言极易误判 —— 优先怀疑「等待时机」类用例问题，而非前端变更。
- **登录态与导航**：`page` fixture 自动登录并 `close_dialog_if_exists()`；`@submenu` 报错通常是抽屉遮挡/导航异常（环境问题），不要动装饰器。
- **跨用例污染**：`browser_context` 是 class 级复用登录态，上游用例若改了全局状态可能污染下游 —— 批量失败时用二分思路定位污染源。
- **SSH 后端验证**：是区分「产品缺陷」与「用例问题」的关键手段，判产品缺陷前尽量用 `ssh_host`/`ssh_vm` 取证。
