# 修复规则手册（repair-rules）

> **阶段三**（`phase3-self-heal-repair`）自愈修复时的硬约束（阶段四 `phase4-regression-loop` 只做回归核查/日志分析，不改代码，故不适用本文件）。做任何修改前必读，并在每轮修复反馈中完整输出「修复前自检」全部勾选项。

## 一、修复纪律

- 严禁盲目修改代码 —— 盲目修改会引入回归或掩盖真实根因。
- **「快速让测试通过」不是目标，「按根因正确修复」才是目标** —— 任何为让本轮 PASSED 而绕过根因的动作都是错误修复。
- **修复必须以最新前端工程代码 / 运行时真实渲染态为依据**（前端变更类），或以阶段二分诊结论为依据（用例问题类）；禁止凭空改定位。
- **源码级治本**：修复写回 `pages/**`/`test_*.py` 源码并经回归/稳定性验证，**禁止**运行时临时打补丁。

## 二、❌ 错误修复模式速查表（命中任一项 → 立即停止，回阶段二 Diagnose）

| # | 错误修复模式 | 正确做法 |
|---|---|---|
| 1 | 跳过根因分析直接调代码让测试过 | 先完成阶段二分诊，再按根因修复 |
| 2 | 用 `try/except` 兜底吞错让用例继续 | 让真实异常抛出，修复实际问题 |
| 3 | 加 `page.wait_for_timeout(N)` 固定等待绕过超时 | 用 `wait_for_page_ready()`/`wait_for_operation_complete()`/`wait_for_source_complete()` 收敛点 |
| 4 | 把断言「等于」改「包含」、删除断言、放宽预期 | 保持原断言强度；若产品行为改变 → 产品缺陷 |
| 5 | 用 `pytest.skip()`/`@pytest.mark.skip`/注释失败步骤 | 环境问题在分诊阶段标记，不改脚本 |
| 6 | 改 `pages/` 已有公共方法定位逻辑去绕过页面对象缺陷 | 前端变更则按真相对齐；页面对象缺陷记录提请处理 |
| 7 | 改需求 MD/脚本中端口/协议/权重/URL 等业务参数让脚本通过 | 业务参数偏差是产品缺陷或环境问题，不是改脚本/MD 的理由 |
| 8 | 移除 `@submenu` 等装饰器以「消除报错」 | 装饰器报错通常是环境问题（抽屉遮挡/导航异常），修环境不动装饰器 |
| 9 | 测试层引入 `locator()`/`expect()`/XPath | 必须通过 Page Object 封装方法调用 |
| 10 | 测试主流程加 `try/finally` 包裹核心步骤 | 用 fixture 的 yield 机制管理清理 |
| 11 | 忽视 teardown 阶段 ERROR | teardown ERROR 视同用例问题必须修；WARNING 必须记录 |
| 12 | 用 `\|\| true`/`echo $?` 掩盖 SSH 命令失败 | 必须断言 `rc` 和 `stdout` |
| 13 | 凭空构造新定位（未经前端代码/渲染态佐证） | 必须以 Grep 前端代码或 recon 渲染态为依据 |
| 14 | 把前端「流程重构」当普通定位改，反复改 locator | 识别为流程重构 → 结合需求 MD 重新对齐步骤 |
| 15 | 改/新增 Page Object 方法时，对脚本原有断言依赖的必填字段用 `if locator.count() > 0: 填 否则什么都不做` 静默跳过、或用方法内部默认值替代原字段值 | **必须 fail-loud**：直接调用 `.fill()`/`.click()`/点选项，不包 `if ...count()>0` 守卫——Playwright 找不到元素会自动超时抛错，问题当场暴露；`best-effort`（`if count()>0` 才操作）仅允许用于确实可选/纯探测的操作（如"有则关掉残留弹窗"），绝不能用于原脚本/需求 MD 显式要求的必填字段 |

> 表里没有的变体按本表精神识别（如 `if not exist: 补创建` 是第 5 项变体）。
>
> **第 15 项补充说明（为什么必须 fail-loud）**：前端变更常伴随表单结构调整（字段挪位置、v-if 条件渲染、新增/移除必填项）。阶段三重写定位时，若图省事用"找不到就跳过"包住新定位，看似让脚本"不报错、能跑完"，实则字段根本没配上，而用例很可能因原有断言未覆盖该字段而**照样判 PASS**——这叫"假绿/测试裸奔"，比当场报错更危险：它给出虚假通过信号，还会把前端改版导致的定位失效掩盖成"已修复"。若怀疑字段确实不存在了（如条件渲染、选了某项才出现），按本文件"定位规范"重新 `recon_page.py`/`Grep refrence/` 确认，更新定位后仍需正常 fill/click，而不是绕过。

## 三、修复范围红线

- 仅允许触及 `test_*.py` 与必要的 `pages/**`。
- **禁止**改 `sugon_web/common/`、`sugon_web/refrence/`、阶段一/历史需求 MD 业务参数、`sugon_web/config/pkey_scloudadmin`。
- **禁止**删除测试/fixture 文件；新增 pytest marker 必须同步 `pytest.ini` 的 markers 列表。

## 四、定位规范（前端变更修复时遵守）

- 优先 `get_by_role()` / `get_by_text(exact=True)` / `get_by_placeholder()`。
- 限定在 dialog / tab / 表格 / 行范围内定位；`first()` / `nth()` 仅作兜底，不作首选。
- **禁止 XPath**（脆弱、页面微调即失效）。
- 优先复用 `sugon_web/common/base.py` 已封装的公共元素/操作（如 `btn_create`、`search`、`click_action`），不自造等价 locator。

## 五、修复前自检 checkbox（每轮 Fix 必须逐条勾选并输出到对话框）

### 通用 7 项（修复前必勾，与本文件「一、修复纪律」「二、速查表」一致）

```
□ 1. 触及需求 MD/脚本既定业务参数?       ___（是 → 禁止修复，回 Diagnose）
□ 2. 触及 common/ 或 refrence/ 公共代码?  ___（是 → 禁止修复）
□ 3. 改 pages/ 已有定位逻辑去绕过缺陷?     ___（是且非前端对齐 → 禁止，记录页面对象修复项）
□ 4. 测试层引入 locator/expect/XPath?      ___（是 → 禁止修复，回 Diagnose）
□ 5. 使用了 wait_for_timeout 固定等待?      ___（是 → 禁止修复，改用收敛点等待）
□ 6. 用 try/except 吞错或放宽了断言?        ___（是 → 禁止修复，回 Diagnose）
□ 7. 仅涉及 test_*.py 和必要页面对象?       ___（否 → 禁止修复，回 Diagnose）
```

### 自愈专项 6 项（本 skill 新增，对抗「凭空改定位」与「静默跳过掩盖假绿」）

```
□ A. 本次修复是否以「最新前端工程代码」或「运行时渲染态」为依据?（否 → 回阶段二，禁止凭空改定位）
□ B. 是否已确认旧定位/旧文案在新前端中确实已变更（而非环境导致临时不可见）?
□ C. 新定位是否遵循优先级（get_by_role/get_by_text(exact) > 范围限定 > first/nth 兜底，禁 XPath）?
□ D. 改动是否仅限 test_*.py 与必要 pages/**，未触碰 common//refrence//MD 业务参数?
□ E. 是否为「前端流程重构」级变更（步骤增减）?（是 → 标记需结合需求 MD 重新对齐，而非简单改定位）
□ F. 是否对原脚本/需求依赖的必填字段用 `if count()>0` 静默跳过或用默认值替代?（是 → 禁止修复，改为 fail-loud 直接 fill/click，见速查表第 15 项）
```

**任一项不通过 → 回阶段二重新分诊，不允许带着违规修复进入下一轮。未在反馈中完整输出本节 13 项 checkbox = 视为本轮修复未开始，不得进入代码编辑（硬约束）。**

## 六、修复后要求

- 修复后必须执行**完整用例**（不是只跑失败步骤），由阶段四统一回归，确保无回归。
- 修复方案记录格式：`修改文件路径:关键改动一句话 + 依据（Grep 前端 / recon 渲染态）`。
