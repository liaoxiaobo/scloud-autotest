# UI 自动化测试脚本开发 · 瘦编排 Skill（Orchestrator）

> **本文件为编排层（在主对话上下文运行，可用 `Agent` 工具派发子智能体）。**
> 它**只负责编排调度**：派发五个阶段子智能体、读运行报告状态、维护循环计数器、驱动跨阶段回退状态机、做全局总收尾。
> **它不亲自执行任何阶段任务、不改写任何阶段规范**——各阶段"执行什么、遵守什么规范"全部在对应子智能体文件内（其 body 已逐字内联本阶段全文规范）。
> 以下「长时间自主任务声明」「运行报告持久化与恢复协议」「工具调用约束」「完成后输出」四节为**原 skill 原文逐字沿用**（仅将 `report_check.py` 脚本路径按白名单改写到新永久目录）；其余为**架构新增**的编排说明。

## 长时间自主任务声明

本 SKILL 执行期间 **AI 全程自主运行**，严禁停下来询问用户，因为本任务设计为长时间自主运行，中途等待用户响应会中断自动化流程。所有修复/检查决策自主完成，仅在无法自主解决的阻塞性问题时允许暂停请求输入。任务从需求转换到稳定性验证可能持续数十分钟至数小时。

> **设计哲学**：给足修复机会，但绝不死磕；检测无意义循环，而非掐表计时。

> **停止口径（2026-06-17 团队决策）**：是否停止主要由"次数 + 进展"决定——单用例 40 次、全局 max(60, 场景数×10) 次、连续 15 次失败在同一位置冻结（详见下文「循环计数器持久化」；按失败位置而非报错文本判定，换报错文本骗不过）；并设**全局活跃墙钟硬上限**：自首次激活起累计**活跃**墙钟 > 10h 时，run_guard 直接**硬停**（退出码 3 拒绝下一次 pytest），强制收尾标"遗留·转人工"（活跃墙钟已扣除长空闲间隔，跨夜/中断恢复不会被秒杀）。即贯彻"检测无意义循环 + 绝不死磕"：每轮在推进就继续修，原地打转或墙钟过长就尽快交人，**不无脑长跑**。

## 运行报告持久化与恢复协议

为对抗上下文压缩导致前序阶段输出丢失，各阶段"立即输出"须在对话框输出的同时，双写到运行报告文件 `skill_runs/test-script-dev/test-script-dev_{任务标识}_{YYYYMMDD_HHMM}.md`（具体写入要求见各 phase 文件末尾"同步持久化"段）。全局规则：

- **任务标识与单文件**：任务标识统一取本次任务的需求 MD 英文文件名（去 `.md`），五个阶段一律以此为准，**不得改用测试脚本名**（脚本名与 MD 名常不一致，会导致 glob 匹配不到而分裂出第二个文件）。一次运行只用一个文件（放 `skill_runs/test-script-dev/`，严禁写入 `logs/`），由首个执行的阶段创建，其余阶段先 glob 找到该文件再在末尾追加（含回退轨迹），**严禁新建第二个文件、严禁覆盖前序内容**。
- **双写不替代**：严禁用写文件替代对话框输出，也严禁用对话框输出替代写文件。
- **压缩后续跑**：每阶段开始前先按 glob `skill_runs/test-script-dev/test-script-dev_{任务标识}_*.md` 取最新文件 `Read`，据此判断已完成到哪、从哪重入；任务标识统一从磁盘上的需求 MD 文件名推导，不靠对话记忆。
- **阶段闸门**：进入下一阶段前，须先 `Read` 运行报告文件 `skill_runs/test-script-dev/test-script-dev_{任务标识}_{YYYYMMDD_HHMM}.md` 确认上一阶段完成块已写入，缺失则先补写再继续。
- **各阶段报告必出区块清单**（压缩也带不走的硬清单；缺任一即视为该阶段未完成，必须补写）：
  - 阶段一：`## 阶段一…完成时间` + 完成清单表
  - 阶段二：`## 阶段二…完成时间` + 完成清单表 +（新建/改动 Page Object 或含复杂交互时）**页面侦察结论卡表**
  - 阶段三：`## 阶段三…完成时间` + 完成清单表 + 5.2 修复循环问题清单（含根因列）
  - 阶段四：`## 阶段四…完成时间` + 完成清单表
  - 阶段五：`## 阶段五…完成时间` + 4.2 完成清单 + 4.3 问题总结 + **4.4 第一部分四张表（① Fixture ② Page Object ③ Helper ④ 断言复用/新增清单）+ 4.4 第二部分 10 列经验沉淀表**（最重、最易被压缩漏写，一表/一列都不能省）
  - 全局总结（面向人）：`## 完成后输出` + 1.总体结论 + 2.执行概览 + 3.风险与后续待办 + 4.产物位置索引 + 5.各阶段耗时统计（全局总览，不与各阶段明细重复）
- **落笔前就近重读 + 写后机器校验（强制，对抗压缩漏写/写简）**：每个阶段在生成"立即输出"前，先重新 `Read` 对应 phase 文件末尾的"立即输出"整节，按其确切表头逐项写全；写完后运行报告锚点校验脚本确认结构齐全：`python .claude/skills/test-script-dev/scripts/report_check.py <本次运行报告 md 路径> --phase <1/2/3/4/5/final>`，退出码非 0（缺锚点）→ 必须按提示补写后重跑，通过方可进入下一阶段或总收尾。
- **全局总结从文件聚合**：全部完成后的全局总结（总体结论/执行概览/风险待办/产物索引）须先 `Read` 报告文件后聚合，不依赖对话记忆。

## 五个阶段的执行编排（架构新增·派发与回退）

> **本节为架构新增**：本 Skill 是总控编排层，**自身不执行任何阶段任务**；各阶段的完整执行指令、规范、检查清单、完成时立即输出格式，全部**逐字内联**在对应子智能体文件 body 内（与原 skill `references/` 各 phase 文件逐字一致，已机器自证零差异）。本 Skill 只按顺序与回退状态机派发子智能体、读盘判进度、维护计数器。

### 阶段 → 子智能体映射

| 阶段 | 派发的子智能体（`Agent` 工具，按 name 显式派发） | 该阶段产出物 / 完成标志（原文口径） |
|---|---|---|
| 阶段一：需求转换与校验 | `phase1-requirements` | 校验通过的 MD 需求文档；MD 已校验通过、无歧义无错误 |
| 阶段二：脚本编写与对齐 | `phase2-coding` | 对齐需求后的测试脚本；脚本与需求完全对齐、各项检查全部通过 |
| 阶段三：执行用例与修复 | `phase3-execution` | 修复后的脚本+检查清单+日志；所有用例达可接受状态 |
| 阶段四：日志分析与核查 | `phase4-log-analysis` | 日志分析与核查报告；每步与需求一致、teardown 段已扫描分级 |
| 阶段五：稳定性验证 | `phase5-stability` | 稳定性验证结果；通过轮次达标且无未修复的用例问题 |

### 派发机制（架构新增，官方依据：Invoke subagents explicitly）

- 本 Skill 用 **`Agent` 工具按 `name` 显式派发**对应阶段子智能体（`Task` 自 v2.1.63 起更名 `Agent`，`Task` 仍为别名）。

> **★ 强制派发铁律（最高优先级，对抗"在主会话偷懒直接干"）：**
> 1. **阶段二、阶段三、阶段四、阶段五，必须通过 `Agent` 工具派发对应子智能体（`phase2-coding` / `phase3-execution` / `phase4-log-analysis` / `phase5-stability`）在其独立 fresh-context 中执行**。
>    - **阶段三为无条件强制派发（最易失控，特别加硬）**：无论用例成本高低、无论是否预期首轮即过，只要进入阶段三就必须派发 `phase3-execution`，**严禁编排层主会话"先直接跑一次 pytest 试试"再决定是否派发**——首轮即过是小概率，实测绝大多数用例都需多轮修复，主会话试跑会污染编排上下文、丢失"旁观监督"，是阶段三失控的根源。
> 2. **严禁本 Skill（编排层主会话）亲自编写测试脚本/页面对象、亲自跑 pytest、亲自做根因分析与修复、亲自做日志核查与稳定性多轮执行**——这些是子智能体的职责。编排层只派发、读盘、读一句话状态、维护计数、驱动回退。
> 3. 阶段一按成本分级**允许**编排层主上下文直跑（上下文轻）；但**一旦阶段一进入需多轮校验/或你判断其上下文将膨胀，也应派发 `phase1-requirements`**。除阶段一这一例外，**其余阶段不得在主会话内直接执行**。
> 4. **回退循环同样适用**：阶段四/五回退到阶段三时，**必须重新 `Agent` 派发 `phase3-execution`**（再派发 `phase4-log-analysis`/`phase5-stability`），**严禁在主会话里直接修复**。每一次回退重入都要重新派发，不得图省事在主会话内改。
> 5. 若发现自己（编排层）已经开始直接读被测前端代码、直接写 `test_*.py`、或直接执行 `pytest`——**立即停止，改为派发对应子智能体**。这是判断"是否违规偷懒"的硬信号。

- 派发的任务 prompt 中**只写指针型输入 + 该阶段最关键的 1-2 条硬约束**（规范全文已在子智能体 body，此处不重述全文；但把"最易被忽视、后果最重"的硬约束 **front-load 进派发首条消息**，因为那是子智能体 fresh context 里最先读到、显著性最高的位置）：
  - 本次任务标识（= 需求 MD 英文文件名去 `.md`；首阶段尚无 MD 时按 phase1 产出后回填）；
  - 运行报告文件路径（按上文 glob 取最新）；
  - 若为回退重入：从运行报告「循环计数区」取出的"待处理问题清单 + 当前循环计数"。
  - **派发文本一律照搬下文「各阶段派发 prompt 模板」**（见本节末），按模板填 `<占位符>`，**禁止自由发挥、禁止删改"首要任务/关联文件必读/硬约束/收尾"任一段**——这是防止"派发时随手写、漏掉关键规范与必读文件"的根本办法。
- **子智能体须前台执行**（不放后台：后台子智能体会自动拒绝需授权的工具调用，导致 `Bash`/写盘被静默拒绝）。
- 子智能体完成后**只回一句话状态**（明细已写运行报告）；本 Skill 只读该状态 + 读运行报告锚点，决定下一步。
- 用户只需触发本 Skill（`/test-script-dev` 或描述匹配自动唤起），**派发由本 Skill 自动完成，用户不必手动逐个 @ 子智能体**。

### 各阶段派发 prompt 模板（强制·照搬填空）

> **总规则（必须遵守）**：派发任一阶段，**必须照搬下方对应模板**，只替换 `<占位符>`；**禁止自由发挥、禁止删改/精简"首要任务、关联文件必读、硬约束、收尾"任一段**。模板的「高频易漏项」只是额外提醒，**绝不代表全部要求**——子智能体仍须完整遵守其 body 正文全文。
>
> **关联文件必读（所有阶段通用，必须原样保留在派发 prompt 里）**：凡阶段规范正文点名要求阅读的关联文件，子智能体**必须用 `Read` 逐个、从头到尾完整读完每一个全文（不跳读、不节选、不只读开头/摘要）**，并**严格按这些关联文件中的约束与规范完成任务**；**严禁因为"上下文里好像见过/我大概记得/篇幅太长"就跳读、不读、或读了不遵守**。记忆/上下文片段**不能**替代对原文件的完整重新阅读。**未完整读完全部关联文件即开始执行 = 违规，本轮作废。**（**例外·被测模块前端工程代码不在"完整通读"之列**：它按 `sugon_web/refrence/module_index.yaml` 的策略执行——用 module_index 定位模块目录 → `Grep` 命中本次相关的组件/文案/路由 → 对命中的相关文件**读全读透**（严禁略读/跳读/凭印象猜），但**严禁整目录/整模块通读**（大模块动辄数百 KB，整读会拖慢、撑爆上下文甚至卡死）。"完整通读"只针对规范/提示/需求 MD 这类小而有界的文件。）
>
> **读到 ≠ 遵守（同等违规，实测高发，必须原样保留在派发 prompt 里）**：实测出现过"已读到规范、却在修复压力下故意绕过"的情况——子智能体明知应走框架公共能力（如导航 `goto_service`/`goto_submenu`、复用既有 fixture/断言/Page 方法），却因其"不直达目标/不好用"，就自创绕路写法（手拼 URL 调 `page.goto(...)`、照搬前端 router 路径、`evaluate` 合成事件、复制粘贴硬绕等）。**严禁以"先让用例跑通/这样更快/框架方法不合用"为由，违反任何你已读到的规范**：当框架公共能力与目标不一致时，**唯一允许**的做法是回到规范定义的正确入口、或按规范"扩展而非改写"（新增带默认值参数/新增方法），**绝不允许自创绕路绕过已读规范**。怀疑是框架配置/映射本身有误时，按规范正确入口走或标记"遗留问题/需人工补充"，**不得在测试代码里绕过**。为跑通而绕过已读规范 = 本轮修复作废（与"未读完即违规"同级）。

> **完成时间必须精确到秒（所有阶段通用，必须遵守）**：各阶段写入运行报告的完成块标题 `## 阶段X：…　完成时间：…` 里的时间，**必须先在 git-bash 运行 `date "+%Y-%m-%d %H:%M:%S"` 取真实系统时间再原样填入，精确到【年月日 + 时:分:秒】俱全**；严禁只写日期（如 `2026-06-18`）、严禁省略时分秒、严禁凭记忆/猜测手写（`report_check.py` 会机械校验该时间，缺秒/缺日期一律判不通过、须改写重跑）。
>
> **读文件用工具、禁 `python -c` 打印（所有阶段通用，防 GBK 崩溃空转）**：读文件内容一律用 `Read`、搜内容用 `Grep`；**严禁用 `python -c "...print(...)"` / `type` / `cat` 去打印文件或前端代码片段来"看内容"**——Windows 下 Python 标准输出默认是 GBK 编码，打印含 `\xa0`(不间断空格)/中文/特殊符号的内容会直接 `UnicodeEncodeError: 'gbk' codec can't encode` 崩溃、白白空转烧 token；若已踩坑看到该报错，立即改用 `Read`，不要纠缠 `encode`/`decode` 变体。

### 循环计数器持久化（架构新增）

因子智能体无状态、每次全新记不住轮次，下列计数机制的"当前值"由本 Skill 落盘到运行报告**「循环计数区」**（架构新增的一个区块），每次派发回退前先读、派发后更新。**阈值口径（2026-06-17 按团队决策调整为下表，统一以 `run_guard.py` 常量与本表为准；`run_guard.py` / `loop_gate.py` / phase3 正文三处必须保持一致）**：

| 计数器 | 上限 |
|---|---|
| 单用例次数（= 一个 CSV 需求 / 一个 def test_ 方法，用 -k 单独跑） | **40 次**（口径：1 次 pytest = 1 次） |
| 全局次数 | **max(60, 场景数 × 10)**（如 8 场景→80） |
| 状态冻结检测（零前进） | **连续 15 次失败在同一位置**（同一测试 nodeid + 同一处最深用户代码 file:line，与报错文本是否变化无关；只有推进到新失败位置/通过才清零） |
| 阶段五回退同一根因修复次数 | 最多 8 次 |
| 全局活跃墙钟硬上限 | 自首次激活起累计**活跃**墙钟 **> 10h** → run_guard 硬停（退出码 3 拒绝、强制收尾标"遗留·转人工"；活跃墙钟已扣除长空闲间隔，跨夜/中断恢复不秒杀） |

> **"单用例"的明确定义（务必让子智能体读懂，避免理解错而产生幻觉）**：这里的"单用例"指**测试需求 CSV 文件里的一行数据（一个"用例编号"/一个测试需求/场景）**，它在阶段二被转换成测试脚本里的**一个 `def test_` 方法**。所以"单用例 40 次" = "每个 CSV 需求（对应一个 `def test_` 方法，用 `-k` 单独跑时）最多跑 40 次 pytest"。它**不是**指整个 `.py` 脚本文件（一个 `.py` 通常含一个 CSV 文件的多个需求 / 多个 `def test_` 方法），也**不是**指一次 pytest 命令。
> **★ 特别强调：单用例更不是指"整个 CSV 文件"**——一个 CSV 文件里有几行需求（几个"用例编号"）就是几个用例 / 几个 `def test_` 方法 / 场景数就是几。例：`requirements_csv/lbv2_http_forward_1&2.csv` 含 2 个用例编号（436766、436767）→ **2 个用例 → 2 个 `def test_` → `--cases 2`**（全局上限 = max(60, 2×10) = 60）。仅当 CSV 里"多行只是参数不同的高重复需求"被 `@pytest.mark.parametrize` 合并进**一个**方法时，才按参数化后的场景数计（此时 `def test_` 方法数 < CSV 行数，`--cases` 传**场景数=def test_ 方法数×参数组数**，以阶段二实际产出的 `def test_`/参数化结构为准）。

> **状态冻结(15) 与 阶段五同根因(8) 不要混淆**：① **状态冻结的 15**（见 phase3 §3.3）= 在阶段三修复循环里，同一用例**连续 15 次失败在同一位置**就停（机械判定，由 `run_guard.py` 按「失败测试 nodeid + 最深用户代码 file:line」做指纹比对，**与报错文本是否变化无关**；只有推进到新失败位置/通过才清零——换 selector 让报错文本变一变骗不过它，这正是把单用例额度全卡在同一步的关键）；② **阶段五回退同一根因的 8** = 用例在阶段五稳定性验证不通过、**被退回阶段三重修**时，针对**同一个根因**最多来回修 8 次（2026-06-18 由 5 放宽到 8，给偶发/复合根因更多收敛机会）。两者发生的阶段不同、机制不同、互不相关。

> **口径说明（2026-06-17）**：计数极简为"1 次 pytest = 1 次"，不区分"改了代码 vs 诊断重跑"；**全局活跃墙钟硬上限 10h（超过 run_guard 直接硬停·退出码 3 拒绝，已扣除长空闲间隔；2026-06-21 由原 6h 软兜底改为 10h 硬停——软兜底无约束力、实测被无视跑满 7h+）**。`run_guard --reset` 后的绕过审计**只统计本次 reset 之后产生的日志**，阶段二试跑/上一次任务残留的旧日志不再被算进本次额度。**回退重入必须用 `--reset --reentry`：不清零累计全局、只给本用例新预算 + 小额回退预算（+10），杜绝"每次回退拿全新预算→无限续命"。**

达上限 → 标记"遗留问题"并停止回退；未达 → 派发并在子智能体完成后更新计数。

- **按退出码硬执行（不得由子智能体二次决定）**：

  - `2` → **计数区缺失或无法解析，同样不放行**：先补全/修正运行报告「循环计数区」（这是抗压缩的硬约束——计数必须每轮真实落盘），再重跑闸门，通过后方可继续。
- **闸门是裁决、不是建议**：编排层不得在退出码非 0 时仍派发；这是消除"阶段三无限试错"的硬刹车，且因只读磁盘计数，**不受阶段三多轮修复触发上下文压缩的影响**。

## 工具调用约束

修改测试脚本时，若 `Edit` 因 `old_string` 不唯一失败，严禁中断流程等待人工确认。按以下优先级自动恢复：

1. **扩大匹配范围**：立即 `Read` 文件，增加 surrounding 函数体或相邻注释使 `old_string` 唯一
2. **使用 replace_all**：确认所有匹配处需相同修改时，改用 `replace_all=true`
3. **替代方案**：上述方法均不可行时，改用 `Write` 重写整个文件

`Edit` 和 `replace_all` 均失败时，必须使用 `Write` 作为最终降级方案；仅当 `Write` 也失败时，记录错误并继续下一步。严禁弹出确认对话框。

### Shell 命令执行约束（强制·防 `cd /d` 报错空转，2026-06-18 新增）

> **背景**：Claude Code 实际通过 **bash（`/usr/bin/bash`，Windows 上是 git-bash）** 执行命令，**不是 CMD**。实测出现过：模型因系统是 Windows 就给命令加 CMD 风格前缀 `cd /d "路径" && python ...`，bash 不认 `/d` → 报 `cd: too many arguments`（退出码 2）→ `&&` 后的 `python run_guard.py` 根本没执行 → 模型又原样重发同一条坏命令、循环空转一个多小时、狂烧 token。

1. **命令一律在仓库根目录、用 bash 执行**：本文所有 `python .claude/skills/.../*.py ...`、`pytest ...` 命令都假定当前工作目录＝仓库根目录、用相对路径，**直接原样运行即可**。
2. **严禁给命令加 `cd` / `cd /d` 前缀**：默认就在仓库根目录，无需切目录；**`cd /d` 是 CMD 语法，在 bash 里必然报 `cd: too many arguments`**。万一确需切目录，只用 bash 语法 `cd "路径"`（**绝不带 `/d`**）。
3. **反循环硬规则（防空转烧 token）**：**同一条命令连续 2 次返回相同报错 → 立即停止"原样重发"**，先诊断命令本身（语法 / 路径 / 工作目录），改对了再发：
   - 看到 `cd: too many arguments` → 你在 bash 里用了 CMD 的 `cd /d`；**去掉整个 `cd ... &&` 前缀**，直接跑后面的 `python`/`pytest` 命令。
   - 看到 `No such file or directory` / 路径找不到 → 确认是否用了正确的仓库相对路径，而不是去 `cd` 到绝对路径。
   - 报错与 run_guard 的"守卫拒绝(退出码 3)"无关时，**不要把 shell/语法错误误判为产品缺陷或环境问题、更不要反复改测试代码**。
4. **只用脚本真实支持的参数**：调 `run_guard.py` 只用 `--reset` / `--reentry` / `--task` / `--cases` / `--release` / `-- pytest ...`（见脚本 `--help`）；**严禁臆造不存在的参数**（如 `--status`），那会被 argparse 当成 pytest 参数误跑、白白消耗一次额度。要查进度就 `Read` 运行报告 + run_guard state 文件，不要靠臆造命令试探。
5. **严禁用 `python -c "...print(...)"`（或 `type`/`cat`）打印文件内容/前端代码片段来"看代码"（防 GBK 编码崩溃空转，2026-06-18 新增）**：要读文件内容一律用 `Read` 工具、要搜内容用 `Grep`/搜索工具——这既是正道，也避开一个实测高发坑：**Windows 下 Python 标准输出默认是 GBK(cp936) 编码，`print` 含 `\xa0`(不间断空格)、中文、特殊符号的前端代码/文案时会直接 `UnicodeEncodeError: 'gbk' codec can't encode character`、命令崩溃**（实测模型为此反复改 `encode('utf-8')`/`decode` 仍失败、空转烧 token——根因在"输出流是 GBK"，不在被打印的字符串）。
   - 看到 `UnicodeEncodeError: 'gbk' codec can't encode ...` → **立即停手，不要再试 encode/decode 变体、不要原样重发**，改用 `Read` 工具读该文件即可。
   - 万一确有必要用 python 处理并打印含中文/特殊字符的内容：用 bash 语法前置环境变量 `PYTHONIOENCODING=utf-8 python -c "..."`，或脚本内先 `import sys; sys.stdout.reconfigure(encoding="utf-8")`。（本 skill 自带的 `precheck.py`/`report_check.py`/`run_guard.py` 已内置该保护，直接调用不受影响。）

6. **全程禁止执行任何 `git` 命令（强制，2026-06-19 新增）**：本工作流执行期间**严禁运行任何 git 命令**（`git checkout` / `git reset` / `git clean` / `git add` / `git commit` / `git stash` / `git restore` 等一律不准）——既不准用 git"绕过失败 / 撤销本应做的修改"，也不准用 git"恢复误删"。**若不慎误删 / 误覆盖了已有测试用例（或任何文件）：立即停止当前任务，在对话框醒目提示用户"误删了什么文件、原状如何、需人工从版本库/备份恢复"，然后等待用户处理——绝不自行用 git 或其它方式补救、绝不继续往下执行。**（注：`run_guard.py`/`precheck.py` 等脚本内部对 git 的【只读】查询是脚本自身行为、与本条无关，你不需要也不应主动敲 git。）

### 子智能体被中断 / 状态不明时的编排处理（强制）

阶段三等子智能体若被用户中断、或你无法确认它是否还在跑：**不要慌乱试探、不要臆造命令、不要在主会话直接接管修复**。按序处理：① `Read` 最新运行报告 + `skill_runs/test-script-dev/_runguard_<任务标识>.json` 判断已完成到哪、计数到几；② 确认无残留 pytest 进程后，需要重入阶段三就规规矩矩 `run_guard.py --reset --reentry --task <标识> --cases <场景数>`（**不带任何 `cd` 前缀**）再重新 `Agent` 派发 `phase3-execution`；③ 仍无法判断则停下、如实向用户说明状态,不空转重试。

## 完成后输出（全局总结，面向人阅读）

**定位说明**：各阶段的明细（完成清单、问题清单、测试执行结果、经验沉淀等）已由各 phase 的"阶段完成时立即输出"逐阶段产出并写入运行报告，**本节不再重复这些明细**。本节是整次执行结束后，面向**人**的一段**全局总结**——让阅读者无需翻看各阶段明细，就能一眼掌握"这次干了什么、结果如何、能否投产、还有什么需要人处理、细节去哪看"。

**触发与口径**：所有阶段执行完毕并通过完成判定后输出，并追加写入运行报告文件末尾。内容须先 `Read` 运行报告文件后聚合生成，不依赖对话记忆；**严禁用本节替代任一阶段的立即输出**（两者并行，明细在阶段、总览在此）。

> **清理守卫状态（强制·收尾必做）**：本次 skill 全部结束时（无论正常完成还是被迫中断），编排层必须运行一次 `python .claude/skills/test-script-dev/scripts/run_guard.py --release` 清除阶段三的守卫哨兵与计数状态，保持环境干净、避免残留状态影响后续运行的绕过审计。（漏删也无妨：哨兵带数小时滑动 TTL，会自动过期；`skill_runs/` 已 gitignore，不影响 CI。）
