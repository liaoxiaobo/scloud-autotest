# UI 自动化测试脚本开发 · 瘦编排 Skill（Orchestrator）

> **本文件为编排层（在主对话上下文运行，可用 `Agent` 工具派发子智能体）。**
> 它**只负责编排调度**：派发五个阶段子智能体、读运行报告状态、维护循环计数器、驱动跨阶段回退状态机、做全局总收尾。
> **它不亲自执行任何阶段任务、不改写任何阶段规范**——各阶段"执行什么、遵守什么规范"全部在对应子智能体文件内（其 body 已逐字内联本阶段全文规范）。
> 以下「长时间自主任务声明」「运行报告持久化与恢复协议」「工具调用约束」「完成后输出」四节为**原 skill 原文逐字沿用**（仅将 `report_check.py` 脚本路径按白名单改写到新永久目录）；其余为**架构新增**的编排说明。

## 长时间自主任务声明

本 SKILL 执行期间 **AI 全程自主运行**，严禁停下来询问用户，因为本任务设计为长时间自主运行，中途等待用户响应会中断自动化流程。所有修复/检查决策自主完成，仅在无法自主解决的阻塞性问题时允许暂停请求输入。任务从需求转换到稳定性验证可能持续数十分钟至数小时。

> **设计哲学**：给足修复机会，但绝不死磕；检测无意义循环，而非掐表计时。

> **墙钟感知（兜底防失控，不替代根因优先）**：对高成本用例（单次墙钟 > 15min），除阶段三的"次数上限"外，引入墙钟提醒——当某用例累计修复+重跑墙钟显著超出预期（如单用例 > 3 小时仍未通过），**强制触发一次阶段三 3.7 的 Phase 4.5 三次失败质疑**，并优先考虑"标记为遗留问题/疑似产品缺陷、转人工"，而非继续耗轮次。这是防失控兜底，仍以"检测无意义循环而非掐表计时"为准。

## 运行报告持久化与恢复协议

为对抗上下文压缩导致前序阶段输出丢失，各阶段"立即输出"须在对话框输出的同时，双写到运行报告文件 `skill_runs/test-script-dev/test-script-dev_{任务标识}_{YYYYMMDD_HHMM}.md`（具体写入要求见各 phase 文件末尾"同步持久化"段）。全局规则：

- **任务标识与单文件**：任务标识统一取本次任务的需求 MD 英文文件名（去 `.md`），五个阶段一律以此为准，**不得改用测试脚本名**（脚本名与 MD 名常不一致，会导致 glob 匹配不到而分裂出第二个文件）。一次运行只用一个文件（放 `skill_runs/test-script-dev/`，严禁写入 `logs/`），由首个执行的阶段创建，其余阶段先 glob 找到该文件再在末尾追加（含回退轨迹），**严禁新建第二个文件、严禁覆盖前序内容**。
- **双写不替代**：严禁用写文件替代对话框输出，也严禁用对话框输出替代写文件。
- **压缩后续跑**：每阶段开始前先按 glob `skill_runs/test-script-dev/test-script-dev_{任务标识}_*.md` 取最新文件 `Read`，据此判断已完成到哪、从哪重入；任务标识统一从磁盘上的需求 MD 文件名推导，不靠对话记忆。
- **阶段闸门**：进入下一阶段前，须先 `Read` 运行报告文件 `skill_runs/test-script-dev/test-script-dev_{任务标识}_{YYYYMMDD_HHMM}.md` 确认上一阶段完成块已写入，缺失则先补写再继续。
- **各阶段报告必出区块清单**（压缩也带不走的硬清单；缺任一即视为该阶段未完成，必须补写）：
  - 阶段一：`## 阶段一…完成时间` + 完成清单表
  - 阶段二：`## 阶段二…完成时间` + 完成清单表
  - 阶段三：`## 阶段三…完成时间` + 完成清单表 + 5.2 修复循环问题清单（含根因列）
  - 阶段四：`## 阶段四…完成时间` + 完成清单表
  - 阶段五：`## 阶段五…完成时间` + 4.2 完成清单 + 4.3 问题总结 + **4.4 第一部分四张表（① Fixture ② Page Object ③ Helper ④ 断言复用/新增清单）+ 4.4 第二部分 10 列经验沉淀表**（最重、最易被压缩漏写，一表/一列都不能省）
  - 全局总结（面向人）：`## 完成后输出` + 1.总体结论 + 2.执行概览 + 3.风险与后续待办 + 4.产物位置索引（全局总览，不与各阶段明细重复）
- **落笔前就近重读 + 写后机器校验（强制，对抗压缩漏写/写简）**：每个阶段在生成"立即输出"前，先重新 `Read` 对应 phase 文件末尾的"立即输出"整节，按其确切表头逐项写全；写完后运行报告锚点校验脚本确认结构齐全：`python .claude/skills/test-script-dev/scripts/report_check.py <本次运行报告 md 路径> --phase <1/2/3/4/5/final>`，退出码非 0（缺锚点）→ 必须按提示补写后重跑，通过方可进入下一阶段或总收尾。
- **全局总结从文件聚合**：全部完成后的全局总结（总体结论/执行概览/风险待办/产物索引）须先 `Read` 报告文件后聚合，不依赖对话记忆。

## 五个阶段的执行编排（架构新增·派发与回退）

> **本节为架构新增**：本 Skill 是总控编排层，**自身不执行任何阶段任务**；各阶段的完整执行指令、规范、检查清单、完成时立即输出格式，全部**逐字内联**在对应子智能体文件 body 内（与原 skill `references/` 各 phase 文件逐字一致，已机器自证零差异）。本 Skill 只按顺序与回退状态机派发子智能体、读盘判进度、维护计数器。

### 阶段 → 子智能体映射

| 阶段 | 派发的子智能体（`Agent` 工具，按 name 显式派发） | 该阶段产出物 / 完成标志（原文口径） |
|---|---|---|
| 阶段一：需求转换与校验 | `phase1-requirements` | 校验通过的 MD 需求文档；MD 已校验通过、无歧义无错误 |
| 阶段二：脚本编写与对齐 | `phase2-coding` | 对齐需求后的测试脚本；脚本与需求完全对齐、各项检查全部通过 |
| 阶段三：执行用例与修复 | `phase3-execution` | 修复后的脚本+检查清单+日志；所有用例达可接受状态 |
| 阶段四：日志分析与核查 | `phase4-log-analysis` | 日志分析与核查报告；每步与需求一致、teardown 段已扫描分级 |
| 阶段五：稳定性验证 | `phase5-stability` | 稳定性验证结果；通过轮次达标且无未修复的用例问题 |

### 派发机制（架构新增，官方依据：Invoke subagents explicitly）

- 本 Skill 用 **`Agent` 工具按 `name` 显式派发**对应阶段子智能体（`Task` 自 v2.1.63 起更名 `Agent`，`Task` 仍为别名）。

> **★ 强制派发铁律（最高优先级，对抗"在主会话偷懒直接干"）：**
> 1. **阶段二、阶段三、阶段四、阶段五，必须通过 `Agent` 工具派发对应子智能体（`phase2-coding` / `phase3-execution` / `phase4-log-analysis` / `phase5-stability`）在其独立 fresh-context 中执行**。
>    - **阶段三为无条件强制派发（最易失控，特别加硬）**：无论用例成本高低、无论是否预期首轮即过，只要进入阶段三就必须派发 `phase3-execution`，**严禁编排层主会话"先直接跑一次 pytest 试试"再决定是否派发**——首轮即过是小概率，实测绝大多数用例都需多轮修复，主会话试跑会污染编排上下文、丢失"旁观监督"，是阶段三失控的根源。
> 2. **严禁本 Skill（编排层主会话）亲自编写测试脚本/页面对象、亲自跑 pytest、亲自做根因分析与修复、亲自做日志核查与稳定性多轮执行**——这些是子智能体的职责。编排层只派发、读盘、读一句话状态、维护计数、驱动回退。
> 3. 阶段一按成本分级**允许**编排层主上下文直跑（上下文轻）；但**一旦阶段一进入需多轮校验/或你判断其上下文将膨胀，也应派发 `phase1-requirements`**。除阶段一这一例外，**其余阶段不得在主会话内直接执行**。
> 4. **回退循环同样适用**：阶段四/五回退到阶段三时，**必须重新 `Agent` 派发 `phase3-execution`**（再派发 `phase4-log-analysis`/`phase5-stability`），**严禁在主会话里直接修复**。每一次回退重入都要重新派发，不得图省事在主会话内改。
> 5. 若发现自己（编排层）已经开始直接读被测前端代码、直接写 `test_*.py`、或直接执行 `pytest`——**立即停止，改为派发对应子智能体**。这是判断"是否违规偷懒"的硬信号。

- 派发的任务 prompt 中**只写指针型输入**，不重述阶段规范（规范已在子智能体 body）：
  - 本次任务标识（= 需求 MD 英文文件名去 `.md`；首阶段尚无 MD 时按 phase1 产出后回填）；
  - 运行报告文件路径（按上文 glob 取最新）；
  - 若为回退重入：从运行报告「循环计数区」取出的"待处理问题清单 + 当前循环计数"。
- **子智能体须前台执行**（不放后台：后台子智能体会自动拒绝需授权的工具调用，导致 `Bash`/写盘被静默拒绝）。
- 子智能体完成后**只回一句话状态**（明细已写运行报告）；本 Skill 只读该状态 + 读运行报告锚点，决定下一步。
- 用户只需触发本 Skill（`/test-script-dev` 或描述匹配自动唤起），**派发由本 Skill 自动完成，用户不必手动逐个 @ 子智能体**。

### 编排层职责边界

- **只做**：派发 / glob+Read 运行报告判进度 / 读一句话状态 / 维护循环计数器 / 驱动回退状态机 / 全局总收尾。
- **严禁（违反即视为执行错误，须立即纠正）**：
  - 严禁把子智能体的完整输出/长篇明细收进本 Skill 自身上下文（明细一律落盘，只读"必出区块"锚点与一句话状态）；
  - **严禁亲自执行阶段任务**：不得在编排层主会话内编写/修改测试脚本与页面对象、不得跑 pytest、不得做根因分析与修复、不得做日志核查、不得做稳定性多轮执行——这些一律派发给对应子智能体（见上方★强制派发铁律）；
  - 严禁靠对话记忆判进度（一律读盘）；
  - 严禁改写/精简/概括任何阶段规范。

### 阶段顺序与各阶段读取文件（原文沿用编排关系）

各阶段子智能体启动后须按其 body 内联原文要求读取关联文件。各阶段读取关系（原文沿用）：

- **阶段一**（`phase1-requirements`）：内联 `phase1-requirements.md` 全文；按原文读 `sugon_web/case_specs/templates/base_case.md`、`sugon_web/case_specs/fixtures_index.md`、用户提供的 CSV 文件。**前置**：用户提供 CSV。**异常处理**：无。
- **阶段二**（`phase2-coding`）：内联 `phase2-coding.md` 全文；按原文读 `sugon_web/case_specs/prompts/test_case_codegen_prompt.md`、`sugon_web/case_specs/fixtures_index.md`、`sugon_web/case_specs/prompts/assertion_guidelines.md`、阶段一产出的 MD、`sugon_web/refrence/module_index.yaml`、被测模块前端工程代码；辅助脚本 `.claude/skills/test-script-dev/scripts/recon_page.py`（运行时侦察，按需）、`.claude/skills/test-script-dev/scripts/precheck.py`（静态门禁，进阶段三前必跑）。**前置**：阶段一完成。**异常处理**：无法定位被测模块前端工程代码时，按 `phase2-coding` body 中"匹配失败"的处理方式执行。
- **阶段三**（`phase3-execution`）：内联 `phase3-execution.md` 全文；按原文同时遵守 `.claude/agents/test-script-phases/phase2-coding.md` 的编码规范、读阶段一产出的 MD、`sugon_web/refrence/` 下被测模块前端工程代码；辅助脚本同上；诊断时按需读失败案例库 `.claude/skills/test-script-dev/references/failure_case_library.md`（命中已收录模式优先套用其根因方向）；判定最终通过前须按子智能体内的「Jenkins 对齐执行闸」追加一次对齐 `Jenkinsfile` 形态（并行无头）的执行。**前置**：阶段二完成（或用户提供现有脚本及对应 MD）。**异常处理**：用例失败在阶段内部按四步法（Reproduce→Isolate→Diagnose→Fix）处理，无需跨阶段跳转。
- **阶段四**（`phase4-log-analysis`）：内联 `phase4-log-analysis.md` 全文；按原文读阶段一产出的 MD。**前置**：阶段三完成。**异常处理**：见下方回退状态机。
- **阶段五**（`phase5-stability`）：内联 `phase5-stability.md` 全文；各轮执行按子智能体内的「Jenkins 对齐执行」对齐 `Jenkinsfile` 形态（并行无头）。**前置**：阶段四完成。**异常处理**：见下方回退状态机。

### 跨阶段回退状态机（架构新增·语义原文沿用）

> 回退**语义**完全沿用原 skill（阶段四"重要问题须返回阶段三修复"；阶段五"失败轮次含用例问题→返回阶段三修复，重新执行阶段四、阶段五，同一根因的用例问题最多修复 2 次"）。本节只把语义搬到编排层驱动，语义本身不改。

```
[阶段一] →done→ [阶段二] →done→ [阶段三] →done→ [阶段四]
                                                    │
                          重要问题/teardown ERROR    │ 仅非重要问题
                                ┌───────────────────┴──────────┐
                                ▼                              ▼
                          [回退阶段三]                      [阶段五]
                          (按计数器约束)                       │
                                │                   失败轮次含用例问题
                                └──────┐          ┌────────────┘
                                       ▼          ▼
                                  重新跑 [阶段四]→[阶段五]
                                       (按"同一根因最多修复 2 次"约束)
                                          │
                                   达标/缺陷/环境 → [总收尾]
```

- 阶段四 `phase4-log-analysis` 返回"返回阶段三修复"（重要问题/teardown ERROR）→ **先跑下方「回退派发硬闸门」`loop_gate.py`（带 `--case`），退出码 0 才**派发 `phase3-execution`（回退重入）→ 再派发 `phase4-log-analysis` → ……（退出码非 0 按闸门规则标记遗留问题并停止）
- 阶段五 `phase5-stability` 返回"返回阶段三修复"（失败轮次含用例问题）→ 同上（闸门带 `--case --rootcause`），并受"同一根因最多修复 2 次"约束；超过则按原文标记遗留问题并结束。
- 任一阶段返回"被迫中断"→ 停止派发，按本文「完成后输出」如实产出全局总结。

### 循环计数器持久化（架构新增·阈值与判定零改动）

因子智能体无状态、每次全新记不住轮次，下列原 skill 既有计数机制的"当前值"由本 Skill 落盘到运行报告**「循环计数区」**（架构新增的一个区块），每次派发回退前先读、派发后更新。**阈值与判定逻辑零改动，完全以子智能体内联的 `phase3-execution` / `phase5-stability` 原文为准**：

| 计数器（原文沿用，判定见原文） | 上限（原文沿用） |
|---|---|
| 单用例修复轮次 | 5 轮（触发进展奖励 → 7 轮） |
| 全局修复轮次 | 15 轮 |
| 状态冻结检测 | 连续 2 轮无变化 |
| 阶段五回退同一根因修复次数 | 最多 2 次 |

达上限 → 按原文规则标记"遗留问题"并停止回退；未达 → 派发并在子智能体完成后更新计数。


#### 回退派发硬闸门（架构新增·把"停止条件"从软约束升级为硬控制）

> **动机**：上表阈值原本写在子智能体正文里、靠其自觉遵守（软约束），弱模型长跑会无视上限继续试错（实测出现过阶段三多轮失控）。现把"要不要再来一轮"的决定权收回到**编排层**，用确定性脚本退出码强制裁决。**阈值与判定语义零改动**，闸门只是机器化地比对上表既有阈值。

- **每次准备回退派发 `phase3-execution`（或阶段五回退重入）之前，编排层必须先跑闸门脚本**：
  `python .claude/skills/test-script-dev/scripts/loop_gate.py <本次运行报告 md 路径> [--case <用例名>] [--rootcause <根因标识>]`
  - 回退某用例修复 → 带 `--case <用例名>`；阶段五同根因回退 → 加带 `--rootcause <根因标识>`；仅校验全局轮次 → 不带可选参数。
- **按退出码硬执行（不得由子智能体二次决定）**：
  - `0` → 允许派发：照常派发对应子智能体并在其完成后更新计数区。
  - `1` → **禁止派发**：编排层立即按原文规则把对应用例/分支标记为"遗留问题（轮次耗尽 / 状态冻结 / 同根因超限）"，停止该回退分支，**严禁再派发**。
  - `2` → **计数区缺失或无法解析，同样不放行**：先补全/修正运行报告「循环计数区」（这是抗压缩的硬约束——计数必须每轮真实落盘），再重跑闸门，通过后方可继续。
- **闸门是裁决、不是建议**：编排层不得在退出码非 0 时仍派发；这是消除"阶段三无限试错"的硬刹车，且因只读磁盘计数，**不受阶段三多轮修复触发上下文压缩的影响**。

### 按成本分级的隔离策略（架构新增，防"过度设计反而变慢"；成本口径原文沿用：低成本<15min / 高成本>15min）

| 场景 | 是否开独立子智能体 |
|---|---|
| 阶段一（上下文轻） | 可不隔离，本 Skill 主上下文直跑（仍须完整读 `phase1-requirements` body 原文执行） |
| 阶段二 | 隔离（派发 `phase2-coding`） |
| 阶段三（无论成本高低 / 是否首轮即过） | **一律隔离派发 `phase3-execution`，无例外**：高成本用例 / 进入多轮修复时**每用例一个 `phase3-execution` 子智能体**（本 Skill 遍历用例，子智能体内部不再派 subagent） |
| 阶段四 | 隔离（派发 `phase4-log-analysis`） |
| 阶段五 | 隔离（派发 `phase5-stability`） |

**铁律**：分级只决定"是否新开上下文"，**不决定"是否遵守规范"**——无论是否隔离，规范一律按子智能体内联原文执行。

修改测试脚本时，若 `Edit` 因 `old_string` 不唯一失败，严禁中断流程等待人工确认。按以下优先级自动恢复：

2. **使用 replace_all**：确认所有匹配处需相同修改时，改用 `replace_all=true`
3. **替代方案**：上述方法均不可行时，改用 `Write` 重写整个文件

`Edit` 和 `replace_all` 均失败时，必须使用 `Write` 作为最终降级方案；仅当 `Write` 也失败时，记录错误并继续下一步。严禁弹出确认对话框。

## 完成后输出（全局总结，面向人阅读）

**定位说明**：各阶段的明细（完成清单、问题清单、测试执行结果、经验沉淀等）已由各 phase 的"阶段完成时立即输出"逐阶段产出并写入运行报告，**本节不再重复这些明细**。本节是整次执行结束后，面向**人**的一段**全局总结**——让阅读者无需翻看各阶段明细，就能一眼掌握"这次干了什么、结果如何、能否投产、还有什么需要人处理、细节去哪看"。

**触发与口径**：所有阶段执行完毕并通过完成判定后输出，并追加写入运行报告文件末尾。内容须先 `Read` 运行报告文件后聚合生成，不依赖对话记忆；**严禁用本节替代任一阶段的立即输出**（两者并行，明细在阶段、总览在此）。

按以下四部分输出：

### 1. 总体结论

一句话给出本次执行的最终判定，让人立即知道结果。例如：
- ✅ `本次自动化用例编写完成并通过稳定性验证，可投入生产使用。`
- ⚠️ `用例已编写，但发现产品缺陷 N 处（需提交缺陷）/ 遗留问题 N 处（需人工介入），暂不可直接投产。`
- ❌ `本次执行未完成：{被迫中断的核心原因}。`

### 2. 执行概览

用一个总览表给出全局画像（不逐文件罗列，只给汇总数字）：

| 维度 | 内容 |
|---|---|
| 被测模块 / 需求来源 | 如：网络-负载均衡 / `requirements_csv/xxx.csv` |
| 场景总数 → 最终通过 | 如：2 → 2 |
| 稳定性验证 | 如：低成本 5 轮，通过 4/5（达标） |
| 产品缺陷 / 遗留问题 / 环境问题 | 如：0 / 0 / 1（各计数，0 也写明） |
| 五阶段状态 | 一/二/三/四/五：✅✅✅✅✅（或标注跳过/未通过） |

### 3. 风险与后续待办（人需关注）

仅列**需要人来处理**的事项，没有则写 `- 无，可直接投产`。例如：
- 产品缺陷：简述现象 + 复现要点，提示"请提交缺陷单"。
- 遗留问题：简述卡点 + 建议人工介入方向。
- 环境问题：简述受影响范围 + 建议优化的环境项。

### 4. 产物位置索引（细节去哪看）

指引阅读者到对应文件查看明细，**不复制明细内容**：

| 产物 | 位置 |
|---|---|
| 结构化需求 MD | `sugon_web/case_specs/{模块}/{需求}.md` |
| 测试脚本 | `sugon_web/testcase/{模块}/test_xxx.py` |
| 执行日志 | `logs/` 目录下对应日志文件 |
