# 阶段五：稳定性验证

## 一、执行总纲

本阶段对每个测试文件固定执行 **5 轮**稳定性验证，5 轮全部执行完毕后统一判定结果。5 轮执行过程中严禁中途修复、结束或跳转其他阶段。

**执行注意事项**

1. **全量执行约束**：必须完整执行 5 轮，无论中间轮次结果如何，严禁提前终止。
2. **禁止中途修复**：5 轮执行完毕前，发现用例问题也不得返回阶段三修复，须等 5 轮全部执行完毕后统一处理。
3. **MD 文档保护**：验证过程中严禁修改阶段一产出的 MD 需求文档，除非确认 MD 本身存在转换错误。
4. **日志规范**：每次运行 pytest 前，通过 `Bash` 定义 `LOG_FILE` 变量，并传入 `--log-file=$LOG_FILE --log-file-level=DEBUG`。严禁执行不带 `--log-file` 的 pytest 命令。
5. **失败处理**：每轮执行后若存在失败用例，按阶段三四步法分析根因并记录，但**仅记录、不修复、不阻断后续轮次**。

## 二、"环境问题"的明确定义

1. **定义**：某用例因环境波动失败且被判定为**环境问题**时，本轮 pytest 仍须完整执行所有用例（不得中途终止）。待本轮全部执行完毕后，在结果分析阶段将该用例标记为"环境问题"。
2. **核心原则**："环境问题"只能在结果分析阶段标记，严禁以任何方式修改测试脚本来绕过失败，包括但不限于：`pytest.skip()`、`@pytest.mark.skip`、`try/except` 捕获异常后既不处理也不重新抛出。
3. **流程**：pytest 完整执行本轮所有用例 → 某用例因环境波动失败 → AI 分析根因确认为环境问题 → 记录失败原因与环境波动特征 → 标记为"环境问题" → 继续执行下一轮。

## 三、执行与判定规则

### 3.1 执行规则

- 固定执行 **5 轮**，每轮执行该文件的全部用例，不得遗漏。
- 每轮执行前按日志规范定义 `LOG_FILE`。
- 某轮中存在失败用例时，分析根因并记录，然后继续执行下一轮。

### 3.2 判定决策树

必须在5 轮稳定性验证全部执行完毕后，再按以下决策树判定。

**判定前说明**：
- "失败轮次中有 用例问题"指：只要任意一轮的任意一个失败用例，其根因判定为**用例问题**，即触发该分支。
- "失败轮次中有 产品缺陷"指：只要任意一轮的任意一个失败用例，其根因判定为**产品缺陷**，即触发该分支。
- "遗留问题"指阶段三因轮次耗尽或状态冻结而强制标记的问题，正常情况下不参与阶段五验证；如带入则按用例问题路径处理（返回阶段三）。
- "通过轮次"指：该轮 pytest 执行结果为 PASSED，即该轮所有用例均执行成功，无任何 FAILED 用例。
- "失败轮次"指：该轮存在根因为用例问题/产品缺陷/环境问题/遗留问题的 FAILED 用例，即该轮 pytest 执行结果为 FAILED。
- 无论最终判定结果如何，均需在问题总结中如实记录所有失败轮次的根因。

```
失败轮次中有 用例问题？
  ├─ 是 → 【验证不通过】返回阶段三修复用例
  │         （按阶段三四步法修复，重新执行阶段四、阶段五。同一根因的用例问题最多修复 2 次，
  │          超过 2 次仍失败的，记录为遗留问题并结束本阶段任务）
  └─ 否 → 通过轮次 ≥ 3 次？
       ├─ 是 → 【验证通过】阶段五结束任务，稳定性验证通过
       └─ 否 → 失败轮次中有 产品缺陷？
                ├─ 是 → 【验证不通过】阶段五结束任务，醒目提示"发现产品缺陷，请提交缺陷"
                │         （若失败轮次中同时含环境问题，提示"环境问题及产品缺陷"）
                └─ 否 → 【验证不通过】阶段五结束任务，提示根因为环境问题
                          （已排除用例问题和产品缺陷，剩余失败轮次即为纯环境问题）
```
