# 阶段五：稳定性验证


```
## 阶段五执行总纲

本阶段对阶段二生成的所有测试文件执行多轮稳定性验证，不得遗漏任何文件。每轮运行须严格遵守阶段三的执行规范与修复纪律，按通过标准统计有效通过次数，直至满足稳定性验证通过标准，即视为完成阶段五（整个工作流任务完成）。

**执行注意事项**

1. **自主运行约束**：本阶段全程自主运行，严禁停下来询问用户。循环中断会浪费已执行的进度，所有修复/检查决策自主完成。
2. **MD 文档保护**：验证过程中严禁修改阶段一产出的 MD 需求文档，除非确认 MD 本身存在转换错误。
3. **日志规范**：每次运行 pytest 前，必须通过 `Bash` 定义 `LOG_FILE` 变量，并传入 `--log-file=$LOG_FILE --log-file-level=DEBUG`。严禁执行不带 `--log-file` 的 pytest 命令。日志命名规则同阶段三（按测试 py 文件名命名，如 `sugon_web/logs/test_xxx.log`）。
4. **失败处理**：若用例执行失败，严格按阶段三的四步法（Reproduce→Isolate→Diagnose→Fix）分析根因并处理。根因分类及处理方式：环境问题跳过、产品缺陷标记、用例问题修复。修复纪律与判定规则同阶段三。
5. **完成条件**：运行 N 轮稳定性验证，统计有效通过次数。当通过次数达到 ⌈N × 2/3⌉ 次时，即视为该测试文件稳定性验证通过。所有测试文件均通过后，阶段五完成。
```

**关于"跳过"的明确定义**

1. **定义**：当某用例因环境波动失败且被判定为**环境问题**时，本轮 pytest 仍须完整执行所有用例（不得中途终止）。待本轮全部执行完毕后，在结果分析阶段将该失败用例标记为"环境问题跳过"。稳定性验证的目标是检验脚本本身是否可靠，环境波动属于外部不可控因素，因此只要本轮不存在未修复的用例问题，即视为本轮通过，继续执行下一轮。
2. **核心原则**："跳过"只能在结果分析阶段标记，严禁以任何方式修改测试脚本来绕过失败，包括但不限于：`pytest.skip()`、`@pytest.mark.skip`、以及 `try/except` 捕获异常后既不处理也不重新抛出（掩盖真实失败）。
3. **正确处理流程**：pytest 完整执行本轮所有用例 → 某用例因环境波动失败 → AI 分析根因确认为环境问题 → 记录该用例失败原因与环境波动特征 → 在结果中标记该用例为环境问题跳过 → 本轮视为通过（环境波动非脚本问题，不计入失败） → 继续执行下一轮。

---

**稳定性验证通过标准**

对每个测试文件执行 **N** 轮稳定性验证，**N 的取值范围为 3 ≤ N ≤ 10**（默认推荐 N = 5，可根据测试耗时与环境波动情况灵活调整）。

1. **单次运行判定**：一轮运行结束后，若所有用例均达到可接受状态（用例问题已修复、产品缺陷已标记、环境问题已跳过），则该轮记为**通过**；若存在未修复的用例问题，则该轮记为**未通过**。
2. **通过率计算**：通过次数 / N。环境问题和产品缺陷不影响单次运行判定——只要不存在未修复的用例问题，该轮即视为通过。
3. **通过门槛**：通过次数必须达到 **⌈N × 2/3⌉** 次（向上取整），即通过率不低于约 66.7%。当某测试文件的通过次数达到上述最低通过次数时，即视为该文件稳定性验证通过；所有测试文件均通过后，阶段五完成。

**稳定性判定规则**

| 失败根因 | 处理方式 |
|---|---|
| 环境问题 | 记录失败原因与环境波动特征，pytest 完整执行完本轮所有用例，该失败用例在结果中标记为环境问题跳过，本轮仍视为通过（只要没有未修复的用例问题），继续执行下一轮 |
| 产品缺陷 | 醒目提示"**发现产品缺陷，请提交缺陷**"，附复现步骤 + 关键日志 + 截图，该轮运行仍视为"通过"（产品缺陷已标记），继续下一轮 |
| 用例问题 | 直接修复代码，修复后重新运行验证；若修复后该轮仍因同一根因失败，禁止在同一根因假设下连续尝试超过 2 次 |

---

**循环规则**

1. 选择运行轮次 N（3 ≤ N ≤ 10，推荐 5），对阶段二生成的每个测试文件依次执行 N 轮
2. 每轮执行完整测试脚本，不得遗漏任何用例
3. 若本轮失败 → 按阶段三四步法分析根因
   - 用例问题 → 修复代码 → 重新执行本轮以验证修复效果；若修复后本轮通过，则计入通过次数；若仍失败，禁止在同一根因假设下连续尝试超过 2 次
   - 环境问题 → 按阶段三四步法分析根因并确认为环境问题 → 记录环境波动特征 → pytest 完整执行完本轮 → 参照上方"关于跳过的明确定义"在结果中将该用例标记为环境问题跳过 → 本轮视为通过 → 继续执行下一轮
   - 产品缺陷 → 标记后继续执行下一轮（该轮视为"通过"）
4. 统计通过次数，达到 ⌈N × 2/3⌉ 次即视为该文件通过
5. 所有测试文件均达到通过门槛 → 阶段五完成

**示例**：N = 5，第2轮修复后通过、第4轮修复后仍失败
```
第1轮：PASSED
第2轮：FAILED（用例问题：断言逻辑错误）→ 修复代码 → 重跑：PASSED
第3轮：PASSED
第4轮：FAILED（用例问题：定位方式错误）→ 修复代码 → 重跑：FAILED（同一根因，已达2次尝试上限）→ 记为未通过
第5轮：PASSED

实际通过次数：4 次（第1、2轮修复后、3、5轮），最低门槛 ⌈5 × 2/3⌉ = 4 次
→ 通过次数达到最低门槛 → 该文件稳定性验证通过 ✅
```
