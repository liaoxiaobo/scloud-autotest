# 阶段一：测试需求转换与校验

## 第一部分：测试需求转换（CSV → MD）

### 执行提示词

> 第一部分执行内容：根据以下提示词把测试需求的 CSV 文件转换为自动化测试需求的 MD 文件。


````
requirements_csv/目录下存放着本次编码任务的测试需求的csv文件，请你阅读这个测试需求的csv文件，把它转换成一个标准的、结构化的md文件，这个md文件用于AI生成UI自动化测试用例脚本的需求文档，通过该文档快速且准确地理解当前编写自动化测试脚本的需求，md 输出样式模板请参考 sugon_web/case_specs/templates/base_case.md 文件的【规范约束】与【推荐填写示例】来写。同时你必须严格遵守以下注意事项与规范：

注意事项：
1. `sugon_web/case_specs/templates/base_case.md` 文件只是一个初稿，可能信息不全，你可以适当增加，但只增加有必要的重要内容，无关紧要的内容不要增加，不要让该文档的篇幅太大或过于臃肿。
2. 你生成的 md 文件的名称需要参考 `sugon_web/case_specs/prompts/test_case_codegen_prompt.md` 文件中定义的命名规范来命名一个简短的英文名称。
3. 你生成的 md 文件，需要放到 `sugon_web/case_specs/` 目录下对应的业务模块目录中，如网络模块的则放在：`sugon_web/case_specs/network`
4. 你在转换的 md 文件中，需要新增注意事项：实现测试步骤或者前置条件的自动化脚本，必读参考 `sugon_web/case_specs/fixtures_index.md`，查阅 fixture 强制约束和速查表，确认框架中是否已有可复用的 fixture，不要针对已有的 fixture 进行重复封装。重复封装会增加维护成本并可能导致用法不一致。

**多场景处理规范（一个 CSV 对应一个 MD）：**

若 CSV 中包含多条测试用例（多行），必须将所有用例合并输出到**单个** MD 文件中，不要拆分为多个 MD 文件。拆分会导致需求分散，难以统一管理和追溯。

1. **提取公共前置条件（强制）**：将各用例中重复的前置条件提取到统一的"前置条件"章节，只保留一份
   - 必须识别可复用资源：如 4 台虚机、SLB V2 实例等跨场景共享资源，在"前置条件"中声明
   - 必须标注共享标识：在资源描述中注明"本资源在多个场景中复用"
   - 不要在每个场景中重复声明相同的前置条件。重复声明会增加冗余且容易遗漏。
2. **场景化测试步骤**：在"测试步骤"章节中用二级标题按场景分组：
   ```markdown
   ### 场景1：{用例名称1}（用例编号：xxx）
   #### 步骤1：...
   - 操作：...
   - 预期：...
   ```
3. **场景依赖标注**：若某场景依赖其他场景执行，必须在前置条件或场景开头注明，例如：`> 依赖：场景1（用例436746）已执行完成`

执行测试命令的编写规范：
1. CSV 文件中若测试步骤写明了具体执行的命令，则需要把这些命令转换后写进 md 文件中。因为要避免在自动化用例执行过程中出现长时间占用会话连接，所以在转换命令时必须修改成使用 nohup 后台执行命令。
2. CSV 文件中的同一组操作若需要执行多个执行命令才能完成的，则使用 `&&` 合并成同一行命令，如：`cd /root/test/ && echo "this is ecs1" >> index.html`
3. CSV 文件中有些命令在执行后，系统不会立刻返回执行结果，这种命令则必须增加轮询等待，直至命令输出符合预期的正确结果，设置最长等待时长为 60 秒，如：`nohup python3 -m http.server 8080 > /dev/null 2>&1 &` 这类命令则需要轮询等待。
4. CSV 文件中若有【打开虚拟机 vnc】、【打开虚拟机 vnc 控制台】、【打开虚拟机 vnc 窗口】等类似的操作虚拟机 VNC 的描述，则在 md 文件中必须改写为：通过 `ssh_vm` fixture 连接虚拟机后台，使用 `ssh_vm.connect(vm_mfip)` 建立 SSH 连接，再调用 `ssh_vm.run()` 执行命令。
5. CSV 文件中若有【ssh 连接虚拟机系统后台】、【ssh 连接虚拟机】、【连接虚拟机后台】等类似的描述，则在 md 文件中必须改写为：使用 `ssh_vm` fixture（`sugon_web/conftest.py`）提供的 SSH 实例，调用其 `connect()`、`run()`、`ping()` 等方法（定义于 `sugon_web/common/ssh.py`）。
6. CSV 文件中若有【本地客户端 ssh 连接环境和访问】、【ssh 连接环境物理机后台时】、【连接节点后台】等类似的描述（如：本地客户端通过 fip 访问负载均衡，执行命令：`curl http://$lb_fip:8080/index.html`），则在 md 文件中必须改写为：使用 `ssh_host` fixture 用于直接连接测试环境的系统后台。

用例执行完成后的测试数据清理流程：

在面对一些长流程的测试用例时，清理数据通常有依赖顺序要求（如先移除关联资源再删除父资源），否则会删除失败。以下是一个负载均衡场景的清理顺序**示例**，供参考：

> **示例：** 负载均衡（LB）相关资源的清理顺序
> 1. 将 lb 中的资源池成员（虚拟机）从 lb 中移除
> 2. 删除 lb（监听器）
> 3. 删除 slb（负载均衡实例）
> 4. 删除虚拟机
> 5. 删除 vpc

**实际清理顺序应根据当前 CSV 测试需求中涉及的资源依赖关系来确定。** 转换 md 文档时，需分析 CSV 中创建的资源类型及其依赖关系，按"先解除关联、后删除父资源"的原则定义清理流程。不同场景（如数据库、存储、网络等）的清理顺序可能完全不同，请勿照搬上述示例。
````

## 第二部分：需求文档校验

> 转换完测试需求的 md 文件后，还不能直接使用，必须检查 md 文件是否正确、表达是否清晰、是否存在错误或歧义。若有问题直接修改，直至无误。

**执行要点：**

- **完整性检查**：逐段检查 MD 文件是否完整、准确地表达了 CSV 中的测试意图
  - 测试步骤是否完整无遗漏，预期结果是否明确可验证
  - 边界条件是否在 MD 中体现
- **命令规范检查**：检查命令转换是否符合第一部分的编写规范
  - 后台执行命令是否使用 nohup
  - 同一组多命令是否用 && 合并成一行
  - 执行后不会立刻返回结果的命令，是否增加了轮询等待（最长 60 秒）
- **fixture 改写检查**：检查 VNC / SSH / 本地客户端操作描述是否已按规范改写
  - 【打开虚拟机 vnc】等操作 → 通过 ssh_vm fixture 连接虚拟机后台执行
  - 【ssh 连接虚拟机系统后台】等操作 → 使用 ssh_vm fixture
  - 【本地客户端 ssh 连接环境】等操作 → 使用 ssh_host fixture
- **清理顺序检查**：检查测试数据清理流程顺序是否正确（是否按照测试需求的 CSV 文件中定义的顺序）
- **脚本可执行性预判**：检查以下内容是否已在需求文档中明确，若缺失或不明确直接补充
  - **关键路径覆盖**：明确每个测试步骤对应的脚本操作和验证结果
  - **断言策略**：明确每个关键步骤使用页面元素断言 / SSH 后端验证 / 两者结合
  - **测试数据策略**：资源名称使用 `random_data()`，批量创建使用 fixture 的 `count` 参数
  - **清理策略**：资源清理顺序按照 CSV 文件中定义的清理顺序来写
- 若发现缺失、歧义或不明确，直接在 MD 文档中补充完善，无需询问

**循环规则：** 按上述检查项逐项检查 → 发现不符合 → 修改 MD 文档 → 重新检查 → 直至全部符合。
- **遵循通用循环约定，严禁停下来询问用户**，所有检查发现的问题自主修改
- 直至全部检查项均通过，方可进入下一阶段
