# 阶段三：执行用例与修复错误（自主循环）


**执行前置要求（每次 pytest 必须遵守）：**

- 每次执行 pytest 前，先通过 `Bash` 按命名规则定义 `LOG_FILE` 变量，再传入 `--log-file=$LOG_FILE --log-file-level=DEBUG`
- 日志目录：`sugon_web/logs/`（不存在则自动创建）
- 命名规则：按实际执行的测试 py 文件名命名，如 `sugon_web/logs/test_lb_v2_tcp_scenario.log`
- 覆盖策略：同一用例多次执行使用相同路径，日志自动覆盖，不产生冗余文件
- 严禁执行不带 `--log-file` 的 pytest 命令，因为没有日志文件就无法进行后续的根因分析和日志核查
- 查看错误日志时，必须注明日志文件路径：`- 日志文件：{完整路径}`

执行新编写的自动化测试用例，验证用例是否能正常跑通。若用例执行失败，必须严格按照以下四步法修复。

**修复纪律（修复前必读）：**
- 严禁盲目修改代码，因为盲目修改可能引入回归或掩盖真实根因
- 严禁在同一根因假设下连续尝试超过2次，因为多次在同一错误假设下尝试会浪费执行时间且无法解决问题

**第一步：复现（Reproduce）**
- 重新阅读需求文档（阶段一产出的 MD 文件）中对应步骤的预期行为。
- 从 `sugon_web/logs/` 目录定位对应日志文件，查看 pytest 错误日志的完整堆栈，确认错误类型：TimeoutError / AssertionError / 定位类错误 / SSH 连接错误 / 其他。
- 如果失败截图存在，查看截图对比预期页面状态 vs 实际页面状态。
- 记录失败现象，并在首次失败后快速补充执行 1 次以确认是否稳定复现。
- 截图与日志交叉验证：若截图显示的状态与日志报错信息冲突，以截图和日志事实为准，不盲信单一信息源。

**第二步：隔离（Isolate）**
根据错误类型执行对应的隔离动作（每种类型只执行对应动作，不要全部执行）：
- 若 TimeoutError：检查是否在 wait_for_load_state('networkidle') 之前执行了操作；用 .count() 验证 locator 是否匹配到 0 个或多个元素；检查是否有异步加载未完成。
- 若 AssertionError：对比预期值和实际值，确认是"数据被污染"（如资源名称冲突）还是"断言逻辑错误"（如期望值写死但实际是动态的）。
- 若定位类错误：使用 page.locator(your_selector).all() 列出当前页面所有匹配元素，对比实际文本与预期文本；确认是否在正确的 dialog / tab / 表格范围内定位。
- 若 SSH 连接错误：检查 ssh_host.run() 或 ssh_vm.run() 的命令语法和目标节点可达性，确认资源是否已创建成功；同时核对需求 MD 文档中定义的 SSH 命令是否被正确转换。
- 若其他错误：检查环境状态（如测试环境是否重启、节点是否可用）。

**第三步：诊断（Diagnose）**

> 诊断前必须先读取 `sugon_web/case_specs/prompts/test_failure_analysis_prompt.md` 全文，严格按照该文件中定义的分析原则、输出格式和约束进行根因判定。

- 区分报错表象和真实根因：TimeoutError / AssertionError / 定位失败等只是现象，不是根因。必须先还原事实（页面实际状态、接口返回值、资源实际存在性），再下结论。
- 基于隔离结果，形成单一、明确的失败根因假设（不要罗列多个可能性，只给出最可能的一个）。
- 根因结论只能是以下 3 种之一：**环境问题** / **用例问题** / **产品缺陷**。
- 验证假设：注释掉无关步骤，仅保留"失败步骤 + 其直接前置条件"，重新执行验证。
- 排除环境干扰：如果失败不稳定（含第一步补充执行后现象不一致），重跑 3 次确认是否为环境问题（3 次中 ≥2 次通过则判定为环境问题，记录后跳过，继续执行其他用例）。
- 按 `sugon_web/case_specs/prompts/test_failure_analysis_prompt.md` 的输出格式输出分析结果：结论（根因分类 + 摘要 + 置信度）、关键证据、排除项、修复建议。
- 若日志与截图信息不足以形成明确根因假设，可补充查阅对应前端工程代码确认页面结构与渲染逻辑。

**第四步：修复（Fix）**

根据第三步诊断的根因分类执行对应策略：

- **若根因为用例问题**：按以下优先级修复代码：
  1. 定位方式错误 → 修正 locator（如页面文案变更、应使用 role 而非 CSS）
  2. 等待时机错误 → 增加/修正 wait_for_load_state / wait_for_selector / wait_for_source_complete
  3. 测试数据错误 → 修正数据准备或断言值（如使用 random_data() 避免名称冲突）
  4. 业务逻辑变更 → 更新测试步骤以匹配最新产品逻辑
  - 只修复根因，不掩盖症状。不要简单地增加 page.wait_for_timeout()，而应使用正确的等待策略。
  - 修复后必须执行完整用例（不是只跑失败步骤），确保修复没有引入回归。
  - 如果修复后仍然失败，必须回到第一步重新分析，严禁在同一根因假设下连续尝试超过 2 次。

- **若根因为产品缺陷**：不修复代码，在对话框中醒目提示"**发现产品缺陷，请提交缺陷**"，附复现步骤 + 关键日志 + 截图，然后继续执行其他用例（若仅一个用例则结束本阶段）。

- **若根因为环境问题**：在对话框中记录该用例为"环境问题已跳过"并标注原因，跳过该用例，继续执行其他用例（若仅一个用例则结束本阶段）。

修改后重新运行用例验证。如此循环多次直至所有用例均达到可接受状态（用例问题已修复、产品缺陷已标记、环境问题已跳过）。注意：这是一个长时间的任务，请你务必要多次修复→验证→修复，直至所有问题都处理完毕。在此期间我没有在电脑旁边，你无需向我确认什么。阶段三修复循环结束之后，在对话框中输出一个结构化的检查清单，各类根因的填写规则如下：
- **用例问题**：修复方案写具体修改内容，是否修复填"是"，修复后是否验证通过填"是/否"。
- **产品缺陷**：修复方案写"产品缺陷，已提交缺陷"，是否修复填"否（产品缺陷）"，修复后是否验证通过填"不适用"。
- **环境问题**：修复方案写"环境问题，已跳过"，是否修复填"否（环境问题）"，修复后是否验证通过填"不适用"。
检查清单字段包括但不限于：序号、用例名称、失败现象、根因分类、修复方案、是否修复、修复后是否验证通过、备注。
