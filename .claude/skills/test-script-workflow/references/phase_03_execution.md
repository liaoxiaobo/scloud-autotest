# 阶段三：执行用例与修复错误（自主循环）

> **设计哲学**：给足修复机会，但绝不死磕；检测无意义循环，而非掐表计时。

---

## 一、执行前置要求（每次 pytest 必须遵守）

- 每次执行 pytest 前，先通过 `Bash` 按命名规则定义 `LOG_FILE` 变量，再传入 `--log-file=$LOG_FILE --log-file-level=DEBUG`
- 日志目录：`sugon_web/logs/`（不存在则自动创建）
- 命名规则：按实际执行的测试 py 文件名命名，如 `sugon_web/logs/test_lb_v2_tcp_scenario.log`
- 覆盖策略：同一用例多次执行使用相同路径，日志自动覆盖，不产生冗余文件
- 严禁执行不带 `--log-file` 的 pytest 命令，因为没有日志文件就无法进行后续的根因分析和日志核查
- 查看错误日志时，必须注明日志文件路径：`- 日志文件：{完整路径}`

---

## 二、执行提示词

````
执行阶段二生成的所有自动化测试用例（如有多个文件则逐一执行），不得遗漏任何文件，验证用例是否能正常跑通。若用例执行失败，必须严格按照以下四步法修复。
````

## 三、修复纪律（修复前必读）

- 严禁盲目修改代码，因为盲目修改可能引入回归或掩盖真实根因
- 严禁在同一根因假设下连续尝试超过2次，因为多次在同一错误假设下尝试会浪费执行时间且无法解决问题

**常见误判模式警示**：以下行为历史上多次被错误归为"用例问题"，实际应重新判定：

1. 修改 CSV/MD 中的端口、协议、权重等业务参数 → 应判定为产品缺陷或环境问题
2. 移除 @submenu 等已有装饰器 → 应判定为环境问题（抽屉遮挡等）
3. 修改 pages/ 下已有公共方法的定位逻辑 → 应判定为页面对象缺陷
4. 放宽断言条件（如把"等于"改为"包含"）→ 应判定为产品缺陷

---

## 四、防循环保护机制

以下三条机制用于防止修复循环陷入无意义死循环导致 token 无限消耗，同时确保正常修复不被中断：

### 4.1 单用例累计修复轮次上限

单个用例无论根因假设如何变化，累计修复轮次达到 **5 轮**后仍未修复：

- 强制标记为"遗留问题（用例问题-轮次耗尽）"
- 停止对该用例的继续修复，继续执行其他用例
- 在问题清单中注明：该用例已耗尽 5 轮修复上限，建议人工介入分析
- **正常用例通常 1~2 轮修复，5 轮是 2~3 倍余量，不会削弱正常修复能力**

### 4.2 状态冻结检测

若连续 **2 轮**修复后，同一用例的失败现象、根因类型与上一轮完全相同：

- 说明修复陷入停滞（在同一问题上反复做相同修改）
- 强制标记为"遗留问题（用例问题-状态冻结）"
- 停止继续修复，继续执行其他用例

### 4.3 全局修复轮次上限

整个阶段三的累计修复轮次达到 **15 轮**后：

- 若仍存在未修复的用例问题，全部标记为"遗留问题（全局轮次耗尽）"
- 停止修复循环，输出完整问题清单
- 正常进入阶段四（日志分析）和阶段五（稳定性验证）
- 遗留问题不参与阶段五验证

## 五、四步修复法

### 第一步：复现（Reproduce）

- 重新阅读需求文档（阶段一产出的 MD 文件）中对应步骤的预期行为。
- 从 `sugon_web/logs/` 目录定位对应日志文件，查看 pytest 错误日志的完整堆栈，确认错误类型：TimeoutError / AssertionError / 定位类错误 / SSH 连接错误 / 其他。
- 如果失败截图存在，查看截图对比预期页面状态 vs 实际页面状态。
- 记录失败现象，并在首次失败后快速补充执行 1 次以确认是否稳定复现。
- 截图与日志交叉验证：若截图显示的状态与日志报错信息冲突，以截图和日志事实为准，不盲信单一信息源。

### 第二步：隔离（Isolate）

根据错误类型执行对应的隔离动作（每种类型只执行对应动作，不要全部执行）：

- 若 TimeoutError：检查是否在 wait_for_load_state('networkidle') 之前执行了操作；用 .count() 验证 locator 是否匹配到 0 个或多个元素；检查是否有异步加载未完成。
- 若 AssertionError：对比预期值和实际值，确认是"数据被污染"（如资源名称冲突）还是"断言逻辑错误"（如期望值写死但实际是动态的）。
- 若定位类错误：使用 page.locator(your_selector).all() 列出当前页面所有匹配元素，对比实际文本与预期文本；确认是否在正确的 dialog / tab / 表格范围内定位。
- 若 SSH 连接错误：检查 ssh_host.run() 或 ssh_vm.run() 的命令语法和目标节点可达性，确认资源是否已创建成功；同时核对需求 MD 文档中定义的 SSH 命令是否被正确转换。
- 若其他错误：检查环境状态（如测试环境是否重启、节点是否可用）。

### 第三步：诊断（Diagnose）

> 诊断前必须先读取 `sugon_web/case_specs/prompts/test_failure_analysis_prompt.md` 全文，严格按照该文件中定义的分析原则、输出格式和约束进行根因判定。

- 区分报错表象和真实根因：TimeoutError / AssertionError / 定位失败等只是现象，不是根因。必须先还原事实（页面实际状态、接口返回值、资源实际存在性），再下结论。
- 基于隔离结果，形成单一、明确的失败根因假设（不要罗列多个可能性，只给出最可能的一个）。
- 根因结论只能是以下 3 种之一：**环境问题** / **用例问题** / **产品缺陷**。（遗留问题由防循环保护机制在阶段三结束时统一标记，不属于单次失败的根因判定）
- 判定为【用例问题】之前，必须先明确排除【产品缺陷】和【环境问题】的可能，并给出排除依据。禁止在缺乏排除证据的情况下默认归类为【用例问题】。
- 验证假设：注释掉无关步骤，仅保留"失败步骤 + 其直接前置条件"，重新执行验证。
- 排除环境干扰：如果失败不稳定（含第一步补充执行后现象不一致），重跑 3 次确认是否为环境问题（3 次中 ≥2 次通过则判定为环境问题，记录后跳过，继续执行其他用例）。
- 按 `sugon_web/case_specs/prompts/test_failure_analysis_prompt.md` 的输出格式输出分析结果：结论（根因分类 + 摘要 + 置信度）、关键证据、排除项、修复建议。
- 若日志与截图信息不足以形成明确根因假设，可补充查阅对应前端工程代码确认页面结构与渲染逻辑。

### 第四步：修复（Fix）

Fix 前必须回读 Diagnose 结论，确认修改与根因匹配。

**【修复前强制自检】（必须逐条输出到对话框）**

```
□ 1. 触及 CSV/MD 业务参数？______（是 → 禁止修复，回 Diagnose。脚本执行失败不是修改业务参数的理由，除非已确认 MD 本身存在转换错误）
□ 2. 触及 common/ 或 refrence/ 公共代码？______（是 → 禁止修复）
□ 3. 触及 pages/ 已有定位逻辑？______（是 → 禁止修复，回 Diagnose。若页面对象确有缺陷，应记录为页面对象修复项，而非在用例中绕过）
□ 4. 仅涉及 test_*.py 和必要页面对象？______（否 → 禁止修复，回 Diagnose）
```

【Fix 前误判检查】对照上方"常见误判模式警示"逐条核验：若本次修改落入①~④任一类，回 Diagnose 重新分类。

根据第三步诊断的根因分类执行对应策略：

- **若根因为用例问题**：按以下优先级修复代码：
  1. 定位方式错误 → 修正 locator（如页面文案变更、应使用 role 而非 CSS）
  2. 等待时机错误 → 增加/修正 wait_for_load_state / wait_for_selector / wait_for_source_complete
  3. 测试数据错误 → 修正数据准备过程中的错误（如使用 random_data() 避免名称冲突）
  4. 业务逻辑变更 → 更新测试步骤以匹配最新产品逻辑

  用例问题修复纪律：
  - 只修复根因，不掩盖症状。不要简单地增加 page.wait_for_timeout()，而应使用正确的等待策略。
  - 修复后必须执行完整用例（不是只跑失败步骤），确保修复没有引入回归。

- **若根因为产品缺陷**：不修复代码，在对话框中醒目提示"**发现产品缺陷，请提交缺陷**"，附复现步骤 + 关键日志 + 截图，然后继续执行其他用例（若仅一个用例则结束本阶段）。

- **若根因为环境问题**：在对话框中记录该用例为"环境问题已跳过"并标注原因，跳过该用例，继续执行其他用例（若仅一个用例则结束本阶段）。

## 六、自主修复循环规则

- 执行失败 → 按四步法分析（第三步必须读取 `sugon_web/case_specs/prompts/test_failure_analysis_prompt.md`）→ 根据根因分类修复/标记/跳过 → 重新运行 → 循环
- **遵循通用循环约定，严禁停下来询问用户**，因为循环中断会浪费已执行的进度，所有修复决策自主完成
- 直至所有用例均达到可接受状态（用例问题已修复、产品缺陷已标记、环境问题已跳过、遗留问题已标记），方可进入下一阶段

### 6.1 每轮执行后输出格式

修改后重新运行用例验证，按上述规则循环执行。每轮执行后须按下方格式输出对话框反馈：

```
---
第N轮执行结果：FAILED/PASSED

【失败现象】
{ pytest 失败的错误摘要，含具体报错行和异常类型 }
- 复现次数：{ 连续复现 N 次 }
- 日志文件：{ 对应的日志文件路径 }

【根因分析】
- 根因类型：环境问题 / 用例问题 / 产品缺陷
- 置信度：高 / 中 / 低
- 隔离结论：{ 隔离后剩余的可能，如"定位方式错误/等待时机错误/数据冲突/断言逻辑错误"等 }
- 分析过程：{ 为什么判定为该类型，关键证据；已排除产品缺陷和环境问题的依据 }

【修复方案】
{ 针对用例问题的具体修复动作；如为环境问题或产品缺陷则写"无需修复" }

【修复后状态】
- 用例问题 → 已修复，立即自动重试
- 环境问题 → 环境问题已跳过，继续执行其余用例
- 产品缺陷 → 已提示产品缺陷，记录后继续执行其余用例
---
```

### 6.2 修复循环结束后的问题清单

循环全部结束后，汇总输出本轮问题清单：

| 序号 | 用例名称 | 失败现象 | 根因分类 | 修复方案 | 是否修复 | 验证结果 | 备注 |
|---|---|---|---|---|---|---|---|

填写规则：
- **用例问题**：修复方案写具体修改内容；是否修复填"是"；验证结果填"是/否"。
- **产品缺陷**：修复方案写"产品缺陷，已提交缺陷"；是否修复填"否（产品缺陷）"；验证结果填"不适用"。
- **环境问题**：修复方案写"环境问题，已跳过"；是否修复填"否（环境问题）"；验证结果填"不适用"。
- **遗留问题**：修复方案写"轮次耗尽/状态冻结/全局上限，建议人工介入分析"；是否修复填"否（遗留问题）"；验证结果填"不适用"。（遗留问题不是单次失败的根因判定结果，而是防循环保护机制触发后的强制标记）

## 阶段完成输出

本阶段结束（正常完成或被迫中断）时，在对话框中输出：

1. **状态标题**
   - 正常完成 → `阶段三任务已完成`
   - 被迫中断 → `阶段三任务被迫中断：{主要原因}`。如有深层根因则补充，无则省略。

2. **完成清单**

汇总每个测试文件的执行结果与修复轮次，按以下表格输出：

| 测试文件 | 执行结果统计 | 修复轮次 | 产品缺陷数 | 环境问题数 | 遗留问题数 | 日志文件路径 |
|---|---|---|---|---|---|---|
| `test_xxx.py` | Passed N / Failed N / Skipped N | N | N | N | N | `sugon_web/logs/test_xxx.log` |

- **修复轮次**：指该测试文件在整个阶段三中的累计修复尝试次数（含所有用例的各轮修复之和）。无修复经历的测试文件记为 0，有修复经历的记为实际轮次。
