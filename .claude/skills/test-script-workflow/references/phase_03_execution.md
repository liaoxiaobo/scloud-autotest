## 一、执行前置要求(每次 pytest 必须遵守)

- 每次执行 pytest 前,先通过 `Bash` 按命名规则定义 `LOG_FILE` 变量,再传入 `--log-file=$LOG_FILE --log-file-level=DEBUG`
- 日志目录:`sugon_web/logs/`(不存在则自动创建);命名按测试 py 文件名,如 `sugon_web/logs/test_lb_v2_tcp_scenario.log`;同名覆盖
- 严禁执行不带 `--log-file` 的 pytest 命令

**首次执行前的静态门禁(强制,零执行成本拦截机械违规)**:

- 阶段二脚本就绪、**首次执行 pytest 之前**,先跑一次静态门禁脚本(黑盒,先 `--help`):
  `python .claude/skills/test-script-workflow/scripts/precheck.py <本次测试文件或目录> --expected-tests <CSV/MD 场景数>`
- 门禁检出"测试层 locator/expect/XPath、固定等待、测试方法体 try/except 包裹、`|| true`、def test_ 数≠场景数、未登记 marker"等**可机器判定**的违规;**退出码非 0 → 必须先修复再执行 pytest**(形成 validator→fix→repeat 反馈环,把违规挡在长时执行之前)。
- **门禁是兜底,不是替代**:断言分层是否合理、是否对齐需求语义,仍由阶段二对齐检查负责;门禁通过不代表语义正确。
- 阶段四/五回退重入阶段三、或修复后再次执行前,同样建议重跑门禁确认未引入新机械违规。

**失败证据采集(定位类根因的关键输入)**:

- 对**含定位类高风险交互的用例**(操作项默认隐藏、同名菜单需 nth、复杂表单组件、自定义组件等),建议执行 pytest 时启用失败 DOM 快照开关 `TEST_SELF_HEAL_DUMP_DOM=true`,失败时刻 `page.content()` 会落盘到 `skill_runs/test-self-heal/dom/`,作为 Reproduce/Diagnose 的一等证据。
- 该开关默认关闭、失败吞异常、不污染既有测试;若项目尚未具备该失败钩子基建,**不阻塞主流程**,按现有截图+日志证据推进即可。

**项目上下文锚点**(诊断时必须考虑):

- 框架:Playwright + Pytest + POM,`pages/` 是页面对象层,测试层禁止用 `locator()` / `expect()` / XPath
- Fixture 作用域:`session` → `browser` / `config` / `ssh_host`;`class` → `browser_context` / `ssh_vm`;`function` → `page`(每个测试新开标签页,自动登录)
- 后端验证:`ssh_host.run("scli ...")` 直连环境;`ssh_vm` 经跳板机连虚机
- 异步中间态高发场景:ECS/EVS 创建删除、快照还原、备份任务、SLB 状态收敛
- pytest.ini 约束:默认排除 `-m 'not slow'`;新增 marker 必须同步更新 `pytest.ini` 的 markers 列表

## 阶段三执行顺序(总导航)

进入阶段三后,严格按以下顺序执行,不得跳节:

1. **先跑静态门禁**(按"一、执行前置要求"的门禁段):门禁未通过 → 先修机械违规,再执行 pytest
2. **首次执行所有测试文件**(按"一、执行前置要求");失败用例 ≥3 → 触发 3.6 批量主因优先;**对高成本用例(单次墙钟 > 15min)按"六、高成本用例的执行提效"组织诊断与重跑**
3. **进入单用例修复循环**:每轮必读"二、修复前强制约束",必走"四、四步修复法"
4. **特殊机制触发**:第 2 轮起检查 3.2 进展奖励;第 3 轮强制 3.4 Mini-Checkpoint;每轮自动检查 3.3 状态冻结;同一用例累计 ≥3 次仍失败强制走 3.7 Phase 4.5 质疑
5. **达到上限后**(单用例 5/7 轮、全局 15 轮)→ 标记遗留问题;所有用例达可接受状态 → 进入阶段四

## 二、修复前强制约束(在做任何修改前必读)

### 2.1 修复纪律

- 严禁盲目修改代码 —— 盲目修改会引入回归或掩盖真实根因(基于错误假设的重复尝试由 3.3 状态冻结机制兜底)
- **"快速让测试通过"不是目标,"按根因分析正确修复"才是目标** —— 任何为了让本轮 PASSED 而绕过根因的动作都是错误修复
- **修复必须遵循阶段二编码规范** —— 阶段二(`references/phase_02_coding.md`)中定义的全部编码规范同样适用于阶段三的修复动作;凡是阶段二禁止的写法,阶段三修复时一律禁止;凡是阶段二要求的写法,阶段三修复时一律遵守
- **数据与结构纪律** —— 清理顺序必须严格依据测试需求 CSV 的"测试数据清理顺序"字段执行,不得自行调整;严禁擅自修改 CSV 已明确定义的测试数据/参数(端口、协议、权重、IP、规格、数量等);多个仅参数不同的高度重复需求应用 `@pytest.mark.parametrize` 参数化,严禁合并进同一测试方法

### 2.2 ❌ 错误修复模式速查表(命中任一项 → 立即停止,回 Diagnose)

**反模式识别口诀**:遇"补充逻辑 / 绕过失败 / 掩盖错误"动作 → 强制对照下表;表里没有的变体也按下表精神识别(如 `if not exist: 补创建` 是第 5 项变体,`|| true` 是第 12 项)。

| # | 错误修复模式 | 正确做法 |
|---|---|---|
| 1 | 把"快速让测试通过"当首要目标,跳过根因分析直接调代码 | 先完成 Diagnose,再按根因类别修复 |
| 2 | 用 `try/except` 兜底吞错让用例继续 | 让真实异常抛出,修复实际问题 |
| 3 | 加 `page.wait_for_timeout(N)` 固定等待"绕过"超时 | 用 `wait_for_page_ready()` / `wait_for_operation_complete()` / `wait_for_source_complete()` 等收敛点 |
| 4 | 把断言"等于"改"包含"、删除断言、放宽预期 | 保持原断言强度;若产品行为改变 → 产品缺陷 |
| 5 | 用 `pytest.skip()` / `@pytest.mark.skip` / 注释掉失败步骤 | 环境问题在结果分析阶段标记,不改脚本 |
| 6 | 改 `pages/` 已有公共方法的定位逻辑绕过页面对象缺陷 | 记录为页面对象修复项,提请测试开发处理 |
| 7 | 修改 CSV/MD 中的端口、协议、权重、URL 等业务参数让脚本通过 | 业务参数偏差是产品缺陷或环境问题,不是改 MD 的理由 |
| 8 | 移除 `@submenu` 等已有装饰器以"消除报错" | 装饰器报错通常是环境问题(抽屉遮挡/导航异常),修环境不动装饰器 |
| 9 | 测试层引入 `locator()` / `expect()` / XPath / 直接 `from playwright import expect` | 必须通过 Page Object 封装的方法调用 |
| 10 | 在测试主流程里加 `try/finally` 包裹核心步骤 | 用 fixture 的 yield 机制管理清理 |
| 11 | 忽视 teardown 阶段的 ERROR(如清理失败、SSH 断连) | teardown ERROR 视同用例问题,必须修复;teardown WARNING 必须记录 |
| 12 | 用 `\|\| true`、`echo $?` 兜底掩盖 SSH 命令失败 | 必须断言 `rc` 和 `stdout` |
| 13 | 凭空构造新定位(未经前端代码/运行时侦察佐证就改 locator 试错) | 必须以 `Grep` 前端工程代码或 `recon_page.py` 运行时渲染态为依据再改 |
| 14 | 把"前端流程/表单结构性差异"当普通定位反复改 locator | 识别为结构性差异 → 回对齐需求 MD 重新梳理步骤,而非死磕 locator |
| 15 | 为"复现快"把调试期裁剪(跳前置/复用资源)固化进脚本 | 调试期手段≠脚本逻辑;最终判定通过必须是一次完整、未裁剪的执行(见"六") |
| 16 | 只为消除 teardown 报错而弱化清理(删清理步骤、清理加 `\|\| true`) | teardown 是成功标准一部分,按根因修清理逻辑,不绕过 |
| 17 | 把 P0/P1 断言降级(P0 必断的成功弹窗/存在性/状态收敛被删或改弱以求过) | 断言分层是需求覆盖的一部分,按 `assertion_guidelines.md` 保持分层强度 |
| 18 | 擅自修改已有且稳定的方法以适配本用例(改稳定的 Page Object 业务方法、断言方法、fixture 内部实现去迁就本用例) | **扩展而非改写**:新建 `assert_<对象>_<新验证点>`/新业务方法,或给原方法新增带默认值的可选参数(保持原行为不变);`assertions/`、`common/` 内已封装方法严禁直接改 |

### 2.3 修复前 7 项强制自检(每轮 Fix 步骤必须逐条勾选并输出到对话框)

```
□ 1. 触及 CSV/MD 业务参数?              ___(是 → 禁止修复,回 Diagnose)
□ 2. 触及 common/ 或 refrence/ 公共代码?  ___(是 → 禁止修复)
□ 3. 触及 pages/ 已有定位逻辑?           ___(是 → 禁止修复,记录为页面对象修复项)
□ 4. 测试层引入了 locator/expect/XPath?   ___(是 → 禁止修复,回 Diagnose)
□ 5. 使用了 wait_for_timeout 固定等待?    ___(是 → 禁止修复,改用收敛点等待)
□ 6. 用 try/except 吞错或放宽了断言?       ___(是 → 禁止修复,回 Diagnose)
□ 7. 仅涉及 test_*.py 和必要页面对象?     ___(否 → 禁止修复,回 Diagnose)
```

任一项不通过 → 回 Diagnose 重新分类,**不允许带着违规修复进入下一轮**。
**未在反馈中完整输出本节 7 项 checkbox = 视为本轮修复未开始,不得进入代码编辑**(此为硬约束,对抗多轮循环遗忘)。

## 三、防循环与进展奖励机制

### 3.1 单用例修复轮次基础上限:5 轮

单个用例累计 5 轮仍未修复 → 标记"遗留问题(用例问题-轮次耗尽)",停止该用例。

### 3.2 进展奖励轮次:+2 轮(每个用例最多触发一次)

**触发轮次**:从该用例的**第 2 轮**起每轮都做检查,任意一轮满足触发条件即可生效。

**触发条件(以下任一即可,需在反馈中明确标注证据)**:

- **根因类型变化**:根因类型从 A 类切换到不同类(如从"用例问题"切到"产品缺陷";或同为用例问题但子类型从"等待时机"切到"定位错误"且基于新证据)
- **失败现象本质变化**:失败步骤、错误类型、堆栈位置发生本质改变(不是同一行同一报错重复出现)

**奖励规则**:满足触发条件 → 该用例上限 5 → 7 轮(仅奖励一次,7 轮仍未修复 → 标记"遗留问题(用例问题-奖励耗尽)");**触发奖励必须在反馈中显式声明**:`【进展奖励】触发,本用例上限 5 → 7 轮,依据:{证据}`

### 3.3 状态冻结检测:连续 2 轮无变化

连续 2 轮失败现象、根因类型、修复方案完全相同 → 标记"遗留问题(用例问题-状态冻结)",停止该用例。

### 3.4 第 3 轮 Mini-Checkpoint:零基重新分析(强制)

**触发时机**:**该用例的第 3 轮**修复(不是阶段三全局第 3 轮)。每个用例独立计数。

任意用例进入第 3 轮修复时,**强制做一次零基重新分析**,而不是基于前两轮假设递推:

```
【零基复盘 - 强制执行】
1. 重新完整阅读需求 MD 中本场景的预期行为(忘掉前两轮假设)
2. 重新读取最新日志的完整堆栈,找最早的异常来源(不是最深的)
3. 检查是否有公共因素(fixture / 页面对象 / 上游用例污染)
4. 重新做证据收集 → 重新做根因判定 → 给出与前两轮不同的假设或明确确认前假设
```

零基复盘后若仍维持原假设,必须给出新证据支持;否则视同状态冻结。

### 3.5 全局修复轮次上限:15 轮

整个阶段三累计 15 轮后,未修复用例全部标记"遗留问题(全局轮次耗尽)",停止修复,进入阶段四、五。遗留问题不参与阶段五验证。

### 3.6 批量失败主因优先(仅在首轮触发,且失败用例 ≥3)

**触发条件**:某测试文件**首次** pytest 执行后,失败用例数 ≥3 → 触发本机制(后续轮次不再触发)。

**先做主因聚类再开修**:

- 是否同一 fixture 报错(setup / teardown 失败)→ 先修该 fixture
- 是否同一页面对象报错(同一 locator / 同一方法)→ 先修该页面对象的下游用例
- 是否同一前置资源缺失(SLB / VPC / VM 未就绪)→ 先确认前置 fixture
- 是否同一 SSH 命令报错 → 先确认目标节点和命令语法

**主因修完后再用一轮验证整体改善**,避免对每个连锁失败用例独立耗轮次。**轮次归属**:批量主因修复占用 1 轮全局轮次(计入 3.5 全局 15 轮上限),不计入任何单用例的 5 轮基础上限。

### 3.7 三次失败质疑根因/架构(Phase 4.5,强制)

**触发时机**:同一用例修复累计 **≥3 次**仍失败(与 3.4 第 3 轮零基复盘叠加生效:3.4 解决"换个假设",3.7 解决"是不是方向/对象本身错了")。

进入本机制时,**停止"头痛医头"式的第 4 次定位/等待修补**,强制在反馈中显式回答三问并给出结论:

```
【Phase 4.5 - 三次失败质疑(强制显式输出)】
1. 是否实为产品缺陷? → 用四步法 Diagnose"判定纪律"中的"后端取证(scli/SSH)"复核 UI 与后端是否均异常
2. 是否需求理解/脚本结构本身错了? → 回读需求 MD,确认不是"在错误的步骤/对象上反复改 locator"(可能需较大重写而非局部改)
3. 是否每次修复都在"别处"冒新问题? → 是 → 架构性信号,不是单点 bug,标记需人工评估
```

- 三问结论必须显式写入本轮反馈,再决定是否继续(仍受 3.1/3.2/3.5 轮次上限约束)。
- 若复核后判定为产品缺陷/环境问题 → 转对应处理路径,不再消耗用例修复轮次。

## 四、四步修复法(每轮修复必走全流程)

### 第一步:复现(Reproduce)

```
[ ] 1. 重读需求 MD 对应步骤的预期行为
[ ] 2. 定位日志文件,看完整堆栈,确认错误类型(TimeoutError / AssertionError / 定位错误 / SSH 错误 / 其他)
[ ] 3. 查看失败截图;若已启用 DOM dump,一并查 skill_runs/test-self-heal/dom/ 下的失败 DOM 快照,对比预期 vs 实际页面状态/真实元素
[ ] 4. 诊断优先用已有证据,不强制全量重跑(见下"诊断重跑分离");仅"失败不稳定/疑似环境波动"时才补跑确认
[ ] 5. 截图、DOM 与日志冲突时,以截图、DOM 和日志事实为准
```

> **诊断重跑分离(高成本用例提效,见"六")**:Diagnose 应优先基于"已有证据(日志最早异常源 + 失败截图 + DOM 快照 + 后端 scli 取证)"推理,**不必每轮都全量重跑**;只有失败不稳定(首次失败、补跑通过)需要确认环境问题时才补跑,且高成本用例可只重跑到失败步骤的最小前置,而非整条。**修复后才做一次完整用例验证**(避免"边猜边全量长跑")。

### 第二步:隔离(Isolate)

按错误类型只执行对应动作,不要全部执行:

| 错误类型 | 隔离动作 |
|---|---|
| **TimeoutError** | 检查是否在 `wait_for_load_state('networkidle')` 之前操作;用 `.count()` 验证 locator 命中数;查异步加载未完成 |
| **AssertionError** | 对比预期值与实际值,辨别"数据被污染"还是"断言逻辑错误"(如写死期望值但实际动态) |
| **定位类错误** | 用 `page.locator(selector).all()` 或 `recon_page.py`(运行时侦察,先 `--help`)列出页面真实匹配元素,对比实际文本/属性;若有失败 DOM 快照一并比对;确认是否在正确的 dialog/tab/表格/行范围内;**先用 `Grep` 查 `sugon_web/refrence/` 前端工程代码确认定位/文案是否真的对不上** |
| **SSH 连接错误** | 检查 `ssh_host.run()` / `ssh_vm.run()` 命令语法、目标节点可达性、资源是否已创建成功;核对 MD 中 SSH 命令转换是否正确 |
| **其他**(仅在以上 4 类均不匹配时才使用,严禁作为 catch-all 默认归类) | 检查环境状态(测试环境是否重启、节点是否可用);若仍不能定位,补查前端工程代码 |

### 第三步:诊断(Diagnose)

**7 条分析原则(必须遵守)**:

1. 先还原事实,再下结论
2. 区分报错表象和真实根因 —— 超时 / 点击失败 / 接口报错 / 断言失败都是表象,不是根因
3. **回溯最早异常源**:读最新日志完整堆栈,定位**最早的异常来源**(不是最深/最后那个报错);长流程用例中,后段失败优先排查前段是否埋因(上游资源未就绪、异步未收敛、上一步污染)
4. 结合失败前后上下文 —— 前序步骤、资源变化、页面状态、异步收敛
5. 截图、DOM 与日志、代码交叉验证;冲突时以截图、DOM 和日志事实为准
6. 仅基于本次提供的材料分析,不假设未提供的信息
7. **检验隐含前提,不默认基础功能正常** —— 搜索/过滤/分页/表单提交等基础 UI 操作,"已生效"是需验证的假设而非默认前提(如搜索后结果集完全未变,根因可能是"搜索未生效",而非"目标不存在");证据不足时保留不确定性,但仍需给出当前最合理的单一主结论 + 置信度

**根因结论只能 3 选 1**:**环境问题** / **用例问题** / **产品缺陷**(遗留问题由本文第三节机制统一标记,不属于单次根因判定)

**判定纪律**:

- 判定为【用例问题】前,必须明确排除【产品缺陷】和【环境问题】并给出排除依据;严禁缺乏证据时默认归类为用例问题
- **后端取证(区分"产品缺陷 vs 用例问题"的通用动作)**:当 UI 现象疑似"操作成功但结果不对/状态不收敛/字段不一致",判定产品缺陷或用例问题前,应尽量用 `ssh_host.run("scli ...")` 或 `ssh_vm` 取后端真实状态作为交叉证据 —— UI 与后端均异常且非脚本/定位问题 → 产品缺陷;UI 异常但后端正常 → 多为用例问题(等待/定位/断言逻辑);证据不足且无法取证 → 保留不确定性,不默认归"用例问题"
- 失败不稳定(首次和补跑现象不一致)→ 重跑 3 次,3 次中 ≥2 次通过则判定环境问题(**重跑验证不计入修复轮次**,因为是诊断动作非修复动作)
- 信息不足以形成明确假设时,**必须**补查 `sugon_web/refrence/` 前端工程代码:
  - 用 `Grep` 搜索失败现象中的关键文案(如未知中文字符串、状态值、按钮名称、错误信息文案)
  - 用 `Grep` 搜索失败用例涉及的资源类型/接口路径(如健康检查、监听器、成员状态判定逻辑)
  - **未查证 → 不得判定为"用例问题"**(此为硬约束,与上一条排除依据要求联动)
- **证据优先级**:截图 / DOM 快照 > 日志 > 代码实现 > 推断

**Diagnose 输出格式**(简洁,4 节):

```
1. 结论:根因分类(环境/用例/产品) + 1~2 句摘要 + 置信度(高/中/低)
2. 关键证据:2~4 条,每条标注证据级别(截图/DOM 快照 > 日志 > 代码 > 推断)
3. 排除项:为什么不是其他两类(各 1 句,缺一不可)
4. 修复建议:短期 1~2 条可执行动作,必要时补 1 条长期建议
```

### 第四步:修复(Fix)

修复前回读 Diagnose 结论,确认改动与根因匹配;**再做一步"对照同模块已通过用例"**:找同模块/同类已通过的用例或 Page Object 方法作参照,完整读其定位/等待/断言写法,列出"待修复处与参照的差异",按参照风格修复,严禁自创一套与本模块不一致的写法;然后按下方决策树执行:

```
根因 = 用例问题 → 输出 2.3 节 7 项自检 checkbox(逐条勾选)
                  ├─ 任一项不通过 → 回 Diagnose
                  └─ 全部通过 → 按以下顺序定位修复点(只改第一个命中的):
                        ① 定位方式错误 → 修正 locator(优先 get_by_role / get_by_text(exact=True));
                           凭空定不准时先用 recon_page.py 运行时侦察或 Grep refrence/ 取证,严禁试错
                        ② 等待时机错误 → 用 wait_for_page_ready / wait_for_operation_complete / wait_for_source_complete
                        ③ 测试数据错误 → 用 random_data() 避免冲突;批量用 fixture 的 count 参数
                        ④ 业务流程偏差 → 按需求 MD 重新对齐测试步骤
                        ⑤ 其他(SSH 命令错误 / teardown ERROR / 资源依赖缺失等)→ 按 Diagnose 修复建议执行

                  涉及断言改动时,必须按本步骤下方"断言差分自检"块对照修复前后断言强度

根因 = 产品缺陷 → 不修复代码,对话框醒目提示"**发现产品缺陷,请提交缺陷**"+ 复现步骤 + 关键日志 + 截图,继续执行其他用例

```

**断言差分自检(根因为用例问题且本轮修复触及断言时,必须输出)**:

```

```

**Teardown 状态判定**(成功标准的一部分):

- **每次执行后必须主动扫描日志的 teardown/cleanup/fixture finalizer 段落**(`Grep` 日志中 teardown/清理/finalizer 关键字),如实记录 WARNING/ERROR,**不得只看测试步骤 PASSED 就判用例通过**。
- pytest PASSED 且 teardown 无 ERROR/WARNING → 用例通过
- pytest PASSED 但 teardown 有 ERROR → 视同用例问题,必须修复(按根因修清理逻辑,严禁删清理步骤或加 `|| true` 绕过)
- pytest PASSED 且 teardown 有 WARNING → 在问题清单中记录,不阻断本阶段完成

## 六、高成本用例的执行提效(诊断/修复重跑分离 + 分层执行)

> **背景**:复杂用例(如裸金属 BMS)单次成功执行的"产品侧固有等待"可达 70~100 分钟(PXE/发现/注册/就绪/清理等异步等待,不可压缩)。若每轮诊断和修复都全量重跑,会把固有等待乘以轮次,导致阶段三耗时数小时。本节用于在**不破坏任何修复纪律**的前提下,减少"全量长跑"的次数。

### 6.1 用例成本分级(进入阶段三时先做)

- 依据需求 MD 中各步骤的等待时长之和,粗判每个用例的单次墙钟成本。
- **低成本用例(单次 < 15min)**:维持现状,全量重跑最简单,不引入额外复杂度。
- **高成本用例(单次 > 15min)**:启用下方 6.2 的诊断/修复重跑分离与 6.3 分层手段。

### 6.2 诊断与修复"重跑分离"

- **诊断阶段不强制全量重跑**:Diagnose 优先基于已有证据(日志最早异常源 + 失败截图 + DOM 快照 + 后端 scli 取证)推理(见四步法 Reproduce/Diagnose);只有失败不稳定需确认环境问题时才补跑。
- **修复后才做一次完整用例验证**:避免"边猜边全量长跑";完整验证是判定通过的唯一依据。

### 6.3 缩短"复现到失败点"的分层手段(给方法,不强制)

对高成本用例,可用以下任一手段缩短定位时间,**必须遵守不破坏断言强度、不绕过步骤的红线**:

1. **就地复现优先用证据**:能从 DOM/截图/scli 后端确认根因的,不重跑。
2. **资源复用断点**:对前置资源已成功创建的情况,利用项目 fixture 作用域与 CSV"测试数据是否可复用"约定,在**调试期**复用已存在资源缩短前置;仅调试期,最终验证仍全量。
3. **分场景拆分**:一个 CSV 含多个可独立场景时,阶段二就按"数量对齐"产出多个 `def test_`,阶段三可用 `-k` **只重跑失败的那个测试方法**,而非整文件。

### 6.4 红线(硬约束)

- 分层/断点续跑**只用于"缩短定位时间"**;**最终判定该用例通过,必须是一次完整、未做任何调试期裁剪的执行**。
- **严禁**把"调试期跳过前置/复用资源"固化进脚本(命中 2.2 速查表第 5 项 / 第 15 项)。
- 本节不改变防循环轮次上限,也不改变任何修复纪律。
