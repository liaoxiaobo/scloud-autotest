# 阶段二：脚本编写与对齐

## 第一部分：编写自动化测试脚本


````
在开始本次任务之前，你必须先全文阅读以下文件：
 1、sugon_web/case_specs/prompts/test_case_codegen_prompt.md，这个文件是UI自动化测试脚本的开发规范，旨在指导和约束你基于该项目现有的框架结构，编写出标准、统一且可复用的测试代码。你在编码过程中必须严格遵守这里面的规范。
 2、sugon_web/case_specs/fixtures_index.md，这个文件包含fixture强制约束和速查表。文件开头的"编写用例前必读"章节规定了fixture的强制要求，并列出了所有可复用的fixture。编写用例前必须先阅读此文件，优先复用现有fixture，不要针对已有的fixture进行重复封装。重复封装会增加维护成本并可能导致用法不一致。
 3、阶段一产出的需求 md 文件。这是阶段一从 CSV 转换并校验完善的结构化需求文档，请从对话上下文中定位并读取该文件，你在编码过程中必须按照该文档中定义的测试需求编写自动化用例。
 4、被测模块对应的前端工程代码。执行以下步骤：
    1）确定前端工程根路径：通过 `ls -d sugon_web/refrence/*/` 列出所有子目录（该命令自动过滤非目录项），取其中的目录名作为前端工程根路径（若存在多个版本目录，执行 `ls -td sugon_web/refrence/*/` 按修改时间倒序，取输出的第一个目录）。
    2）确定测试模块名：从阶段一产出的 MD 文件存放路径推断（如文件放在 `case_specs/network/` 下则对应"网络"模块），或从 CSV 文件名、用户在对话中提到的模块名推断。
    3）读取 `sugon_web/refrence/module_index.yaml`，先过滤掉 value 列表中包含"废弃"或"禁止参考"字样的 key（这些为废弃或未启用模块，不参与匹配），然后对剩余的模块按以下**4级匹配策略**定位前端工程目录（搜索均不区分大小写）：
       **第1级（精确匹配 key）**：模块名与某个 key 完全一致 → 直接使用该 key。
       **第2级（精确匹配缩写）**：模块名与某个 value 列表中的**任何一项**完全一致（不区分大小写）→ 使用该 key。例如 `VPC`、`SLB`、`ER`、`TM` 均可在 `vpc` 的 value 列表中找到完全一致的项，直接命中 `vpc`；`EVS` 命中 `evs` 的 `EVS`。此级避免短缩写（如 `ER`、`TM`）落入第3级的子串匹配而产生误匹配。
       **第3级（模糊匹配 value 列表）**：
         - 在所有 value 列表中模糊搜索模块名。
         - 若**只命中一个 key** → 直接使用该 key。
         - 若**命中多个 key** → 结合阶段一产出的 **MD 文件内容**进行二次筛选：在 MD 中搜索各候选 key 的标识（key 本身、value 列表中的各子模块缩写），统计出现频次，取出现频次最高的候选 key 作为匹配结果。例如搜索"网络"同时命中 `vpc` 和 `vpn`，若 MD 中出现 `VPC`、`SLB`、`EIP` 等标识则判定为 `vpc`，若出现 `VPN` 则判定为 `vpn`。
         - 二次筛选后仍无法区分（各候选频次相同或 MD 中均无相关标识）→ 进入第4级。
       **第4级（无法定位）**：第1~3级均未命中唯一 key → 视为匹配失败。
    4）若匹配成功，拼接 `根路径/匹配的目录名` 得到完整路径，读取该路径下的前端工程代码。
    5）若匹配失败（包括 modules 中搜索不到该模块名、第3级歧义无法消解、或对应目录在文件系统中不存在），**立即停止该任务**，并在对话框中输出醒目提示：已结束本任务，因为无法找到与本任务对应的前端工程目录，请直接告知该任务对应的前端工程目录，以便继续执行本任务。

**搜索工具约束（查阅前端代码时必须遵守）：**

- 必须使用专用搜索工具（`Grep`、`Glob`、`Agent` 或 `Read`）
- 不要使用 `Bash(python -c ...)` 或 `Bash(find/grep/...)` 等 shell 命令做文件搜索。shell 命令会绕过专用搜索工具的优化逻辑，导致搜索结果不完整。
- 推荐策略：先通过 `Agent` 工具（用于复杂目录探索）快速定位目标模块目录和关键文件 → 再通过 `Grep` 精确搜索元素选择器、按钮文案 → 最后通过 `Read` 精读关键组件文件
- 禁止行为：不要批量读取整个前端目录。批量读取会浪费 token 且引入无关内容；不要用 shell 脚本遍历文件做内容匹配；不要把前端代码复制到测试文件中。复制前端代码会破坏引用关系。

**推荐用例骨架（编码时参考）：**

```python
@allure.title("模块-功能点")
def test_xxx(self, page_fixture, resource_fixture):
    # page_fixture 和 resource_fixture 为占位符，实际使用时替换为对应模块的 fixture（如 page、vm、vpc 等）
    """一句话描述测试目的"""
    xxx = ...

    with allure_step_log("步骤1: 准备测试数据"):
        ...

    with allure_step_log("步骤2: 执行页面操作"):
        ...

    with allure_step_log("步骤3: 验证结果"):
        ...
```

 阅读完以上文件之后，你再根据这些文件中的内容，开始编写本次任务的自动化测试用例。编写和修复脚本时，严禁修改阶段一产出的 MD 需求文档，除非确认 MD 本身存在转换错误（如未按 CSV 转换、描述错误等）。脚本执行失败不得作为修改 MD 的理由。
````

**生成后强制自检（第一部分结束前必须执行）：**

代码生成完成后、进入第二部分之前，必须执行以下自检。凡是与 `test_case_codegen_prompt.md` 明确冲突的项，必须先修正；其余项作为质量提醒处理。

| 检查项 | 检查方法 | 不通过的判定标准 |
|--------|----------|-----------------|
| vm 参数化格式 | `Grep` 搜索 `@pytest.mark.parametrize("vm"` | 发现 `{"count":` 且前面没有 `"basic":` |
| try/finally | `Grep` 搜索 `try:` + `finally:` | 测试方法体内出现 `try/finally` |
| Playwright API 越层 | `Grep` 搜索 `\.locator\(`、`from.*playwright import expect` | 测试层出现 `locator()` 或 `expect()` |
| Helper 位置 | `Grep` 搜索 class 体内是否有 `_` 前缀的辅助函数 | class 体内存在 Helper 方法 |
| 断言完整性 | 核对步骤与校验 | 存在只有操作日志、没有结果断言的关键步骤 |
| 日志掩盖错误 | `Grep` 搜索 `` `\|\| true` `` | SSH 命令中出现 `` `|| true` `` |
| fixture 复用 | 核对是否引用了 `fixtures_index.md` 中的 fixture | 自行封装了功能重复的 fixture |
| 用例数量对齐 | `Grep` 搜索正则 `def test_\w+` 数量 | 测试方法数 < CSV 行数 |

自检通过后，输出本次生成的所有测试文件路径清单，供后续阶段引用。

**自检失败后的处理**：根据失败项列表重写对应代码 → 重写后再次执行自检 → 循环直至全部通过。

## 第二部分：测试脚本与需求对齐检查（自主循环）

> 第一部分编写完脚本后，对照阶段一产出的需求 MD、第一部分引用的编码规范（`sugon_web/case_specs/prompts/test_case_codegen_prompt.md`）**以及对应前端工程代码**逐项检查，发现遗漏或偏差直接修改，循环直至完全对齐。

**一、需求对齐检查**

1. **步骤完整性**：脚本覆盖了需求 MD 中的所有测试步骤，无遗漏、无多余，步骤顺序与需求一致
2. **边界条件覆盖**：脚本实现了需求 MD 中定义的所有边界条件测试代码
3. **断言完整性**：脚本实现了需求 MD 中定义的所有断言点，断言内容与需求一致，SSH 后端验证和列表字段回读无遗漏
4. **测试数据对齐**：资源名称使用 `random_data()`，批量创建使用 fixture 的 `count` 参数，测试数据准备与前置条件一致；vm 批量创建必须使用 `{"basic": {"count": N}}` 格式（count 必须在 basic 子字典中），不要写成 `{"count": N}` 或手动循环创建。这两种方式无法利用 fixture 的批量创建和自动清理能力，会增加代码冗余
5. **清理策略对齐**：脚本实现了需求 MD 中定义的所有清理步骤，清理顺序与需求一致，所有创建的资源均已覆盖；清理核心原则为"清理 fixture 负责回收，测试方法只负责测试"，若资源已由现有 fixture teardown 完整覆盖则直接复用，若现有 teardown 无法覆盖则参照 yield-based cleanup fixture 模式补充。若 MD 中标注了"共享同一套测试数据"，必须将这些场景置于同一测试类中通过 class-scoped fixture 共享资源，待该批次所有用例执行完成后统一清理

**二、编码规范检查**

1. **fixture 复用**：优先复用现有 fixture，未自行封装功能重复的 fixture，已阅读 `fixtures_index.md` 确认参数支持情况；实现测试步骤或前置条件时已参考该文件
2. **页面对象规范**：页面对象只封装交互逻辑不组织测试步骤，新增方法有 docstring，未新增与现有公共能力同义的方法
3. **定位规范**：优先使用 `get_by_role()` / `get_by_text(exact=True)` / `get_by_placeholder()`，限定在 dialog / tab / 表格 / 行范围内定位，不要使用 XPath。XPath 脆弱且难以维护，页面结构微调就会导致定位失败；`first()` / `nth()` 不作为首选，应先缩小范围后再作为兜底
4. **等待规范**：进入页面或表单提交后先执行 `wait_for_page_ready()` 或 `wait_for_load_state('networkidle')`，优先使用 `wait_for_operation_complete()` / `wait_for_source_complete()`，不要使用固定等待。固定等待会增加执行时间且不保证页面加载完成
5. **断言规范**：状态变更类断言顺序为：成功弹窗 → 资源状态 → 列表字段/详情字段；SSH 命令执行后必须断言返回值（`rc`、`stdout`），不要使用 `` `|| true` `` 掩盖命令错误，因为这会静默吞掉 SSH 命令失败，导致测试通过但实际环境未就绪；每步操作后必须紧跟断言（`assert` 或框架断言方法），不要仅记录日志（`logger.info`）而不做断言，因为日志不能替代验证；列表断言优先使用 `assert_list_contain()` / `assert_status()` / `assert_deleted()`
6. **用例结构规范**：用例结构为准备数据 → 执行操作 → 校验结果，步骤使用 `with allure_step_log()`，测试主流程未使用 `try/finally` 或 `try/except` 包裹核心步骤

**循环规则：** 按上述 11 项逐项检查 → 发现不符合 → 修改脚本 → 重新检查 → 直至全部符合。
- **遵循通用循环约定，严禁停下来询问用户**，因为循环中断会浪费已执行的进度，所有检查发现的问题自主修改
- 直至全部检查项均通过，方可进入下一阶段
