# UI 自动化测试脚本开发 SKILL

## 长时间自主任务声明

本 SKILL 执行期间 **AI 全程自主运行**，严禁停下来询问用户，因为本任务设计为长时间自主运行，中途等待用户响应会中断自动化流程。所有修复/检查决策自主完成，仅在无法自主解决的阻塞性问题时允许暂停请求输入。任务从需求转换到稳定性验证可能持续数十分钟至数小时。

> **设计哲学**：给足修复机会，但绝不死磕；检测无意义循环，而非掐表计时。

> **墙钟感知（兜底防失控，不替代根因优先）**：对高成本用例（单次墙钟 > 15min），除阶段三的"次数上限"外，引入墙钟提醒——当某用例累计修复+重跑墙钟显著超出预期（如单用例 > 3 小时仍未通过），**强制触发一次阶段三 3.7 的 Phase 4.5 三次失败质疑**，并优先考虑"标记为遗留问题/疑似产品缺陷、转人工"，而非继续耗轮次。这是防失控兜底，仍以"检测无意义循环而非掐表计时"为准。

## 运行报告持久化与恢复协议

为对抗上下文压缩导致前序阶段输出丢失，各阶段"立即输出"须在对话框输出的同时，双写到运行报告文件 `skill_runs/test-script-workflow/test-script-workflow_{任务标识}_{YYYYMMDD_HHMM}.md`（具体写入要求见各 phase 文件末尾"同步持久化"段）。全局规则：

- **任务标识与单文件**：任务标识统一取本次任务的需求 MD 英文文件名（去 `.md`），五个阶段一律以此为准，**不得改用测试脚本名**（脚本名与 MD 名常不一致，会导致 glob 匹配不到而分裂出第二个文件）。一次运行只用一个文件（放 `skill_runs/test-script-workflow/`，严禁写入 `logs/`），由首个执行的阶段创建，其余阶段先 glob 找到该文件再在末尾追加（含回退轨迹），**严禁新建第二个文件、严禁覆盖前序内容**。
- **双写不替代**：严禁用写文件替代对话框输出，也严禁用对话框输出替代写文件。
- **压缩后续跑**：每阶段开始前先按 glob `skill_runs/test-script-workflow/test-script-workflow_{任务标识}_*.md` 取最新文件 `Read`，据此判断已完成到哪、从哪重入；任务标识统一从磁盘上的需求 MD 文件名推导，不靠对话记忆。
- **阶段闸门**：进入下一阶段前，须先 `Read` 运行报告文件 `skill_runs/test-script-workflow/test-script-workflow_{任务标识}_{YYYYMMDD_HHMM}.md` 确认上一阶段完成块已写入，缺失则先补写再继续。
- **各阶段报告必出区块清单**（压缩也带不走的硬清单；缺任一即视为该阶段未完成，必须补写）：
  - 阶段一：`## 阶段一…完成时间` + 完成清单表
  - 阶段二：`## 阶段二…完成时间` + 完成清单表
  - 阶段三：`## 阶段三…完成时间` + 完成清单表 + 5.2 修复循环问题清单（含根因列）
  - 阶段四：`## 阶段四…完成时间` + 完成清单表
  - 阶段五：`## 阶段五…完成时间` + 4.2 完成清单 + 4.3 问题总结 + **4.4 第一部分四张表（① Fixture ② Page Object ③ Helper ④ 断言复用/新增清单）+ 4.4 第二部分 10 列经验沉淀表**（最重、最易被压缩漏写，一表/一列都不能省）
  - 全局总结（面向人）：`## 完成后输出` + 1.总体结论 + 2.执行概览 + 3.风险与后续待办 + 4.产物位置索引（全局总览，不与各阶段明细重复）
- **落笔前就近重读 + 写后机器校验（强制，对抗压缩漏写/写简）**：每个阶段在生成"立即输出"前，先重新 `Read` 对应 phase 文件末尾的"立即输出"整节，按其确切表头逐项写全；写完后运行报告锚点校验脚本确认结构齐全：`python .claude/skills/test-script-workflow/scripts/report_check.py <本次运行报告 md 路径> --phase <1/2/3/4/5/final>`，退出码非 0（缺锚点）→ 必须按提示补写后重跑，通过方可进入下一阶段或总收尾。
- **全局总结从文件聚合**：全部完成后的全局总结（总体结论/执行概览/风险待办/产物索引）须先 `Read` 报告文件后聚合，不依赖对话记忆。

## 五个阶段的执行编排

**本文件（SKILL.md）为总控文件**，只定义工作流编排、阶段顺序、文件读取关系和全局约束。**各阶段的具体执行指令、提示词、要读取的关联文件、检查清单详见 `references/` 目录下的对应文件及其引用的关联文件**，执行各阶段前必须先读取对应 reference 获取完整指令。

执行以下各个阶段任务的过程中，必须先使用 Read 工具完整读取下文提到的该阶段"读取文件"字段中 `references/` 目录下的 phase 文件，以获取该阶段的完整执行指令。应严格按照顺序读取 phase 文件及其列出的关联文件。严禁在未读取 phase 文件及其列出的关联文件的情况下开始执行阶段任务，因为各阶段指令分散在 phase 文件及其引用的关联文件中，跳过阅读会导致执行偏差。

### 阶段一：需求转换与校验
将 CSV 测试需求文件转换为结构化 MD 需求文档，并进行质量校验。

**读取文件：** `references/phase_01_requirements.md`（第一部分+第二部分），以及其引用的 `sugon_web/case_specs/templates/base_case.md`、`sugon_web/case_specs/fixtures_index.md`、用户提供的 CSV 文件
**文件内容：** CSV→MD 转换规范与 MD 质量校验
**前置条件：** 用户提供 CSV 测试需求文件
**执行顺序：** 先执行第一部分（CSV→MD），在同一文件中继续执行第二部分（MD 校验）
**完成标志：** CSV 已转换为规范的 MD 需求文档（若用户直接提供，标记为跳过），且 MD 文档已校验通过，无歧义无错误
**产出物：** 校验通过的 MD 需求文档
**异常处理：** 无

### 阶段二：脚本编写与对齐
基于 MD 需求编写 Playwright + Pytest 自动化测试脚本，并与需求进行对齐检查。

**读取文件：** `references/phase_02_coding.md`（第一部分+第二部分），以及其引用的 `sugon_web/case_specs/prompts/test_case_codegen_prompt.md`、`sugon_web/case_specs/fixtures_index.md`、`sugon_web/case_specs/prompts/assertion_guidelines.md`、阶段一产出的测试需求 MD 文件、`sugon_web/refrence/module_index.yaml`、被测模块对应的前端工程代码；以及本 skill 的辅助脚本 `scripts/recon_page.py`（运行时侦察，定位不确定时按需调用）、`scripts/precheck.py`（静态门禁，进入阶段三前必跑）
**文件内容：** 编码规范、断言规范、用例骨架、需求对齐与编码规范检查、运行时侦察、静态门禁闸门
**前置条件：** 阶段一完成
**执行顺序：** 先执行第一部分（编写脚本），在同一文件中继续执行第二部分（对齐检查）
**完成标志：** 脚本与需求完全对齐，各项检查全部通过
**产出物：** 对齐需求后的测试脚本
**异常处理：** 若无法定位被测模块对应的前端工程代码（按 `phase_02_coding.md` 中"匹配失败"的处理方式执行）

### 阶段三：执行用例与修复
执行测试用例，修复错误直至所有用例达到可接受状态。

**读取文件：** `references/phase_03_execution.md`，以及其引用的 `references/phase_02_coding.md`、阶段一产出的测试需求 MD 文件、`sugon_web/refrence/` 下被测模块的前端工程代码；以及本 skill 的辅助脚本 `scripts/recon_page.py`（诊断定位类失败时运行时侦察）、`scripts/precheck.py`（首次执行前静态门禁）
**文件内容：** pytest 执行与四步法修复：日志规范、静态门禁、Reproduce→Isolate→Diagnose→Fix、检查清单、高成本用例执行提效
**前置条件：** 阶段二完成（或用户提供现有脚本及对应 MD 文档）
**完成标志：** 所有用例达到可接受状态（用例问题已修复、产品缺陷已标记、环境问题已跳过）
**产出物：** 修复后的脚本 + 检查清单 + 日志文件
**异常处理：** 用例失败在阶段内部按四步法（Reproduce→Isolate→Diagnose→Fix）处理，无需跨阶段跳转。

### 阶段四：日志分析与核查
分析执行日志，核查测试需求覆盖度，并强制扫描 teardown 段告警。

**读取文件：** `references/phase_04_log_analysis.md`，以及其引用的阶段一产出的测试需求 MD 文件
**文件内容：** 日志分析与需求覆盖度核查：teardown 段强制扫描、重要/非重要问题分级、完成标志
**前置条件：** 阶段三完成
**完成标志：** 日志分析完成，每个步骤与需求一致，且 teardown 段已扫描并分级
**产出物：** 日志分析与核查报告
**异常处理：** 若日志分析发现重要需求未满足或 teardown 段存在 ERROR → **返回阶段三**修复脚本后重新分析；若仅非重要细节问题（含 teardown WARNING）→ 直接进入阶段五

### 阶段五：稳定性验证
多次执行验证脚本稳定性（按用例成本自适应轮次：低成本 5 轮 / 高成本 3 轮）。

**读取文件：** `references/phase_05_stability.md`
**文件内容：** 稳定性验证：自适应轮次（低成本 5 轮 / 高成本 > 15min 用例 3 轮，阈值同步）、判定规则（环境/产品/用例）、经验沉淀
**前置条件：** 阶段四完成
**完成标志：** 所选轮次执行完毕后，通过轮次达标（低成本 ≥ 3 / 高成本 ≥ 2）且无未修复的用例问题（环境问题跳过、产品缺陷标记不计入）；若已标记产品缺陷，阶段五正常结束并提示提交缺陷
**产出物：** 稳定性验证结果
**异常处理：** 用例失败在阶段内部按稳定性判定规则处理，无需跨阶段跳转。

## 工具调用约束

修改测试脚本时，若 `Edit` 因 `old_string` 不唯一失败，严禁中断流程等待人工确认。按以下优先级自动恢复：

1. **扩大匹配范围**：立即 `Read` 文件，增加 surrounding 函数体或相邻注释使 `old_string` 唯一
2. **使用 replace_all**：确认所有匹配处需相同修改时，改用 `replace_all=true`
3. **替代方案**：上述方法均不可行时，改用 `Write` 重写整个文件

`Edit` 和 `replace_all` 均失败时，必须使用 `Write` 作为最终降级方案；仅当 `Write` 也失败时，记录错误并继续下一步。严禁弹出确认对话框。

## 完成后输出（全局总结，面向人阅读）

**定位说明**：各阶段的明细（完成清单、问题清单、测试执行结果、经验沉淀等）已由各 phase 的"阶段完成时立即输出"逐阶段产出并写入运行报告，**本节不再重复这些明细**。本节是整次执行结束后，面向**人**的一段**全局总结**——让阅读者无需翻看各阶段明细，就能一眼掌握"这次干了什么、结果如何、能否投产、还有什么需要人处理、细节去哪看"。

**触发与口径**：所有阶段执行完毕并通过完成判定后输出，并追加写入运行报告文件末尾。内容须先 `Read` 运行报告文件后聚合生成，不依赖对话记忆；**严禁用本节替代任一阶段的立即输出**（两者并行，明细在阶段、总览在此）。

按以下四部分输出：

### 1. 总体结论

一句话给出本次执行的最终判定，让人立即知道结果。例如：
- ✅ `本次自动化用例编写完成并通过稳定性验证，可投入生产使用。`
- ⚠️ `用例已编写，但发现产品缺陷 N 处（需提交缺陷）/ 遗留问题 N 处（需人工介入），暂不可直接投产。`
- ❌ `本次执行未完成：{被迫中断的核心原因}。`

### 2. 执行概览

用一个总览表给出全局画像（不逐文件罗列，只给汇总数字）：

| 维度 | 内容 |
|---|---|
| 被测模块 / 需求来源 | 如：网络-负载均衡 / `requirements_csv/xxx.csv` |
| 场景总数 → 最终通过 | 如：2 → 2 |
| 稳定性验证 | 如：低成本 5 轮，通过 4/5（达标） |
| 产品缺陷 / 遗留问题 / 环境问题 | 如：0 / 0 / 1（各计数，0 也写明） |
| 五阶段状态 | 一/二/三/四/五：✅✅✅✅✅（或标注跳过/未通过） |

### 3. 风险与后续待办（人需关注）

仅列**需要人来处理**的事项，没有则写 `- 无，可直接投产`。例如：
- 产品缺陷：简述现象 + 复现要点，提示"请提交缺陷单"。
- 遗留问题：简述卡点 + 建议人工介入方向。
- 环境问题：简述受影响范围 + 建议优化的环境项。

### 4. 产物位置索引（细节去哪看）

指引阅读者到对应文件查看明细，**不复制明细内容**：

| 产物 | 位置 |
|---|---|
| 结构化需求 MD | `sugon_web/case_specs/{模块}/{需求}.md` |
| 测试脚本 | `sugon_web/testcase/{模块}/test_xxx.py` |
| 执行日志 | `logs/` 目录下对应日志文件 |
| 完整运行报告（含各阶段明细、经验沉淀） | `skill_runs/test-script-workflow/test-script-workflow_{任务标识}_{时间戳}.md` |
