# UI 自动化测试脚本开发 SKILL

## 适用场景

用户提供了 CSV 格式的测试需求文件，需要完成以下完整流程：
1. 将 CSV 转换为结构化 MD 需求文档并进行质量校验
2. 基于 MD 需求编写 Playwright + Pytest 自动化测试脚本并检查与需求对齐
3. 执行测试并修复错误直至所有用例达到可接受状态
4. 分析日志核对需求覆盖度
5. 多次执行验证脚本稳定性（至少 3 次）

---

## 长时间自主任务声明

本 SKILL 执行期间 **AI 全程自主运行**，严禁停下来询问用户，因为本任务设计为长时间自主运行，中途等待用户响应会中断自动化流程。所有修复/检查决策自主完成，仅在无法自主解决的阻塞性问题时允许暂停请求输入。遇到需修复的问题，直接参考 `sugon_web/case_specs/prompts/test_failure_analysis_prompt.md` 分析根因并修复。

---

## 工作流总览

**本文件（SKILL.md）为总控文件**，只定义工作流编排、阶段顺序、文件读取关系和全局约束。**各阶段的具体执行指令、提示词、检查清单详见 `references/` 目录下的对应文件**，执行各阶段前必须先读取对应 reference 获取完整指令。

### 正常流程

```
CSV需求 → MD文档与校验 → 脚本编写与对齐 → 执行用例与修复 → 日志分析 → 稳定性验证 → 输出完成报告
```

### 异常/循环流程

- 阶段一（第二部分）、二（第二部分）、三、五含自主循环：发现不符合 → 修改 → 重新检查 → 直至通过
- 阶段四核查未通过 → 返回阶段三重新修复 → 再次进入阶段四
- 阶段三、五执行失败 → 按稳定性判定规则处理（环境问题跳过 / 产品缺陷标记 / 用例问题修复）

## 五阶段执行编排

### 阶段一：需求转换与校验
**读取文件：** `references/phase_01_requirements.md`
**执行顺序：** 先执行第一部分（CSV→MD），在同一文件中继续执行第二部分（MD 校验）
**完成标志：** MD 文档校验通过，无歧义无错误
**异常处理：** 无

### 阶段二：脚本编写与对齐
**读取文件：** `references/phase_02_coding.md`
**执行顺序：** 先执行第一部分（编写脚本），在同一文件中继续执行第二部分（对齐检查）
**完成标志：** 脚本与需求完全对齐，11 项检查全部通过
**异常处理：** 若无法定位被测模块对应的前端工程代码（按 `phase_02_coding.md` 中"匹配失败"的处理方式执行）

### 阶段三：执行用例与修复
**读取文件：** `references/phase_03_execution.md`
**完成标志：** 所有用例达到可接受状态（用例问题已修复、产品缺陷已标记、环境问题已跳过）
**异常处理：** 用例失败在阶段内部按四步法（Reproduce→Isolate→Diagnose→Fix）处理，无需跨阶段跳转。

### 阶段四：日志分析与核查
**读取文件：** `references/phase_04_log_analysis.md`
**完成标志：** 日志分析完成，每个步骤与需求一致
**异常处理：** 若日志分析发现重要需求未满足 → **返回阶段三**修复脚本后重新分析；若仅非重要细节问题 → 直接进入阶段五

### 阶段五：稳定性验证
**读取文件：** `references/phase_05_stability.md`
**完成标志：** 连续三次运行均无未修复的用例问题（环境问题跳过、产品缺陷标记不计入），或已标记产品缺陷
**异常处理：** 用例失败在阶段内部按稳定性判定规则处理，无需跨阶段跳转。

所有自主循环遵循：发现不符合 → 自主修改 → 重新检查/执行 → 直至全部通过。遵循"长时间自主任务声明"中的约定，严禁停下来询问用户，因为循环中断会浪费已执行的进度。若遇到无法自主解决的阻塞性问题，按"长时间自主任务声明"中的约定暂停请求输入。所有决策自主完成。阶段三、五的根因分析必须先读取 `sugon_web/case_specs/prompts/test_failure_analysis_prompt.md`。

## 硬性约束

### 一、代码约束

- 不要修改 `sugon_web/common/` 目录下的任何公共模块代码（包括但不限于 `base.py`、`playwright.py`、`ssh.py` 及 `mixins/` 子目录下的文件）。这些文件为框架公共模块，自行修改会影响全部测试用例且难以回滚。如需增强公共能力，记录需求即可。
- 不要修改 `sugon_web/refrence/` 目录下的前端工程代码。该目录为引用的外部工程，修改会导致代码与线上版本不一致，增加维护风险。（注意：项目实际目录名为 `refrence`，是已存在的非标准拼写，严禁更改该目录名。）
- 不要重复封装已有 fixture（如 `vm`、`vpc`、`slb`、`eip` 等），因为重复封装会浪费维护成本且可能引入不一致。编写用例前必须阅读 `fixtures_index.md` 确认可复用能力。
- 不要使用 XPath 定位元素，因为 XPath 脆弱且难以维护，页面结构微调就会导致定位失败。优先使用 `get_by_role()`、`get_by_text(exact=True)`、`get_by_placeholder()` 等语义化定位方式。
- 不要在测试主流程使用 `try/except` 包裹核心步骤来吞掉异常，因为这会掩盖真实的测试失败原因，导致问题被静默吞掉。不要在测试方法中使用 `try/finally`，因为资源清理应通过 fixture 的 yield 机制实现。
- 新增页面对象业务方法必须有 docstring，说明用途、参数含义、可选值或默认值。
- 页面对象只负责页面交互与业务动作封装，不负责组织测试步骤。
- 页面对象中如果已有公共能力能覆盖，不要新增同义方法，因为同义方法会增加维护成本且可能导致用法混乱。
- 元素定位优先限定在当前可见 `dialog`、当前激活 `tab`、目标表格或目标行范围内；`first()`、`nth()` 不作为首选，应先缩小范围后再作为兜底方案，这样可以减少定位歧义，避免误触非目标元素。
- 不要在测试层直接使用 `locator()`、`expect()` 等 Playwright 底层 API，因为这会破坏测试层的抽象边界，导致测试与页面实现紧耦合。所有页面交互必须通过 Page Object 封装的方法调用。

### 二、长时间任务约束

- 本任务从需求转换到稳定性验证可能持续数十分钟至数小时
- 本 SKILL 默认执行全部 5 个阶段。若用户明确指定了入口（如直接提供 MD 文档时跳过阶段一、仅修复现有脚本时跳过阶段一二），按用户指定入口执行。

### 三、工具调用约束

在修改测试脚本时，若 `Edit` 工具因 `old_string` 在文件中不唯一而失败，严禁中断流程等待人工确认，因为工具调用失败是常见情况，应优先通过自动恢复策略解决。必须按以下优先级自动恢复，直至修改成功或穷尽所有手段：

1. **扩大匹配范围**：立即 `Read` 文件，在 `old_string` 中增加 surrounding 函数体、类名或相邻注释，使匹配字符串在文件中唯一，重新执行 `Edit`
2. **使用 replace_all**：如果确认所有匹配处都需要完全相同的修改（如批量替换同类清理代码），则改用 `replace_all=true`
3. **替代方案**：若上述方法均不可行，改用 `Write` 重写整个文件

**核心原则**：`Edit` 工具调用失败时，必须先尝试自动恢复。若扩大匹配范围的 `Edit` 和 `replace_all` 均失败，必须使用 `Write` 重写整个文件作为最终降级方案；仅当 `Write` 也失败时，才记录错误并继续下一步。严禁弹出确认对话框。

## 完成后输出（按以下顺序）

### 2. 代码自检
- 是否已阅读 `fixtures_index.md`，确认参数支持情况（特别是 count 批量创建参数）
- 是否优先复用了现有 fixture，而非自行封装新的 fixture
- 是否已经阅读同模块现有用例，并按其标题风格命名
- 是否已经阅读相关页面对象、测试数据和已有公共能力，并优先复用
- vm 参数化是否使用 `{"basic": {"count": N}}` 格式，而非 `{"count": N}`
- 每步操作后是否有明确断言，而非仅记录日志
- 测试文件组织方式是否沿用了目标文件和同模块现有风格
- 是否通过 `pytest --collect-only` 或 Python 语法检查验证代码无基础错误

### 3. 测试执行结果
